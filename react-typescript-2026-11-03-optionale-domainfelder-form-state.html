Optionale Domain-Felder sind keine optionalen Formularfelder

Ein optionaler Wert im Zielobjekt bedeutet nicht, dass sein Feldzustand während der Bearbeitung fehlen darf.

03.11.2026 · TypeScript-Mapped-Types · TypeScript 6.0 · Tief · ~8 min

Im Profil ist die Telefonnummer optional. Der generisch abgeleitete Form-State übernimmt das Fragezeichen – und plötzlich ist auch form.phone optional. Die Komponente verwendet Optional Chaining, die Validierung überspringt das Feld gelegentlich, und touched existiert erst nach der ersten Eingabe. Eine fachlich optionale Telefonnummer hat einen strukturell lückenhaften Formularzustand erzeugt.

TL;DR

Mapped Types kopieren Property-Modifier des Ausgangstyps. Für einen registrierten Form-State ist das oft die falsche Semantik: Jeder Key braucht jederzeit value, touched und error, auch wenn der spätere Command den Wert weglassen darf. Entferne deshalb die Key-Optionalität mit -? und entscheide separat, ob null oder undefined gültige Feldwerte bleiben. Die Rückübersetzung in „vorhanden oder abwesend“ gehört an die Submit-Grenze.

Prerequisites

Du kennst keyof, indexierte Zugriffstypen und generische React-Komponenten. Die Beispiele beziehen sich auf TypeScript 6.0. Das Handbuch dokumentiert Mapping-Modifier; exactOptionalPropertyTypes verdeutlicht den Laufzeitunterschied zwischen einem fehlenden Key und einem vorhandenen Key mit undefined.

Der Aha-Effekt

Optionalität beschreibt zwei unabhängige Achsen. Erstens: Muss der Key im Objekt vorhanden sein? Zweitens: Darf sein Wert undefined oder null sein? Ein phone?: string im Update-Command beantwortet primär die erste Frage: Die Telefonnummer darf ausgelassen werden.

Der Form-State beantwortet eine andere Frage. Wenn das Telefonfeld gerendert, validiert und als „berührt“ markiert wird, braucht es einen dauerhaften Zustand. -? entfernt im Mapped Type den optionalen Property-Modifier. NonNullable<T[K]> normalisiert zusätzlich den Feldwert. Erst zusammen entsteht hier die beabsichtigte Invariante: Jeder Form-Key existiert und jedes Eingabefeld besitzt einen konkreten Wert.

So macht man es falsch

Die naive Abbildung übernimmt den Modifier von phone. Dadurch muss jede Konsumentin mit einem fehlenden Feldzustand rechnen:

import { useState, type ReactElement } from "react";

type ProfileDraft = {
  displayName: string;
  phone?: string;
  marketingOptIn: boolean;
};

type FieldState<T> = {
  value: T;
  touched: boolean;
  error: string | null;
};

type FormState<T> = {
  [K in keyof T]: FieldState<T[K]>; // übernimmt das ?
};

type ProfileForm = FormState<ProfileDraft>;

export function PhoneField({ form }: { form: ProfileForm }): ReactElement {
  return <label>
    Telefon
    <input value={form.phone?.value ?? ""} readOnly />
    {form.phone?.touched && <span>{form.phone.error}</span>}
  </label>;
}

Warum ist das falsch?

Optional Chaining verhindert nur den unmittelbaren Fehler. Es beantwortet nicht, wann der Feldzustand angelegt wird, ob ein fehlender Zustand „unberührt“ oder „nicht registriert“ bedeutet und ob die Validierung ihn ignorieren darf. Diese Mehrdeutigkeit wandert in Renderer, Validatoren und Submit-Code.

Das Symptom ist uneinheitliches Verhalten: Pflichtlogik läuft nur für vorhandene Feldobjekte, Fehlermeldungen verschwinden beim Entfernen eines Keys, und generische Helfer liefern breitere Typen als die UI tatsächlich zulässt. Der Mapped Type ist syntaktisch korrekt, modelliert aber die falsche Lebensdauer.

So macht man es richtig mit Trade-offs

Der interne Form-State wird vollständig normalisiert. Die optionale Telefonnummer besitzt während der Bearbeitung den leeren String als UI-Repräsentation. Erst toCommand entscheidet, ob sie im Zielobjekt fehlt:

import { useState, type FormEvent, type ReactElement } from "react";

type ProfileDraft = {
  displayName: string;
  phone?: string;
  marketingOptIn: boolean;
};

type FieldState<T> = {
  value: T;
  touched: boolean;
  error: string | null;
};

type FormState<T> = {
  [K in keyof T]-?: FieldState<NonNullable<T[K]>>;
};

type ProfileForm = FormState<ProfileDraft>;
type UpdateProfileCommand = ProfileDraft;

const initialForm = {
  displayName: { value: "", touched: false, error: null },
  phone: { value: "", touched: false, error: null },
  marketingOptIn: { value: false, touched: false, error: null }
} satisfies ProfileForm;

export function toCommand(form: ProfileForm): UpdateProfileCommand {
  const phone = form.phone.value.trim();
  return {
    displayName: form.displayName.value.trim(),
    marketingOptIn: form.marketingOptIn.value,
    ...(phone === "" ? {} : { phone })
  };
}

export function ProfileEditor(): ReactElement {
  const [form, setForm] = useState<ProfileForm>(initialForm);

  function submit(event: FormEvent): void {
    event.preventDefault();
    console.log(toCommand(form)); // API-Aufruf im echten Projekt
  }

  return <form onSubmit={submit}>
    <label>Telefon
      <input value={form.phone.value} onChange={event =>
        setForm(current => ({ ...current, phone: {
          ...current.phone, value: event.target.value, touched: true
        }}))
      } />
    </label>
    <button>Speichern</button>
  </form>;
}

Die NonNullable-Utility entfernt null und undefined aus dem Feldwert. Das ist keine universelle Regel: Ein Drei-Zustands-Feld kann null absichtlich benötigen. Dann entfernst du nur -? oder definierst eine feldspezifische Normalisierung.

Der Trade-off ist Kopplung an gleichnamige flache Keys. Verschachtelte Objekte, Arrays, Datei-Uploads oder abhängige Felder brauchen meist ein eigenes Formmodell. Eine explizit geschriebene ProfileForm-Schnittstelle ist dann oft verständlicher. Schema-basierte Formularbibliotheken sind eine weitere Alternative, besonders wenn Runtime-Validierung und Fehlermeldungen aus derselben Definition entstehen sollen.

Fallstricke am Rand

  • NonNullable entfernt auch fachlich relevantes null; verwende es nicht mechanisch.
  • Ein leerer String ist nur dann eine gute UI-Repräsentation, wenn er eindeutig „nicht angegeben“ bedeutet.
  • satisfies prüft die Initialstruktur, erzeugt aber zur Laufzeit keine Formularfelder.

Selbst ausprobieren

Kopiere beide Typvarianten in den TypeScript Playground mit Version 6.0 und aktiviere strict sowie exactOptionalPropertyTypes. Entferne phone aus initialForm. Erwartung: Die korrigierte Variante meldet den fehlenden Key, die naive erlaubt ihn. Entferne danach NonNullable und beobachte im Editor den breiteren Typ von form.phone.value.

Prüfstand: Die Submit-Abbildung wurde mit leerer, ausgefüllter und whitespace-only Telefonnummer unter Node getestet. HTML-Struktur, Diagrammanzahl und Codeklammern wurden geprüft. Ein TypeScript-Compile- oder React-Integrationstest war lokal nicht verfügbar und wird nicht behauptet.

Verwandte Themen

exactOptionalPropertyTypes trennt fehlende Keys von explizitem undefined. Discriminated Unions modellieren mehrstufige Felder ohne Boolesche Kombinationen. Runtime-Schemas verbinden Eingabeprüfung und Fehlermeldungen. Form Commands entkoppeln Bearbeitungszustand vom API-Payload.
