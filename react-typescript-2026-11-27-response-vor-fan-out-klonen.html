Eine Response muss vor dem Fan-out geklont werden

Ein Fetch-Body ist kein wiederverwendbarer Wert. Sobald mehrere Verbraucher ihn brauchen, wird seine Besitzfrage zur Architekturentscheidung.

Datenzugriff & Caching · TypeScript 6.0 + Fetch/Cache API · Tief · ~8 min

Die Offline-Version funktioniert im Test, scheitert aber nach dem nächsten Telemetrie-Feature. Der Service Worker liest aus jeder JSON-Antwort eine Schema-Version, legt die Antwort anschließend in den Cache und gibt sie an die React-App weiter. Plötzlich wirft response.clone() einen TypeError. Netzwerkstatus und Payload sind korrekt; verbraucht wurde lediglich der falsche Besitzanspruch.

TL;DR

Der Body einer Response ist ein Stream und grundsätzlich nur einmal konsumierbar. json(), text(), die Cache API und die Seite konkurrieren deshalb um dieselben Bytes. Wenn eine Antwort mehrere Verbraucher hat, klonst du sie unmittelbar am Fan-out – vor dem ersten Lesen. Jeder Zweig erhält genau eine Response. Das macht den Datenfluss sichtbar, verhindert zeitabhängige Fehler und zwingt dich, Speicher- und Lebenszeitkosten bewusst zu behandeln.

Prerequisites

Du solltest Service Worker, Promises und die Fetch API kennen. MDN erklärt die einmalige Nutzung von Response-Bodies, die Bedeutung von bodyUsed und das Verhalten von Cache.put(). Das Beispiel bezieht sich auf TypeScript 6.0 mit lib: ["ES2024", "WebWorker"].

Der Aha-Effekt

Eine Response sieht wie ein gewöhnliches Objekt aus, trägt aber eine lineare Ressource: ihren Body. TypeScript bildet diesen Zustandswechsel nicht im Typ ab. Vor und nach await response.json() lautet der statische Typ weiterhin Response; zur Laufzeit wechselt bodyUsed jedoch von false auf true.

Die Designentscheidung: Klone nicht als Reparatur vor dem zweiten Lesen. Klone an der Stelle, an der ein Besitzer zu mehreren Verbrauchern wird.

So macht man es falsch

Der folgende Service Worker erweitert eine bestehende Network-first-Strategie um eine Prüfung. Die Reihenfolge wirkt lokal: erst inspizieren, dann cachen. Genau dadurch ist der Body bereits gestört, bevor der zweite Zweig entsteht.

// sw.ts – fehlerhafte, aber realistische Variante
declare const self: ServiceWorkerGlobalScope;
export {};

async function inspectVersion(response: Response): Promise<void> {
  const data: unknown = await response.json();
  console.debug("Schema empfangen", data);
}

async function load(request: Request): Promise<Response> {
  const network = await fetch(request);
  await inspectVersion(network);       // Body wird konsumiert

  const cacheCopy = network.clone();   // TypeError: Body schon benutzt
  const cache = await caches.open("api-v3");
  await cache.put(request, cacheCopy);
  return network;
}

self.addEventListener("fetch", (event) => {
  if (event.request.method === "GET") {
    event.respondWith(load(event.request));
  }
});

Warum ist das falsch?

json() liest den Stream vollständig. Laut MDN wirft clone() nach der Benutzung des Bodys. Selbst ohne explizite Inspektion bleibt das Problem: Cache.put() konsumiert die übergebene Antwort, während der Browser den zurückgegebenen Body ebenfalls lesen muss. Das Symptom hängt daher davon ab, welcher Verbraucher zuerst zugreift – nicht von der fachlichen Gültigkeit der Antwort.

Ein Check von bodyUsed heilt die Architektur nicht. Er entdeckt nur, dass der Besitzvertrag bereits verletzt wurde. Wer dann still auf Caching oder Auslieferung verzichtet, verwandelt einen deterministischen Fehler in inkonsistentes Offline-Verhalten.

So macht man es richtig mit Trade-offs

Erzeuge alle Zweige direkt nach fetch(). Das Original gehört der Seite, ein Klon dem Cache und ein weiterer der Inspektion. event.waitUntil() hält den Service Worker für die Hintergrundarbeit am Leben, ohne die Auslieferung unnötig darauf warten zu lassen.

// sw.ts – vollständiger Ausschnitt, TypeScript 6.0 / WebWorker-Lib
declare const self: ServiceWorkerGlobalScope;
export {};

async function inspectVersion(response: Response): Promise<void> {
  const data: unknown = await response.json();
  console.debug("Schema empfangen", data);
}

async function load(
  request: Request,
  event: FetchEvent,
): Promise<Response> {
  const network = await fetch(request);
  if (!network.ok) return network;

  // Fan-out: alle Besitzverhältnisse entstehen vor dem ersten Lesen.
  const forCache = network.clone();
  const forInspection = network.clone();

  const background = Promise.all([
    caches.open("api-v3").then((cache) => cache.put(request, forCache)),
    inspectVersion(forInspection),
  ]).then(() => undefined);

  event.waitUntil(background);
  return network;
}

self.addEventListener("fetch", (event) => {
  if (event.request.method === "GET") {
    event.respondWith(load(event.request, event));
  }
});

Der Preis ist real: clone() teilt den Stream intern auf. Wenn Zweige unterschiedlich schnell lesen, können Daten gepuffert werden; MDN warnt deshalb besonders bei großen Bodies vor ungebremstem Speicherbedarf. Eine Alternative ist, genau einmal in einen ArrayBuffer zu lesen und daraus mehrere Responses zu bauen. Das macht die Kosten explizit, puffert aber immer den gesamten Body und muss Status sowie Header korrekt kopieren. Wenn die Inspektion keinen Produktwert hat, ist Weglassen die billigste Alternative.

Textliche Erklärung: Direkt nach dem Netzwerkzugriff wird die Response in drei Besitzpfade aufgeteilt. Jeder Pfad konsumiert genau einen Body; nachträgliches Klonen ist nicht nötig und nach dem ersten Lesen nicht mehr möglich.

Fallstricke am Rand

  • clone() muss vor jedem Aufruf von json(), text(), blob() oder arrayBuffer() erfolgen.
  • Cache nur Requests und Statuscodes, für die deine Strategie definiert ist; ein erfolgreicher Fetch bedeutet nicht automatisch fachlich cachebare Daten.
  • Fange Fehler der Hintergrundarbeit gezielt ab, wenn ein abgelehntes waitUntil() nicht als fehlgeschlagener Worker-Vorgang gelten soll.

Selbst ausprobieren

Erzeuge in fünf Minuten in der Browser-Konsole new Response('{"version":3}'). Lies zunächst bodyUsed, rufe json() auf und prüfe den Wert erneut. Versuche danach clone(): Erwartet wird ein TypeError. Wiederhole den Versuch, klone diesmal zuerst und lies Original sowie Klon getrennt. Beide Auswertungen sollen denselben Inhalt liefern.

Verwandte Themen

  • ReadableStream-Backpressure: Sie erklärt, warum langsame Klon-Zweige Speicher binden können.
  • Cache-Strategien: Network-first und stale-while-revalidate setzen unterschiedliche Fehler- und Frischeverträge.
  • Runtime-Validierung: Geparstes JSON bleibt an der Systemgrenze zunächst unknown.
  • Service-Worker-Lebenszeit: waitUntil() koppelt Hintergrundarbeit an das auslösende Event.
