flushSync ist eine Integrationsgrenze, kein Update-Modus

Synchronisiere React-eigene DOM-Arbeit mit dem Commit – und erzwinge synchrone Commits nur für fremde Taktgeber.

React-Render-Verhalten · React 19.3 + TypeScript 6.0 · Tief · ~8 min

Eine Chatliste hängt eine Nachricht an und scrollt direkt danach zum neuen Listenelement. Sporadisch findet querySelector nichts: setMessages hat ein Rendern angefordert, doch der Event-Handler läuft noch gegen den alten DOM. Der schnelle Fix umschließt jedes Update mit flushSync. Das Symptom verschwindet – und eine lokale Timing-Frage wird zum globalen Scheduling-Eingriff.

TL;DR

Wenn React den Ablauf kontrolliert, verschiebe DOM-Messung oder Scrollen in useLayoutEffect. Dieser Hook läuft nach dem Commit und vor dem nächsten Paint. Nutze flushSync nur, wenn eine synchrone Browser- oder Drittanbieter-API den aktualisierten DOM noch vor Rückkehr ihres Callbacks beobachten muss. flushSync darf zusätzliche Arbeit synchron ausführen, Suspense-Fallbacks erneut zeigen und die Performance beeinträchtigen; es ist kein Standardersatz für sauberes Commit-Timing.

Prerequisites

Du solltest State-Snapshots, Effects und DOM-Refs kennen. React beschreibt State als Snapshot, dokumentiert useLayoutEffect für Arbeit nach dem Commit und flushSync als seltenen Ausweg. Der Artikel bezieht sich auf die laut Versionsseite aktuelle React-Version 19.3 und TypeScript 6.0.

Der Aha-Effekt

Ein State-Setter mutiert weder die State-Variable des laufenden Renderings noch garantiert er einen DOM-Commit vor der nächsten JavaScript-Zeile. React darf Updates sammeln und den Bildschirm anschließend an den neuen Snapshot angleichen. Die richtige Abstraktion für React-eigene DOM-Arbeit ist deshalb nicht „schneller committen“, sondern „nach dem Commit ausführen“.

Entscheidende Frage: Wer besitzt die Deadline – Reacts Commit-Zyklus oder eine fremde synchrone API?

So macht man es falsch

Dieser Code macht aus jedem Hinzufügen einen erzwungenen synchronen Commit, nur damit die nächste Zeile den neuen Knoten findet:

import { useState } from "react";
import { flushSync } from "react-dom";

type Message = { id: string; text: string };

export function Chat() {
  const [messages, setMessages] = useState<Message[]>([]);

  function appendAndScroll(text: string) {
    const next = { id: crypto.randomUUID(), text };

    flushSync(() => {
      setMessages(current => [...current, next]);
    });

    document
      .querySelector(`[data-message-id="${CSS.escape(next.id)}"]`)
      ?.scrollIntoView({ block: "nearest" });
  }

  // Ausschnitt: Rendering der Liste
}

Warum ist das falsch?

Der Code funktioniert, erweitert aber den Vertrag unnötig: Statt „scrolle nach dem Commit“ verlangt er „committe diese Aktualisierung jetzt synchron“. React weist darauf hin, dass flushSync auch ausstehende Updates außerhalb des Callbacks flushen, Effects ausführen und bei suspendierender Arbeit Fallbacks erneut sichtbar machen kann.

Beobachtbar wird das als eng gekoppelte Handlerlogik, unnötige synchrone Rendergrenzen und schwerer erklärbares Verhalten benachbarter Komponenten. Eine pauschale Performanceverbesserung oder -verschlechterung lässt sich ohne Messung nicht beziffern; dokumentiert ist jedoch, dass häufige synchrone Flushes Reacts Scheduling-Spielraum einschränken.

So macht man es richtig

Die Nachricht bleibt deklarativer Zustand; die einmalig benötigte Ziel-ID liegt als imperativer Marker in einem Ref. useLayoutEffect beobachtet den Commit und greift über einen zweiten, begrenzten Ref auf genau diese Liste zu.

import { useLayoutEffect, useRef, useState } from "react";

type Message = { id: string; text: string };

export function Chat() {
  const [messages, setMessages] = useState<Message[]>([]);
  const listRef = useRef<HTMLUListElement>(null);
  const pendingScrollId = useRef<string | null>(null);

  function appendMessage(text: string) {
    const next = { id: crypto.randomUUID(), text };
    pendingScrollId.current = next.id;
    setMessages(current => [...current, next]);
  }

  useLayoutEffect(() => {
    const id = pendingScrollId.current;
    if (id === null) return;
    pendingScrollId.current = null;
    listRef.current
      ?.querySelector(
        `[data-message-id="${CSS.escape(id)}"]`,
      )
      ?.scrollIntoView({ block: "nearest" });
  }, [messages]);

  return <ul ref={listRef}>{/* Nachrichten */}</ul>;
}

useLayoutEffect blockiert den Paint und sollte deshalb nur eingesetzt werden, wenn die Zwischenposition nicht sichtbar werden darf. Reicht ein Scrollen nach dem Paint, ist useEffect die günstigere Alternative. flushSync bleibt für echte Integrationsgrenzen: Im synchronen beforeprint-Callback muss etwa ein Drucklayout im DOM stehen, bevor der Browser den Druckdialog öffnet. Dort kann ein eng begrenztes flushSync(() => setIsPrinting(true)) gerechtfertigt sein.

Fallstricke am Rand

  • flushSync darf nicht während Rendern, useEffect oder useLayoutEffect aufgerufen werden.
  • Ein Layout Effect läuft nur im Client; serverseitig existiert kein Layout zum Messen.
  • Globale DOM-Abfragen koppeln Komponenten stärker als ein lokaler Ref.

Selbst ausprobieren

Baue in zehn Minuten eine Liste mit „Hinzufügen“-Button. Frage unmittelbar nach setItems im Handler das neue Element ab und protokolliere das Ergebnis. Verschiebe dieselbe Abfrage anschließend in useLayoutEffect. Erwartung: Der Handler arbeitet noch mit dem alten DOM; der Layout Effect findet den Knoten nach dem Commit. Miss bei Interesse beide Varianten im React Profiler, statt eine Geschwindigkeitsaussage abzuleiten.

Verwandte Themen

  • State-Snapshots: Handler lesen Werte ihres Renderings, nicht den angeforderten Folgezustand.
  • Refs: Sie begrenzen imperative DOM-Fähigkeiten auf den tatsächlich besessenen Knoten.
  • Suspense: Ein erzwungener Flush kann eine ausstehende Boundary wieder in den Fallback versetzen.
  • Performance-Messung: Commit-Dauer und Interaktionslatenz gehören in den Profiler, nicht in Vermutungen.
