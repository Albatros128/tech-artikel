Ein langlebiger Factory-HttpClient kann DNS-Wechsel trotzdem verpassen

Kommunikation · .NET 10 / IHttpClientFactory / SocketsHttpHandler · Fortgeschritten · ~7 min

TL;DR

IHttpClientFactory löst DNS-Wechsel nur dann zuverlässig, wenn neu erzeugte Clients auch tatsächlich neue beziehungsweise rotierte Handler nutzen können. Hält ein Singleton denselben Factory-Client dauerhaft fest, bleibt dieser an seinem ursprünglichen Handler gebunden.

Prerequisites

  • Microsoft Learn: IHttpClientFactory
  • Microsoft Learn: Troubleshooting
  • Microsoft Learn: PooledConnectionLifetime

Der Aha-Effekt

Die Factory verwaltet vor allem HttpMessageHandler-Instanzen. Ein neuer CreateClient()-Aufruf kann nach Ablauf der Handler-Lifetime einen anderen Handler erhalten. Ein bereits existierender HttpClient wechselt seinen Handler aber nicht nachträglich.

Aha: Handler-Rotation hilft nur neuen Clients. Ein festgehaltener Client bleibt an seiner alten Handler-Instanz hängen.

Im Projektkontext

Bei ASP.NET Core in Docker oder Kubernetes können sich Ziel-IP-Adressen ändern, während DNS-Namen stabil bleiben. Genau dort wird die Lebensdauer von Handlern und Connections relevant.

So macht man es falsch

builder.Services.AddHttpClient<InventoryClient>();
builder.Services.AddSingleton<InventoryCache>();

public sealed class InventoryCache
{
    private readonly InventoryClient _client;

    public InventoryCache(InventoryClient client)
        => _client = client;
}

Warum ist das falsch?

Wird der Typed Client einmal in einem Singleton erzeugt, lebt auch dessen interner HttpClient entsprechend lange. Die Factory kann zwar für zukünftige Clients neue Handler bereitstellen, aber der Singleton fragt keinen neuen Client mehr an. Bei einem DNS-Wechsel kann das zu veralteten Verbindungen führen.

So macht man es richtig

public sealed class InventoryCache
{
    private readonly IHttpClientFactory _factory;

    public InventoryCache(IHttpClientFactory factory)
        => _factory = factory;

    public async Task<string> LoadAsync(CancellationToken ct)
    {
        using var client = _factory.CreateClient("Inventory");
        return await client.GetStringAsync("/api/inventory", ct);
    }
}

Alternativ kann ein bewusst langlebiger Client mit SocketsHttpHandler.PooledConnectionLifetime verwendet werden. Dann wird die DNS-Aktualisierung stärker über das Connection-Recycling gesteuert.

Diagramm

Fallstricke am Rand

  • Typed Clients nicht indirekt in Singletons festhalten.
  • PooledConnectionLifetime löst ein anderes Lifetime-Problem als Handler-Rotation.
  • Retry behebt stale DNS nicht, sondern reagiert nur auf Fehler.

Selbst ausprobieren

Erzeuge einen Named Client mit kurzer Handler-Lifetime. Halte einen Client dauerhaft fest und rufe parallel regelmäßig CreateClient() auf. Beobachte, dass nur neu erzeugte Clients von der Handler-Rotation profitieren.

Verwandte Themen

  • DelegatingHandler-Lifetime: wichtig für DI-Scopes.
  • HTTP/2: beeinflusst Connection-Pooling.
  • Kubernetes Service Discovery: DNS-Namen bleiben stabil, Endpoints nicht zwingend.
  • Polly: Resilience ist kein Ersatz für korrektes Connection-Lifetime-Management.
