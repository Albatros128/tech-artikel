Nicht jedes Argument darf den Generic-Typ mitbestimmen

NoInfer<T> macht aus einem Parameter eine Prüfung, statt ihn heimlich zur zweiten Quelle der Wahrheit zu machen.

TypeScript-Typsystem · TypeScript 7.0.2, NoInfer seit 5.4 · Tief · ~8 min

Ein Workflow kennt die Zustände draft, review und published. Die Konfigurationsfunktion soll daraus eine präzise Union ableiten und sicherstellen, dass der Initialzustand dazugehört. Trotzdem akzeptiert TypeScript plötzlich archived. Nicht die Union ist falsch modelliert – die Inferenz hat zu viele Stimmen bekommen.

TL;DR

Wenn ein generischer Typ aus einem Argument entstehen und ein anderes Argument nur dagegen geprüft werden soll, markiere das zweite mit NoInfer<T>. Dadurch sammelt TypeScript dort keine Inferenzkandidaten mehr. Der Parameter bleibt vom Typ T, beeinflusst aber nicht, was T wird. Das Muster eignet sich für Defaults, Fallbacks und Initialwerte; es ersetzt weder Runtime-Validierung noch gutes API-Design.

Prerequisites

Du solltest Generics, Literal-Unions und Inferenz kennen. Die offizielle Referenz dokumentiert NoInfer<Type> als Utility Type seit 5.4. Der Versionsbezug dieses Artikels ist TypeScript 7.0.2; die beschriebene Semantik ist seit der Einführung stabil.

Der Aha-Effekt

Ein Parameter vom Typ T erfüllt in einer generischen Signatur oft zwei Aufgaben: Er liefert Kandidaten für T und wird anschließend auf Kompatibilität mit T geprüft. Diese Rollen sehen syntaktisch gleich aus, sind konzeptionell aber verschieden. Bei einem Default soll die Optionsliste bestimmen, was erlaubt ist. Der Default soll lediglich beweisen, dass er dazugehört.

NoInfer macht einen Parameter nicht strenger. Es entscheidet, wer den Vertrag formuliert und wer ihn nur erfüllen muss.

So macht man es falsch

Die Signatur wirkt zunächst korrekt. Beide Parameter verwenden dieselbe Union S. Genau dadurch darf jedoch auch initial Kandidaten für S liefern.

// workflow.ts – problematische Variante
type Workflow<S extends string> = {
  states: readonly S[];
  initial: S;
};

export function defineWorkflow<const S extends string>(
  states: readonly S[],
  initial: S,
): Workflow<S> {
  return { states, initial };
}

const editorial = defineWorkflow(
  ["draft", "review", "published"],
  "archived", // kann S erweitern, statt abgelehnt zu werden
);

// S kann als "draft" | "review" | "published" | "archived"
// inferiert werden.

Warum ist das falsch?

TypeScript löst Generics strukturell. Es sucht passende Kandidaten an allen Inferenzpositionen und wählt einen Typ, der den Aufruf ermöglicht. Aus der Liste kommen drei Literale, aus dem zweiten Argument ein viertes. Eine größere Union erfüllt beide Parameter – also besteht der Aufruf, obwohl er die fachliche Absicht verletzt.

Das beobachtbare Symptom ist tückisch: Im Editor erscheint kein Fehler, und der Rückgabetyp behauptet anschließend, archived sei ein erlaubter Zustand. Die Implementierung hat zur Laufzeit nichts geprüft; Typen werden beim Emit entfernt. Die Release Notes zu TypeScript 5.4 beschreiben genau dieses Problem als konkurrierende Inferenzquellen.

So macht man es richtig – mit Trade-offs

Die Zustandsliste ist die Quelle. NoInfer<S> verhindert nur am Initialwert die Kandidatensuche. Danach wird der Wert normal gegen die bereits bestimmte Union geprüft.

// workflow.ts – TypeScript 5.4+
type Workflow<S extends string> = {
  states: readonly S[];
  initial: S;
};

export function defineWorkflow<const S extends string>(
  states: readonly S[],
  initial: NoInfer<S>,
): Workflow<S> {
  if (!states.includes(initial)) {
    throw new Error(`Unbekannter Initialzustand: ${initial}`);
  }
  return { states, initial };
}

const editorial = defineWorkflow(
  ["draft", "review", "published"],
  "draft", // OK
);

defineWorkflow(
  ["draft", "review", "published"],
  "archived", // Fehler: nicht Teil der inferierten Union
);

Der Runtime-Guard wirkt im vollständig typisierten Aufruf redundant, schützt aber JavaScript-Consumer, unsichere Casts und dynamische Grenzen. Der Trade-off von NoInfer: Die API legt bewusst eine Inferenzrichtung fest. Wenn beide Argumente gleichberechtigt den Typ bilden sollen, wäre es falsch. Als Alternative kann eine curried API zuerst die Zustände festlegen und in einem zweiten Aufruf den Default annehmen. Das ist eindeutig, kostet aber einen zusätzlichen Aufruf und verändert die Ergonomie.

// Alternative: Inferenz zeitlich trennen
const workflowFrom = <const S extends string>(states: readonly S[]) =>
  (initial: S): Workflow<S> => ({ states, initial });

const editorial = workflowFrom(["draft", "review", "published"])(
  "draft",
);

Fallstricke am Rand

  • NoInfer konserviert keine Literale von selbst. Für API-Eingaben helfen const-Typparameter oder as const.
  • Ist die Liste bereits nur als string[] typisiert, bleibt S breit. Dann kann der Compiler unbekannte Werte nicht unterscheiden.
  • Ersetze damit keine Runtime-Prüfung an Netzwerk-, Storage- oder JavaScript-Grenzen.
  • Verteile NoInfer nicht reflexartig. Dokumentiere, welcher Parameter die fachliche Quelle der Wahrheit ist.

Selbst ausprobieren

Plane zehn Minuten ein. Kopiere beide Varianten in den TypeScript Playground und aktiviere strict. Fahre über editorial und vergleiche die inferierte Union. Setze anschließend states in eine Variable vom Typ string[]. Erwartung: NoInfer weist archived bei der Literal-Liste zurück, kann bei der verbreiterten string[] aber keine verlorene Information zurückholen. Ergänze zuletzt einen Wert aus JSON.parse und beobachte, warum der Runtime-Guard weiterhin eine eigene Aufgabe hat.

Verwandte Themen

  • Const-Typparameter: Sie bewahren Literalinformationen an der Inferenzquelle.
  • satisfies: Es prüft einen Vertrag, ohne den präzisen Ausdruckstyp zu ersetzen.
  • Runtime-Validierung: Sie übernimmt dort, wo Compile-Time-Typen keine Herkunft garantieren.
  • Builder- und Curry-APIs: Getrennte Aufrufphasen können Inferenzreihenfolgen explizit modellieren.
