Ein Result-Typ typisiert keine Exceptions

Erwartete Fehler werden erst durch Klassifizierung zu Daten – nicht durch ein generisches E.

TypeScript-API-Modellierung · TypeScript 6.0 · Tief · ~8 min

Ein Checkout liefert Result<Order, PaymentError>. Im Fehlerzweig zeigt die UI deshalb „Karte abgelehnt“ an. Wochen später wirft der JSON-Parser einen SyntaxError; der Helper legt ihn trotzdem als PaymentError in das Result. Der Compiler ist zufrieden, doch die Fehleranzeige liest Felder, die nie existierten.

TL;DR

Result<T, E> beschreibt einen kontrollierten Rückgabekanal. Es beweist nicht, dass eine aufgerufene Funktion nur E werfen oder ein Promise nur mit E ablehnen kann. Behandle den Wert im catch als unknown, klassifiziere ausschließlich bekannte Fehler und wirf alles andere erneut. So bleibt E eine belastbare Domänenzusage statt eines Sammelbegriffs für beliebige Defekte.

Prerequisites

Vorausgesetzt sind discriminated unions, async/await und Narrowing. TypeScript dokumentiert useUnknownInCatchVariables; unter strict ist die Option aktiv. Der Versionsbezug ist TypeScript 6.0.

Der Aha-Effekt

TypeScript besitzt keine geprüften Exceptions. Der Rückgabetyp Promise<T> beschreibt den Fulfillment-Wert, aber keinen typisierten Rejection-Kanal. JavaScript kann außerdem jeden Wert werfen oder an Promise.reject übergeben. Deshalb ist E nicht das, was die Operation „werfen könnte“, sondern nur das, was deine Grenze nach einer Laufzeitprüfung als erwarteten Fehler anerkennt.

Die Designfrage lautet: Welche Fehler gehören zum normalen Protokoll dieser Operation – und welche sollen als unbekannte Störung sichtbar bleiben?

So macht man es falsch

Der generische Helper sieht wiederverwendbar aus, kann seine wichtigste Behauptung aber nicht prüfen:

type Result<T, E> =
  | { ok: true; value: T }
  | { ok: false; error: E };

async function attempt<T, E>(
  operation: () => Promise<T>
): Promise<Result<T, E>> {
  try {
    return { ok: true, value: await operation() };
  } catch (cause) {
    return { ok: false, error: cause as E };
  }
}

// Behauptet PaymentError, obwohl E nirgends geprüft wird.
const result = await attempt<Order, PaymentError>(submitOrder);

Warum ist das falsch?

Der Typparameter E erscheint nur in der Ausgabe. Der Aufrufer darf ihn daher frei wählen; die Assertion verbindet den unbekannten Laufzeitwert ohne Beleg mit diesem Wunschtyp. Ein Netzwerkfehler, ein Programmierfehler oder sogar throw "offline" wird zum angeblichen PaymentError.

Das beobachtbare Symptom liegt später: Ein exhaustiver switch über Fehlercodes scheint sicher, erhält aber ein Objekt ohne code. Zugleich verschwinden unerwartete Defekte im normalen UI-Pfad und werden schwerer zu erkennen. Das Problem ist keine fehlende Union-Variante, sondern eine unehrliche Grenze.

So macht man es richtig

Die Grenze erhält einen expliziten Klassifizierer. Er darf einen bekannten Domänenfehler liefern; undefined bedeutet „nicht erkannt“. Unbekannte Werte werden erneut geworfen und bleiben damit im Exception-Kanal.

type Result<T, E> =
  | { ok: true; value: T }
  | { ok: false; error: E };

async function attemptKnown<T, E>(
  operation: () => Promise<T>,
  classify: (cause: unknown) => E | undefined
): Promise<Result<T, E>> {
  try {
    return { ok: true, value: await operation() };
  } catch (cause: unknown) {
    const error = classify(cause);
    if (error === undefined) throw cause;
    return { ok: false, error };
  }
}

type PaymentError =
  | { code: "declined"; message: string }
  | { code: "expired"; message: string };

function asPaymentError(cause: unknown): PaymentError | undefined {
  if (!(cause instanceof PaymentApiError)) return undefined;
  if (cause.code !== "declined" && cause.code !== "expired") {
    return undefined;
  }
  return { code: cause.code, message: cause.message };
}

const result = await attemptKnown(submitOrder, asPaymentError);

Der Trade-off ist zusätzliche Laufzeitlogik. Dafür liegt die Übersetzung direkt an der Systemgrenze und ist separat testbar. Eine Alternative ist, dass der API-Client erwartete HTTP-Antworten selbst als Result zurückgibt und nur Transport- oder Programmfehler wirft. Bei kleinen lokalen Funktionen kann eine gewöhnliche Exception mit engem try/catch einfacher sein; ein Result lohnt sich erst, wenn erwartete Fehler Teil der Aufruferentscheidung sind.

Fallstricke am Rand

  • instanceof funktioniert über Realm- oder Paketgrenzen nicht immer zuverlässig; ein validiertes strukturelles Protokoll kann passender sein.
  • Ein Klassifizierer darf keine vertraulichen Rohantworten ungefiltert in UI-Fehler kopieren.
  • Ein catch um zu viel Code kann auch Fehler aus Rendering, Logging oder Mapping versehentlich klassifizieren.

Selbst ausprobieren

Baue in zehn Minuten beide Helper nach. Lass die Operation nacheinander einen bekannten PaymentApiError, einen SyntaxError und den String "offline" werfen. Erwartung: attempt meldet dreimal einen scheinbaren PaymentError; attemptKnown erzeugt nur beim ersten Wert ein Err und wirft die beiden unbekannten Werte erneut.

Verwandte Themen

  • Runtime-Validierung: Auch Fehlerpayloads aus HTTP-Antworten beginnen als unbekannte Daten.
  • Error Boundaries: In React gehören unerwartete Renderfehler in eine Ausfallzone, nicht in Domänenstate.
  • Exhaustive Unions: Sie sind nur so sicher wie die Grenze, die ihre Varianten erzeugt.
  • Observability: Erneut geworfene Defekte benötigen zentrale Erfassung mit Ursache und Kontext.
