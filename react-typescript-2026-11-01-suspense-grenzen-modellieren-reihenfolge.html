Suspense-Grenzen modellieren eine Reveal-Reihenfolge

Die Grenze gehört dorthin, wo Produktdesign entscheidet, welche Inhalte gemeinsam erscheinen sollen.

01.11.2026 · React-Suspense · React 19.3 · Tief · ~8 min

Die Produktseite besitzt eine Zusammenfassung und einen Block mit Empfehlungen. Beide Module werden separat geladen. Im lokalen Netz wirkt alles korrekt; bei gedrosselter Verbindung bleibt jedoch die gesamte Inhaltsfläche im großen Skeleton, obwohl die Zusammenfassung längst verfügbar ist. Der langsamste Teil bestimmt unbeabsichtigt, wann die ganze Seite sichtbar wird.

TL;DR

Eine Suspense-Grenze ist eine Koordinationsentscheidung: Alle suspendierenden Nachfahren unter derselben nächsten Grenze werden als gemeinsame Reveal-Einheit behandelt. Setze Grenzen deshalb nach der gewünschten Wahrnehmungsreihenfolge. Inhalte, die zusammen erscheinen sollen, teilen eine Grenze. Sekundäre Inhalte, die später nachrücken dürfen, erhalten eine verschachtelte Grenze. Mehr Grenzen bedeuten nicht automatisch bessere UX; sie erzeugen mehr Zwischenzustände.

Prerequisites

Du kennst Komponenten, dynamische Imports und Fallbacks. Die Beispiele beziehen sich auf React 19.3. React dokumentiert die Semantik von Suspense und das Code-Splitting mit lazy. lazy muss auf Modulebene deklariert werden und erwartet einen Default-Export.

Der Aha-Effekt

Die nächstgelegene übergeordnete Suspense-Grenze entscheidet nicht, welcher Request gestartet wird. Sie entscheidet, welcher Teil des Baums durch einen Fallback ersetzt wird und welche Inhalte gemeinsam sichtbar werden. Ob der suspendierende Nachfahr direkt unter der Grenze liegt oder mehrere Komponenten tief verschachtelt ist, ändert diese Koordination nicht.

Damit ist die Baumposition der Grenze eine sichtbare Produktentscheidung. Eine einzige große Grenze sagt: „Diese Fläche ist erst sinnvoll, wenn alles bereit ist.“ Eine innere Grenze sagt: „Der äußere Inhalt ist bereits nützlich; dieser Teil darf später folgen.“ Das ist der Kern – nicht die Anzahl der Spinner.

So macht man es falsch

Hier teilen zwei unabhängig nützliche Module eine einzige Grenze. Das langsamere Empfehlungs-Bundle hält dadurch auch die fertige Zusammenfassung hinter dem Seiten-Skeleton zurück:

import { lazy, Suspense } from "react";

const ProductSummary = lazy(() => import("./ProductSummary"));
const Recommendations = lazy(() => import("./Recommendations"));

export function ProductPage() {
  return (
    <main>
      <ProductNavigation />
      <Suspense fallback={<ProductPageSkeleton />}>
        <ProductSummary />
        <Recommendations />
      </Suspense>
    </main>
  );
}

function ProductNavigation() {
  return <nav aria-label="Produkt">Übersicht · Details</nav>;
}

function ProductPageSkeleton() {
  return <div aria-label="Produkt wird geladen">Produkt wird geladen …</div>;
}

Warum ist das falsch?

React behandelt den gesamten Baum innerhalb dieser Grenze als eine Reveal-Einheit. Suspendiert Recommendations, zeigt React den Fallback anstelle beider Module. Das beobachtbare Symptom ist kein falscher Datenzustand, sondern unnötig spät sichtbarer Primärinhalt. Die Ursache liegt nicht im Import selbst, sondern in der gewählten Koordinationsfläche.

Die umgekehrte Überkorrektur ist ebenso problematisch: eine Grenze um jede kleine Karte. Dann erscheinen zahlreiche Skeletons und Inhalte in wechselnder Reihenfolge. Das kann Layout und Aufmerksamkeit unruhiger machen. Ohne Messung lässt sich daraus keine Performanceverbesserung ableiten; geändert wird zunächst die wahrgenommene Reveal-Sequenz.

So macht man es richtig mit Trade-offs

Die Zusammenfassung ist Primärinhalt. Empfehlungen sind nützlich, aber nicht notwendig, um die Seite zu verstehen. Eine äußere Grenze schützt den Hauptbereich; eine innere Grenze erlaubt den zweiten Reveal-Schritt:

import { lazy, Suspense } from "react";

const ProductSummary = lazy(() => import("./ProductSummary"));
const Recommendations = lazy(() => import("./Recommendations"));

export function ProductPage() {
  return (
    <main>
      <ProductNavigation />
      <Suspense fallback={<SummarySkeleton />}>
        <ProductSummary />
        <Suspense fallback={<RecommendationsSkeleton />}>
          <Recommendations />
        </Suspense>
      </Suspense>
    </main>
  );
}

function ProductNavigation() {
  return <nav aria-label="Produkt">Übersicht · Details</nav>;
}

function SummarySkeleton() {
  return <div aria-label="Zusammenfassung wird geladen">Lade Übersicht …</div>;
}

function RecommendationsSkeleton() {
  return <section aria-label="Empfehlungen werden geladen">Lade Empfehlungen …</section>;
}

Zuerst erscheint der äußere Fallback. Sobald die Zusammenfassung bereit ist, wird sie zusammen mit dem inneren Empfehlungen-Fallback sichtbar. Danach ersetzt das Empfehlungsmodul nur seinen eigenen Platzhalter. Der Trade-off: Du musst zusätzliche Zwischenzustände gestalten und stabile Flächen reservieren, sonst springt das Layout.

Wenn beide Bereiche fachlich nur gemeinsam verständlich sind, bleibt die einzelne Grenze die bessere Variante. Für bereits sichtbare Inhalte, die bei einer Aktualisierung erneut suspendieren, sind startTransition oder useDeferredValue eine andere Entscheidung: Sie können verhindern, dass fertiger Inhalt sofort wieder durch einen Fallback verschwindet. Manuelle isLoading-Zustände bleiben eine Alternative, wenn die Datenquelle Suspense nicht unterstützt; sie verlagern die Koordination jedoch in Anwendungslogik.

Diagramm

Fallstricke am Rand

  • Suspense erkennt keine Datenabfragen, die erst in einem Effect oder Event-Handler starten.
  • Ein suspendierender Fallback aktiviert selbst die nächsthöhere Grenze; halte Fallbacks deshalb leichtgewichtig.
  • Deklariere lazy nicht innerhalb der Komponente, sonst kann der Komponententyp bei Renderings neu entstehen und State zurückgesetzt werden.

Selbst ausprobieren

Öffne in einem React-Projekt die DevTools, aktiviere langsames Netzwerk und verzögere den Import von Recommendations testweise im Entwicklungs-Bundler. Vergleiche zuerst die einzelne, danach die verschachtelte Grenze. Erwartung: In der ersten Variante bleibt die Zusammenfassung bis zum langsamsten Modul verborgen. In der zweiten wird sie sichtbar, während nur der Empfehlungsbereich seinen Fallback zeigt. Prüfe zusätzlich mit Tastatur und Screenreader, ob die Platzhalter verständliche, nicht ständig wiederholte Statusinformationen liefern.

Verwandte Themen

startTransition hält bereits sichtbare Navigation während nicht dringender Updates stabil. useDeferredValue lässt einen Teil der UI bewusst hinterherlaufen. Error Boundaries definieren Fehler- statt Ladeflächen. Streaming SSR nutzt Suspense-Grenzen zusätzlich als Einheiten für schrittweise ausgeliefertes HTML.
