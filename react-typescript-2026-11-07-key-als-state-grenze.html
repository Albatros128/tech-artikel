Ein key ist eine State-Grenze, kein Listen-Hack

Wenn die fachliche Identität wechselt, darf React den alten Komponenten-State nicht immer weitertragen.

07.11.2026 · React-State-Modellierung · React 19.3 · Tief · ~8 min

Du öffnest Kunde A in einem Seitendialog, änderst die Adresse und wechselst ohne Speichern zu Kunde B. Der Titel zeigt bereits B, im Formular steht noch der Entwurf von A. Ein Effect kopiert die neuen Props kurz darauf in den lokalen State und scheint das Problem zu lösen. Doch für einen Render existieren neue Identität und alter Entwurf gleichzeitig – und ein aufgeklappter Abschnitt im Kind bleibt trotzdem offen.

TL;DR

React ordnet State einer Position im UI-Baum zu. Bleiben Komponententyp und Position gleich, bleibt auch der lokale State erhalten, selbst wenn die Props eine andere Entität beschreiben. Wenn ein Entitätswechsel den gesamten lokalen Teilbaum neu beginnen soll, gib der inneren Komponente einen fachlichen key. Ein neuer Schlüssel erzeugt eine neue Identität und setzt State sowie DOM unterhalb dieser Grenze zurück. Das ist eine semantische Entscheidung, keine Optimierung.

Prerequisites

Du kennst useState, useEffect und kontrollierte Formulare. Die Beispiele beziehen sich auf React 19.3. Relevant sind Reacts Erklärungen zum Erhalten und Zurücksetzen von State sowie zu Fällen, in denen du keinen Effect brauchst.

Der Aha-Effekt

Props beantworten: „Welche Daten soll diese Instanz jetzt darstellen?“ Ein key beantwortet die grundlegendere Frage: „Ist das noch dieselbe Instanz?“ React dokumentiert, dass State an die Position im Render-Baum gebunden ist. Der Schlüssel wird Teil dieser Identität. Ändert er sich, wird der Teilbaum nicht aktualisiert, sondern neu aufgebaut.

Damit modellierst du eine fachliche Grenze: Ein Editor für Kunde A und ein Editor für Kunde B sind nicht zwei Zustände desselben Editors, sondern zwei verschiedene Arbeitskontexte. Der Reset umfasst automatisch jeden lokalen State darunter – auch Validierungsfehler, offene Akkordeons und nicht kontrollierte DOM-Eingaben.

So macht man es falsch

Die verbreitete Lösung spiegelt die neuen Props nachträglich in lokalen State:

import { useEffect, useState } from "react";

type Customer = { id: string; name: string; email: string };

export function CustomerEditor({ customer }: { customer: Customer }) {
  const [draft, setDraft] = useState(customer);

  useEffect(() => {
    setDraft(customer);
  }, [customer]);

  return (
    <form>
      <h2>{customer.name} bearbeiten</h2>
      <input
        value={draft.email}
        onChange={event =>
          setDraft({ ...draft, email: event.target.value })
        }
      />
      <AdvancedFields customerId={customer.id} />
    </form>
  );
}

Das ist kein unrealistischer Sonderfall: Ein Formular soll absichtliche Änderungen lokal halten, erhält aber beim Wechsel einen neuen Datensatz. Der Effect repariert nur den State, den er kennt.

Warum ist das falsch?

Effects laufen nach dem Commit. React beschreibt deshalb bei diesem Muster zunächst einen Render mit veraltetem State und anschließend einen weiteren Render durch setDraft. Sichtbares Flackern ist nicht garantiert, aber die Zwischenkombination existiert und Kindkomponenten können damit arbeiten. Außerdem bleiben unabhängige State-Zellen wie AdvancedFields erhalten.

Noch gefährlicher ist die unklare Semantik: Soll ein Hintergrund-Refresh denselben Entwurf überschreiben? Soll der Wechsel zu einer anderen Kundennummer alles verwerfen? Der Effect behandelt jede Änderung am Objekt gleich. Die eigentliche Designentscheidung – gleiche oder neue Arbeitsidentität – verschwindet in Synchronisierungslogik.

So macht man es richtig mit Trade-offs

Trenne die Auswahl vom zustandsbehafteten Editor. Der äußere Teil kennt die fachliche Identität und setzt dort die Grenze:

import { useState } from "react";

type Customer = { id: string; name: string; email: string };

export function CustomerPanel({ customer }: { customer: Customer }) {
  return <CustomerEditor key={customer.id} customer={customer} />;
}

function CustomerEditor({ customer }: { customer: Customer }) {
  const [draft, setDraft] = useState(() => ({ ...customer }));

  return (
    <form>
      <h2>{customer.name} bearbeiten</h2>
      <label>
        E-Mail
        <input
          value={draft.email}
          onChange={event =>
            setDraft({ ...draft, email: event.target.value })
          }
        />
      </label>
      <AdvancedFields customerId={customer.id} />
    </form>
  );
}

Beim Wechsel der ID entsteht ein neuer Editor; sein Initializer liest genau einmal den neuen Kunden. Der Trade-off ist vollständig: Fokus, Textauswahl, Undo-Historie und jeder lokale Kind-State gehen verloren. Genau deshalb darf der Schlüssel nicht beiläufig wechseln.

Sollen Entwürfe beim Zurückwechseln erhalten bleiben, speichere sie oberhalb der Grenze, etwa als Record<CustomerId, Draft>, oder in einem externen Store. Soll nur ein Teil zurückgesetzt werden, ist ein expliziter Reducer-Reset präziser. Und wenn Props nur berechenbare Anzeigeinformationen liefern, berechne sie im Render statt sie überhaupt in State zu kopieren.

Diagramm

Fallstricke am Rand

  • Ein zufälliger Schlüssel wie Math.random() remountet bei jedem Render und zerstört Eingaben.
  • Ein key ist für das Kind kein normales Prop; übergib die ID zusätzlich, wenn es sie benötigt.
  • Ein Reset löst keine Persistenzfrage. Ungespeicherte Änderungen brauchen gegebenenfalls eine Warnung.

Selbst ausprobieren

Baue in zehn Minuten zwei Kundenbuttons und den Editor aus dem Beispiel. Tippe einen Entwurf für A, öffne AdvancedFields und wechsle zu B. Ohne key bleiben beide lokalen Zustände erhalten. Ergänze key={customer.id}: Erwartung ist ein frischer B-Entwurf und ein zurückgesetztes Kind. Wechsle danach zurück zu A; der alte Entwurf ist ebenfalls weg. Hebe ihn anschließend nach oben, um die Alternative bewusst zu testen.

Prüfstand: Die Identitätsmechanik wurde mit einem kleinen Zustandsmodell unter Node geprüft; HTML-Struktur, Überschriftenfolge, Diagrammanzahl und Wortumfang wurden automatisiert kontrolliert. Ein React-DOM-Integrationstest und ein TSX-Compile-Test waren lokal nicht verfügbar und werden nicht behauptet.

Verwandte Themen

Controlled Components verschieben die Lebensdauer des Entwurfs zum Elternteil. Reducer-Resets erlauben selektive Übergänge statt eines kompletten Remounts. State Colocation entscheidet, welche Grenze den Zustand besitzen soll. Router-Keys können dieselbe Identitätsentscheidung an Parametern oder Ressourcen festmachen.
