Error Boundaries definieren Ausfallzonen

Die richtige Boundary sitzt dort, wo ein Fehler fachlich isoliert werden kann – nicht automatisch nur am Root und nicht um jedes kleine Element.

21.10.2026 · Frontend-Architektur · React 19.3 · Tief · ~8 min

Ein einzelnes Umsatzdiagramm erhält unerwartete Daten und wirft beim Rendern. Statt nur dieses Panel zu ersetzen, verschwindet das gesamte Dashboard: Navigation, Aktivitätsfeed und alle weiterhin nutzbaren Aktionen. Die Anwendung besitzt zwar eine Error Boundary – aber sie sitzt ausschließlich am Root.

Das ist kein fehlender Fehlerhandler. Es ist eine zu grob gewählte Ausfallzone.

TL;DR

Ein Renderfehler wandert im Komponentenbaum nach oben bis zur nächsten Error Boundary. Deren Position bestimmt deshalb, welcher Teil der Oberfläche durch einen Fallback ersetzt wird. Behalte eine Root-Boundary als letzte Sicherung und ergänze fachliche Boundaries um unabhängige Bereiche, die getrennt ausfallen und sinnvoll separat wiederholt werden können.

Prerequisites

Du solltest Reacts Render- und Commit-Modell, Klassenkomponenten auf Lesebene und die offizielle Referenz zu Error Boundaries kennen. Der Versionsbezug ist React 19.3.

Der Aha-Effekt

Eine Boundary ist weniger ein technischer try/catch-Ersatz als eine architektonische Grenze. React entfernt bei einem ungefangenen Renderfehler standardmäßig die betroffene UI. Eine Boundary fängt Fehler ihrer Nachkommen ab und rendert stattdessen ihren Fallback. Damit beantwortet ihre Position eine Produktfrage: Welche Funktionen dürfen gemeinsam verschwinden?

Das lässt sich nicht allein aus der Komponentengröße ableiten. Zwei kleine Widgets können fachlich voneinander unabhängig sein; mehrere große Komponenten können gemeinsam eine unteilbare Checkout-Strecke bilden. Die sinnvolle Granularität folgt der Wiederherstellbarkeit und dem Nutzen des verbleibenden UI.

So macht man es falsch

Eine Root-Boundary ist wichtig, aber als einzige Grenze macht sie jeden Renderfehler zu einem Totalausfall:

Wirft RevenuePanel beim Rendern, ist die Root-Boundary der nächste Fänger. Ihr Fallback ersetzt folglich auch Navigation und Aktivitätsfeed. Ein try/catch direkt um <RevenuePanel /> hilft nicht: React rendert das Kind später; Renderfehler laufen durch den Komponentenbaum, wie auch die offizielle Lint-Dokumentation erklärt.

Warum ist das falsch?

Die Mechanik ist hier wichtiger als die Syntax. JSX erzeugt zunächst nur eine Beschreibung. Der Funktionsaufruf des Kindes findet nicht innerhalb des lexikalischen try-Blocks des Parents statt. React übernimmt die Ausführung und propagiert den Fehler zur nächsten Boundary. Diese ist damit die Einheit, die atomar zwischen normaler UI und Fallback wechselt.

Eine globale Boundary schützt vor einer leeren Seite, erhält aber keine Teilfunktion. Umgekehrt erzeugt eine Boundary um jeden Avatar oder Button unruhige Mikro-Fallbacks, mehr Zustände und unklare Wiederholungslogik. React empfiehlt ausdrücklich Grenzen an Stellen, an denen eine Fehlermeldung sinnvoll angezeigt werden kann – nicht pauschal um jede Komponente.

So macht man es richtig mit Trade-offs

Behalte die Root-Boundary für unbekannte Fehler. Ergänze darunter Grenzen für fachlich unabhängige Panels. Eine wiederverwendbare Boundary kann Fehler protokollieren und über einen wechselnden resetKey einen neuen Versuch zulassen:

Der Preis sind zusätzliche Fallback-Zustände, Logging-Kontext und eine bewusste Retry-Semantik. Ein Retry ohne geänderte Eingabe wiederholt nur denselben deterministischen Fehler. Alternativ kann ein Router Error Boundaries pro Route bereitstellen; für stark verschachtelte Anwendungen reduziert das eigenen Infrastrukturcode, bindet die Fehlergrenzen aber an die Routing-Struktur.

Diagramm

flowchart TD
  A[Root-Boundary] --> B[Navigation]
  A --> C[Dashboard]
  C --> D[Umsatz-Boundary]
  C --> E[Aktivitäts-Boundary]
  D --> F[Umsatz-Panel]
  E --> G[Aktivitäts-Panel]
  F -. Renderfehler .-> D

Der Fehler des Umsatz-Panels endet an seiner nächsten Boundary. Deren Fallback ersetzt nur diesen Teilbaum; Navigation und Aktivitätsbereich bleiben erhalten. Ohne die innere Grenze würde der Fehler bis zur Root-Boundary weiterlaufen.

Fallstricke am Rand

  • Falsche Fehlerklasse: Klassische Error Boundaries fangen keine Fehler aus Event-Handlern, Server Rendering oder beliebigem asynchronem Code wie setTimeout. Diese Pfade brauchen eigene Behandlung.
  • Boundary wirft selbst: Fehler im eigenen Fallback werden erst von einer weiter oben liegenden Boundary gefangen.
  • Logging ohne Kontext: Protokolliere Bereich und Component Stack, aber zeige Nutzern keine internen Fehlermeldungen oder sensiblen Payloads.
  • Funktionskomponenten: React 19.3 bietet weiterhin keine eingebaute Möglichkeit, eine Error Boundary als Funktionskomponente zu definieren; eine kleine Klasse oder eine etablierte Bibliothek ist die Alternative.

Selbst ausprobieren

Baue in zehn Minuten ein Dashboard mit zwei Panels und einem Schalter, der im Umsatz-Panel während des Renderns throw new Error("invalid revenue") ausführt. Teste zuerst nur mit der Root-Boundary und danach mit der zusätzlichen Panel-Boundary. Erwartete Beobachtung: Im ersten Fall verschwindet die gesamte App hinter dem globalen Fallback; im zweiten bleiben Navigation und Aktivitätsfeed bedienbar. Entferne danach die Panel-Boundary wieder – dieser kleine Mutationstest zeigt, ob dein Test wirklich die Ausfallzone absichert.

Die TSX-Beispiele wurden strukturell geprüft, aber nicht als React-Integrationstest ausgeführt, weil in der Laufzeit keine React-/TypeScript-Toolchain installiert war.

Verwandte Themen

Suspense-Grenzen definieren Lade- statt Fehlerzonen und sollten oft ähnlich fachlich geschnitten werden. Route-Level Recovery verbindet URL-Segmente mit eigenen Fallbacks. Observability macht aus componentDidCatch ein verwertbares Signal. Mutation Testing prüft, ob ein Test die Boundary-Platzierung tatsächlich schützt. Progressive Degradation fragt allgemeiner, welche Kernfunktion trotz Teilfehler verfügbar bleiben muss.
