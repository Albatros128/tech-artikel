Verzögere das Ergebnis, nicht die Eingabe

useDeferredValue hält das Textfeld unmittelbar und macht nur den langsamen Ergebnisbereich unterbrechbar.

React-Concurrent-Rendering · React 19.3 + TypeScript · Tief · ~8 min

Die Produktsuche funktioniert korrekt, bis der Katalog einige tausend Zeilen umfasst. Mit jedem Tastendruck rendert React die gefilterte Liste neu. Das Textfeld fühlt sich an, als würde es Buchstaben verschlucken. Der naheliegende Versuch, das kontrollierte Input-Update in eine Transition zu legen, löst jedoch genau die falsche Arbeit vom Nutzerereignis.

TL;DR

Der Wert eines kontrollierten Textfelds ist dringend und muss synchron zur Eingabe aktualisiert werden. Übergib stattdessen eine mit useDeferredValue abgeleitete Version der Suchanfrage an den nachweislich langsamen Ergebnis-Teilbaum. React darf dessen Renderarbeit unterbrechen und neu starten. Das macht die Berechnung nicht schneller und reduziert keine Requests; es verändert ihre Priorität.

Prerequisites

Du solltest kontrollierte Inputs, Renderphasen und Props kennen. Grundlage sind die offiziellen Referenzen zu useDeferredValue, useTransition und memo. Der Artikel bezieht sich auf React 19.3.

Der Aha-Effekt

„Deferred“ bedeutet nicht „warte 300 Millisekunden“. React rendert zuerst mit dem bisherigen Wert und startet anschließend sofort einen Hintergrund-Render mit dem neuen Wert. Trifft währenddessen die nächste Eingabe ein, darf React die veraltete Arbeit verwerfen und mit dem neuesten Wert neu beginnen. Die UI besitzt dabei bewusst zwei zeitliche Perspektiven: query beschreibt die aktuelle Eingabe, deferredQuery den Stand, den der Ergebnisbereich gerade darstellen kann.

Concurrent Rendering spart nicht automatisch Arbeit. Es schützt dringende Interaktion davor, auf weniger dringende Renderarbeit warten zu müssen.

So macht man es falsch

Dieses Beispiel markiert ausgerechnet den State als Transition, der das Textfeld kontrolliert. React dokumentiert ausdrücklich, dass Transition-Updates keine Text-Inputs steuern können.

// ProductSearch.tsx – problematische Variante
import { useState, useTransition } from "react";

export function ProductSearch() {
  const [query, setQuery] = useState("");
  const [isPending, startTransition] = useTransition();

  return (
    <>
      <input
        value={query}
        onChange={(event) => {
          startTransition(() => {
            setQuery(event.target.value); // kontrolliert das Input
          });
        }}
      />
      {isPending && <span>Aktualisiere…</span>}
      <ProductList query={query} />
    </>
  );
}

Warum ist das falsch?

Das Textfeld muss nach jedem onChange unmittelbar den neuen value erhalten. Eine Transition ist dagegen unterbrechbar und darf später sichtbar werden. Damit kollidieren zwei Verträge: DOM-Eingabe und React-State können vorübergehend auseinanderlaufen. Das Problem ist nicht, dass Transitions „zu langsam“ wären, sondern dass die dringende Zustandsänderung falsch klassifiziert wurde.

Auch ein pauschales Debounce löst eine andere Aufgabe. Es wartet absichtlich eine Zeitspanne und kann etwa Request-Frequenz begrenzen. useDeferredValue besitzt laut React-Dokumentation keinen festen Delay und verhindert allein keine zusätzlichen Netzwerkzugriffe.

So macht man es richtig – mit Trade-offs

Aktualisiere query normal. Die verzögerte Sicht gehört an die Grenze zum teuren Teilbaum. memo verhindert hier, dass die Liste beim dringenden Render sofort noch einmal mit demselben deferredQuery-Prop arbeitet. Es bleibt eine Optimierung, keine Korrektheitsgarantie.

// ProductSearch.tsx
import { memo, useDeferredValue, useState } from "react";

type Product = { id: string; name: string };
type Props = { products: readonly Product[] };

const ProductList = memo(function ProductList({
  products,
  query,
}: Props & { query: string }) {
  const normalized = query.trim().toLocaleLowerCase("de");
  const visible = products.filter((product) =>
    product.name.toLocaleLowerCase("de").includes(normalized),
  );

  return (
    <ul>
      {visible.map((product) => <li key={product.id}>{product.name}</li>)}
    </ul>
  );
});

export function ProductSearch({ products }: Props) {
  const [query, setQuery] = useState("");
  const deferredQuery = useDeferredValue(query);
  const isStale = query !== deferredQuery;

  return (
    <>
      <label>
        Produkte suchen
        <input
          value={query}
          onChange={(event) => setQuery(event.target.value)}
        />
      </label>
      <div aria-busy={isStale} style={{ opacity: isStale ? 0.6 : 1 }}>
        <ProductList products={products} query={deferredQuery} />
      </div>
    </>
  );
}

Der Trade-off ist sichtbare Stale-Time: Kurzzeitig passt die Liste nicht zum Textfeld. Kennzeichne diesen Zustand, statt ihn zu verstecken. Setze das Muster erst ein, wenn React Profiler oder eine reproduzierbare Interaktion den langsamen Renderpfad zeigt. Für Server-Suche kann Debouncing zusätzlich sinnvoll sein; für Suspense-basierte Datenquellen kann der alte Inhalt bis zum neuen Ergebnis sichtbar bleiben.

Fallstricke am Rand

  • Übergib keine im Render neu erzeugten Objekte an useDeferredValue; ihre Identität ändert sich jedes Mal.
  • Teure Arbeit außerhalb des Renderns wird dadurch nicht priorisiert. Verwende dort Debounce, Throttle oder einen Worker.
  • Ein neuer products-Array bei jedem Parent-Render hebt den Nutzen von memo auf.
  • Die Liste muss auch mit einem älteren Suchwert semantisch korrekt und bedienbar bleiben.

Selbst ausprobieren

Plane zehn Minuten ein. Erzeuge lokal 20.000 Produkte und füge in ProductList vorübergehend eine absichtlich teure, aber reine Schleife ein. Vergleiche im React Profiler zuerst die direkte Query-Weitergabe und danach useDeferredValue. Tippe schnell mehrere Zeichen. Erwartung: Die Gesamtrechenarbeit ist nicht garantiert kleiner, aber das Input übernimmt Zeichen früher; unvollständige Hintergrund-Renderings können verworfen werden. Entferne anschließend die künstliche Last – ohne messbare Verzögerung ist die Optimierung unnötig.

Verwandte Themen

  • startTransition: passend, wenn du die nicht dringende State-Aktualisierung selbst besitzt.
  • Suspense und Caching: entscheiden, wie alte und noch nicht geladene Ergebnisse koexistieren.
  • Debounce und AbortController: begrenzen Netzwerkverkehr und verwerfen überholte Requests.
  • React Profiler: trennt gefühlte Trägheit von tatsächlich teuren Renderpfaden.
