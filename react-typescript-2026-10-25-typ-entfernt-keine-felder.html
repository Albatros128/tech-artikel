Ein TypeScript-Typ entfernt keine Felder

Eine Variable kann wie ein öffentliches DTO aussehen und beim Serialisieren trotzdem Passwort-Hash und Reset-Token enthalten.

25.10.2026 · TypeScript-Typsystem · TypeScript 6.0 + ECMAScript JSON · Tief · ~8 min

Der Endpunkt ist sauber typisiert: Er verspricht PublicUser, die IDE zeigt nur drei öffentliche Properties, und der Pull Request wirkt harmlos. Im Browser tauchen dennoch passwordHash und resetToken auf. Niemand hat any verwendet. Der Fehler entsteht, weil ein statischer Typ mit einer Laufzeittransformation verwechselt wurde.

TL;DR

Eine Typannotation begrenzt, welche Properties TypeScript an einer Stelle sichtbar macht. Sie verändert das JavaScript-Objekt nicht. Übergib deshalb interne Entitäten nie allein durch Umtypisieren an einen Serializer. Erzeuge an der API-Grenze ein neues Objekt über eine explizite Allowlist. Das ist ausführlicher, macht aber die veröffentlichte Datenform überprüfbar.

Prerequisites

Du kennst Objekt-Typen, async/await und JSON. Die Beispiele beziehen sich auf TypeScript 6.0. Entscheidend sind TypeScripts strukturelle Typkompatibilität, die Excess-Property-Prüfung für frische Objektliterale und das dokumentierte Verhalten von JSON.stringify.

Der Aha-Effekt

TypeScript fragt bei einer Zuweisung im Wesentlichen: Besitzt die Quelle mindestens die benötigten kompatiblen Member? Ein DbUser mit fünf zusätzlichen Feldern kann deshalb als PublicUser verwendet werden. Die zusätzlichen Felder verschwinden nicht; nur die statische Sicht wird schmaler.

Frische Objektliterale wirken strenger, weil TypeScript dort Excess Properties gesondert prüft. Diese Prüfung führt leicht zur falschen Intuition, Objekttypen seien grundsätzlich „geschlossen“. Sobald das Objekt bereits in einer Variablen steckt, greift die normale strukturelle Kompatibilität. Der Serializer erhält anschließend den echten Laufzeitwert, nicht die eingeschränkte Editor-Sicht.

So macht man es falsch

Die folgende Funktion ist ohne Type Assertion und ohne any typkompatibel. Trotzdem gibt sie alle aufzählbaren eigenen Felder des Repository-Objekts als JSON aus.

import { findUserById, type DbUser } from "./user-repository";

type PublicUser = {
  id: string;
  displayName: string;
  avatarUrl: string | null;
};

function asPublicUser(user: DbUser): PublicUser {
  return user; // strukturell kompatibel, aber unverändert
}

export async function serializeUser(id: string): Promise<string> {
  const entity = await findUserById(id);
  const dto: PublicUser = asPublicUser(entity);
  return JSON.stringify(dto);
}

Angenommen, DbUser enthält zusätzlich email, passwordHash und resetToken. Die Variable dto erlaubt im TypeScript-Code zwar keinen Zugriff auf diese Member. Das zugrunde liegende Objekt besitzt sie aber weiterhin.

Warum ist das falsch?

Typen werden beim Übersetzen entfernt. Es gibt zur Laufzeit keinen PublicUser-Filter. JSON.stringify besucht laut MDN die aufzählbaren eigenen Properties des übergebenen Objekts. Sind Repository-Felder normale Objekt-Properties, werden sie deshalb serialisiert – unabhängig vom annotierten Variablentyp.

Beobachtbar ist eine API-Antwort mit mehr Feldern als im OpenAPI-Schema, im Frontend-Typ oder in der IDE. Das ist zunächst ein Vertragsbruch und kann bei sensitiven Feldern ein Sicherheitsvorfall sein. Omit<DbUser, "passwordHash"> löst ihn nicht: Auch ein Utility Type beschreibt nur eine Compile-Time-Sicht und löscht zur Laufzeit nichts.

So macht man es richtig mit Trade-offs

Erzeuge ein neues Objekt und kopiere ausschließlich die Felder, die den Prozess verlassen dürfen. Das Objektliteral ist gleichzeitig Dokumentation, Transformation und Review-Punkt.

import { findUserById, type DbUser } from "./user-repository";

type PublicUser = {
  id: string;
  displayName: string;
  avatarUrl: string | null;
};

export function toPublicUser(user: DbUser): PublicUser {
  const dto = {
    id: user.id,
    displayName: user.displayName,
    avatarUrl: user.avatarUrl
  } satisfies PublicUser;

  return dto;
}

export async function serializeUser(id: string): Promise<string> {
  const entity = await findUserById(id);
  return JSON.stringify(toPublicUser(entity));
}

satisfies prüft hier nur, dass das neu erzeugte Objekt zum Vertrag passt; die Entfernung geschieht durch die explizite Projektion. Der Trade-off ist Wiederholung. Dafür führt ein neues internes Feld nicht automatisch zu einer neuen öffentlichen Property. Ergänzt du dagegen ein Pflichtfeld im DTO, meldet der Compiler die unvollständige Projektion.

Eine Rest-Destrukturierung wie const { passwordHash, ...rest } = user ist kürzer, arbeitet aber als Blocklist: Ein später ergänztes Geheimnis landet automatisch in rest. Eine Schema-Bibliothek, die unbekannte Felder nachweislich entfernt, ist eine sinnvolle Alternative für viele Grenzen. Sie bringt Laufzeitkosten und Konfiguration mit; ihr Strip- oder Strict-Verhalten muss getestet werden. Der replacer-Parameter von JSON.stringify kann für eine kleine, zentrale Grenze ebenfalls als Allowlist dienen, erzeugt jedoch kein wiederverwendbares DTO-Objekt.

Fallstricke am Rand

  • Getter und eigene toJSON-Methoden können die Serialisierung zusätzlich beeinflussen. Teste die tatsächliche Ausgabe, nicht nur Object.keys.
  • Verschachtelte Objekte brauchen eigene Projektionen. Eine sichere äußere Allowlist macht ein eingebettetes internes Profil nicht automatisch öffentlich.
  • Verwechsle Response-Projektion nicht mit Eingabevalidierung: Eingehendes unknown muss weiterhin zur Laufzeit geprüft werden.

Selbst ausprobieren

Nimm dir fünf Minuten. Lege ein Objekt mit id, displayName und passwordHash an. Weise es einer Variable vom Typ PublicUser zu und serialisiere diese. Erwartung: Der Hash bleibt im JSON. Ersetze die Zuweisung anschließend durch toPublicUser; jetzt darf die Ausgabe nur die explizit kopierten Felder enthalten. Füge dem Ursprungsobjekt danach mfaSecret hinzu und prüfe, dass die Allowlist unverändert sicher bleibt.

Prüfstand: Die Laufzeitformen, die Blocklist-Gegenprobe und die JSON-Ausgabe wurden mit einem Node-Test geprüft. Ein TypeScript-Compile-Test war in dieser Umgebung nicht verfügbar und wird nicht behauptet.

Verwandte Themen

Runtime-Validierung schützt die entgegengesetzte Richtung an Eingabegrenzen. OpenAPI-Vertragstests entdecken zusätzliche Response-Felder. Data Minimization fragt, welche Daten ein Consumer überhaupt benötigt. Mapper-Tests sichern explizite Projektionen gegen unbeabsichtigte Erweiterungen.
