Ein Timeout muss die Arbeit abbrechen, nicht nur das Warten

Promise.race begrenzt die Geduld des Aufrufers – nicht die Lebenszeit eines Requests.

Datenzugriff & Tests · TypeScript 6.0 + Web Fetch API · Tief · ~8 min

Die Produktsuche zeigt nach fünf Sekunden „Zeitüberschreitung“. Im Netzwerk-Panel läuft der Request trotzdem weiter und erreicht später den Server. Unter Last häufen sich genau diese unsichtbaren Verlierer: Die UI hat aufgegeben, aber Verbindung, Body-Download und Backend-Arbeit besitzen noch keinen Abbruchgrund.

TL;DR

Ein Timeout ist eine Deadline für die Operation, nicht bloß ein früher Fehler für ihren Aufrufer. Promise.race ignoriert das spätere Ergebnis des verlierenden Promises, storniert ihn aber nicht. Übergib stattdessen ein AbortSignal an fetch. Kombiniere eine Deadline aus AbortSignal.timeout(ms) mit einem vorhandenen Signal über AbortSignal.any(). Teste nicht nur die Fehlermeldung, sondern auch, dass die Arbeit das Signal beobachtet und beendet.

Prerequisites

Du solltest Promises, fetch und AbortController kennen. Maßgeblich sind der DOM-Standard zu AbortSignal, der Fetch-Standard sowie die Dokumentation zu AbortSignal.timeout() und AbortSignal.any(). Die Typbeispiele beziehen sich auf TypeScript 6.0.

Der Aha-Effekt

Promises besitzen keinen eingebauten Abbruchmechanismus. race entscheidet nur, wessen Settlement den Ergebnis-Promise bestimmt. Die andere Operation erhält dadurch weder ein Ereignis noch eine Anweisung zum Stoppen. Abbruch ist ein separates Protokoll: Eine API akzeptiert ein Signal, prüft dessen Zustand, beendet ihre Arbeit und weist ihren noch offenen Promise mit dem Abbruchgrund zurück.

Review-Frage: Wenn dein Timeout gewinnt – welches Objekt informiert die laufende Arbeit darüber?

So macht man es falsch

Diese Variante erzeugt zwar pünktlich einen Fehler, lässt aber den Fetch ohne Signal weiterlaufen:

function timeoutAfter(ms: number): Promise<never> {
  return new Promise((_, reject) => {
    setTimeout(() => reject(new Error("timeout")), ms);
  });
}

export async function loadProducts(query: string) {
  const response = await Promise.race([
    fetch(`/api/products?q=${encodeURIComponent(query)}`),
    timeoutAfter(5_000),
  ]);

  return response.json();
}

Warum ist das falsch?

Nach fünf Sekunden ist nur der von Promise.race zurückgegebene Promise abgelehnt. Der ursprüngliche Fetch bleibt erreichbar und darf weiter settlen; sein späteres Ergebnis wird lediglich nicht mehr verwendet. Das ist keine Race-Condition im UI, sondern eine auseinanderfallende Lebenszeit von Aufrufer und Arbeit.

Beobachtbare Symptome sind weiterlaufende Requests nach sichtbarem Timeout, unnötige Antwort-Downloads und Tests, die grün werden, obwohl ihr Fake später noch Nebenwirkungen ausführt. Ob ein abgebrochener Request serverseitige Arbeit tatsächlich stoppt, hängt vom Transport und Server ab. Dokumentiert und überprüfbar ist jedoch, dass Fetch den Signalgrund verarbeitet, seinen Promise zurückweist und betroffene Streams abbricht.

So macht man es richtig

Die Datenzugriffsgrenze besitzt die Deadline und reicht das kombinierte Signal bis zu fetch durch. Ein optionales Signal des Aufrufers bleibt erhalten, etwa für Navigation oder einen Abbrechen-Button.

type FetchWithDeadlineOptions = Omit<RequestInit, "signal"> & {
  timeoutMs: number;
  signal?: AbortSignal;
};

export async function fetchWithDeadline(
  input: RequestInfo | URL,
  { timeoutMs, signal, ...init }: FetchWithDeadlineOptions,
): Promise<Response> {
  const deadline = AbortSignal.timeout(timeoutMs);
  const combined = signal
    ? AbortSignal.any([signal, deadline])
    : deadline;

  return fetch(input, { ...init, signal: combined });
}

const response = await fetchWithDeadline("/api/products", {
  timeoutMs: 5_000,
  signal: navigationController.signal,
});

Der Vorteil ist ein durchgängiger Abbruchvertrag und ein unterscheidbarer TimeoutError-Grund bei einem reinen Deadline-Signal. Der Trade-off: AbortSignal.timeout() lässt seinen internen Timeout nicht vorzeitig löschen. Für sehr viele lange Deadlines oder eigene Listener kann ein manueller AbortController mit setTimeout, clearTimeout im finally und sauberer Listener-Entfernung sinnvoller sein. Als Alternative kann eine Datenzugriffsbibliothek Signale bereitstellen; entscheidend bleibt, dass dein Fetch sie tatsächlich verwendet.

Fallstricke am Rand

  • Ein bereits abgebrochenes Eingangssignal macht auch das kombinierte Signal sofort abgebrochen.
  • AbortSignal.timeout() misst aktive Zeit; eine suspendierte Seite oder ein suspendierter Worker kann die Deadline pausieren.
  • Fange TimeoutError nicht pauschal als leere Ergebnisliste ab – Timeout und „keine Treffer“ sind verschiedene Zustände.

Selbst ausprobieren

Schreibe in zehn Minuten eine slowOperation(signal), die nach 100 Millisekunden einen Zähler erhöht und bei abort ihren Timer löscht. Starte sie zuerst ohne Signal gegen einen ablehnenden 10-ms-Timer in Promise.race: Der Aufrufer sieht den Timeout, der Zähler steigt später trotzdem. Wiederhole den Test mit AbortSignal.timeout(10). Erwartung: Die Operation meldet den Abbruch und der Zähler bleibt unverändert.

Verwandte Themen

  • Latest request wins: Relevanzprüfung verhindert veraltete State-Schreibvorgänge zusätzlich zum Ressourcenabbruch.
  • Server-Timeouts: Client- und Server-Deadline sollten getrennt beobachtbar und korrelierbar sein.
  • Retries: Ein Timeout darf nicht automatisch nicht-idempotente Operationen wiederholen.
  • Fake Timer: Deterministische Tests müssen Timer und Abbruchereignis kontrolliert fortschalten.
