Ein Update ist kein halbes Domänenobjekt

Partial beschreibt fehlende Properties. Was eine Änderung bedeutet, musst du selbst modellieren.

TypeScript-API-Modellierung · TypeScript: exactOptionalPropertyTypes seit 4.4 · Tief · ~7 min

Du speicherst ein Profilformular. Der Anzeigename ändert sich, die Biografie bleibt unberührt. Nach dem lokalen Update ist sie plötzlich undefined; nach demselben Update über HTTP bleibt der alte Text stehen. Beide Wege benutzen Partial<User>. Das Problem steckt nicht im Netzwerk, sondern in einem Vertrag, der unterschiedliche Absichten zusammenwirft.

TL;DR

Trenne dein Lesemodell vom Änderungsauftrag. Lege fest: Eine fehlende Property bedeutet unverändert, ein String setzt den Wert, null leert ein dafür freigegebenes Feld. Aktiviere strict und exactOptionalPropertyTypes, damit explizites undefined diesen Vertrag nicht unbemerkt aufweicht. Das ist eine bewusste API-Entscheidung, keine automatisch aus HTTP abgeleitete Semantik.

Prerequisites

Vorausgesetzt sind Object Spread, JSON und strukturelle Typisierung. Das Handbook zu Partial erklärt den Utility Type; die Release Notes zu TypeScript 4.4 dokumentieren die Einführung exakter optionaler Properties. Die Beispiele benötigen keine Bibliothek und keine Imports. Lege die Typen und Funktionen gemeinsam in profile.ts ab.

// tsconfig.json – minimale Prüfkonfiguration
{
  "compilerOptions": {
    "target": "ES2022",
    "strict": true,
    "exactOptionalPropertyTypes": true,
    "noEmit": true
  },
  "files": ["profile.ts"]
}

Der Aha-Effekt

Ein Domänenobjekt beschreibt einen Zustand. Ein Update beschreibt eine Absicht. Dass beide dieselben Feldnamen haben, macht sie nicht zum selben Konzept. Ein Benutzer besitzt eine ID; ein Profil-Update darf sie trotzdem nicht verändern. Eine leere Biografie ist ein gültiger Zustand; „nicht angefasst“ ist dagegen keine Eigenschaft der Biografie, sondern des Auftrags.

Meine Designfolgerung: Leite Schreibverträge nur dann mechanisch aus Lesemodellen ab, wenn ihre Änderungsregeln tatsächlich identisch sind. Ein kleiner eigener Typ ist häufig aussagekräftiger als ein universeller Generic.

So macht man es falsch

Der folgende Ausschnitt zeigt einen plausiblen Formularadapter. Ohne exakte optionale Properties akzeptiert der Compiler das explizite undefined. Der Spread übernimmt diesen vorhandenen Schlüssel und überschreibt den bisherigen Wert.

// Fehlervariante: mit strict, aber ohne exactOptionalPropertyTypes
type User = {
  id: string;
  displayName: string;
  bio: string | null;
};

function updateLocally(user: User, patch: Partial<User>) {
  return { ...user, ...patch };
}

const before: User = { id: "42", displayName: "Ada", bio: "Entwicklerin" };
const patch: Partial<User> = { displayName: "Ada L.", bio: undefined };
const local = updateLocally(before, patch);
// local.bio ist zur Laufzeit undefined.
const body = JSON.stringify(patch);
// '{"displayName":"Ada L."}' – bio fehlt auf dem Transportweg.

Warum ist das falsch?

Abwesenheit und ein vorhandener Schlüssel mit Wert undefined sind in JavaScript unterscheidbar. Die Compiler-Referenz erläutert genau diese Lücke. Beim Lesen kann ein optionales Feld weiterhin undefined ergeben; die Option verändert vor allem, welche Werte du ausdrücklich schreiben darfst.

Hinzu kommt die Transportgrenze: JSON.stringify lässt undefined-valued Object-Properties weg. Ein lokaler Spread und ein JSON-Roundtrip führen deshalb nicht zwangsläufig denselben Änderungsauftrag aus. Sichtbare Symptome sind verschwindende Felder im optimistischen UI und ein Rücksprung nach dem Refetch. Das ist ein Korrektheitsproblem, keine Performancefrage.

So macht man es richtig

Der eigene Vertrag nennt nur veränderbare Felder. In diesem Beispiel ist ausschließlich die Biografie leerbar. Die Implementierung behandelt Abwesenheit ausdrücklich und erhält null als echte Änderung. Verwende hier nicht patch.bio ?? user.bio: Das würde „leeren“ wieder als „unverändert“ interpretieren.

// profile.ts – User aus dem ersten Beispiel übernehmen
type ProfilePatch = {
  displayName?: string;
  bio?: string | null;
};

function applyProfilePatch(user: User, patch: ProfilePatch): User {
  return {
    ...user,
    displayName: patch.displayName === undefined
      ? user.displayName : patch.displayName,
    bio: patch.bio === undefined ? user.bio : patch.bio,
  };
}

const rename: ProfilePatch = { displayName: "Ada L." };
const clearBio: ProfilePatch = { bio: null };
const unchanged: ProfilePatch = {};

// Erwartete Typfehler separat ausprobieren:
// const ambiguous: ProfilePatch = { bio: undefined };
// const forbidden: ProfilePatch = { id: "99" };

Der Trade-off ist Pflegeaufwand: Neue editierbare Felder müssen bewusst ergänzt werden. Dafür entkoppelst du Datenanzeige und Schreibrechte. Als Alternative kann Partial<Pick<User, "displayName" | "bio">> passen, wenn beide Felder exakt dieselben Werte wie im Lesemodell erlauben. Für verschachtelte Daten oder Operationen wie „Listenelement entfernen“ ist ein expliziter Operationsvertrag präziser als ein rekursives DeepPartial.

Die gezeigte Funktion erwartet bereits geprüfte Eingaben. Ein Server muss einen eingehenden JSON-Body zusätzlich validieren, unbekannte Felder nach seiner eigenen Policy behandeln und Schreibrechte prüfen. Ein TypeScript-Typ ist weder Eingabevalidierung noch Autorisierung.

Diagramm

Fallstricke am Rand

  • exactOptionalPropertyTypes wird nicht allein durch strict aktiviert; schalte es zusätzlich ein.
  • Ein eigener Typ verbietet nicht automatisch sämtliche zusätzlichen Properties in bereits typisierten Variablen. Der Server benötigt weiterhin eine explizite Allowlist.
  • Ein flacher Patch definiert keine Merge-Regeln für verschachtelte Objekte. Entscheide zwischen vollständigem Ersetzen und eigenen Unteroperationen.

Selbst ausprobieren

Nimm dir zehn Minuten im TypeScript Playground. Prüfe zuerst die Fehlervariante ohne die Option und vergleiche Spread mit JSON-Roundtrip. Aktiviere anschließend die Option: Die Zuweisung von bio: undefined muss scheitern. Teste den neuen Vertrag mit {}, { bio: null } und { bio: "" }. Erwartung: alter Text, null und leerer String bleiben drei unterschiedliche Ergebnisse – auch nach dem Roundtrip.

Prüfstand: Diese drei Laufzeitfälle und die abweichende Fehlervariante wurden mit Node getestet. Ein separater TypeScript-Compiler war lokal nicht installiert; die erwarteten Typdiagnosen wurden deshalb nicht als bestandener Compile-Test gewertet.

Verwandte Themen

Runtime-Schemas sichern den Übergang von unbekanntem JSON zum Schreibvertrag. Optimistische Updates profitieren von identischer Semantik in Client und Server. Versionskonflikte ergänzen diesen Vertrag, wenn parallele Änderungen nicht still überschrieben werden dürfen.
