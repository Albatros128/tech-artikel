satisfies prüft Konfiguration, ohne ihre Inferenz zu verschlucken

Eine breite Typannotation macht ein Objekt sicher, aber häufig unpräzise. Der bessere Vertrag prüft die Form und lässt den konkreten Wert trotzdem sichtbar.

TypeScript-Typsystem · TypeScript 6.0 (satisfies seit 4.9) · Tief · ~8 min

Dein Frontend kennt drei Umgebungen. Lokal liefert ein Mock Transport Daten aus Fixtures, Staging und Produktion sprechen HTTP. Die Konfiguration sieht harmlos aus – bis Code, der ausdrücklich die lokale Konfiguration verwendet, nicht mehr auf fixtures zugreifen darf. Der Compiler kennt nur noch die breite Union. Du hast Sicherheit gewonnen und Wissen verloren.

TL;DR

Annotiere eine konkrete Konstante nicht vorschnell mit ihrem Obertyp. Schreibe das Objekt normal hin und hänge satisfies AppConfig an. TypeScript prüft dann, ob der Ausdruck zum Vertrag passt, behält aber den präziseren abgeleiteten Typ des Ausdrucks. Das ist ideal für statische Konfigurationen. Es ersetzt weder Runtime-Validierung noch eine bewusste Abstraktionsgrenze.

Prerequisites

Du solltest Union Types und Narrowing kennen. Hilfreich sind außerdem das keyof-Kapitel und Indexed Access Types. Die maßgebliche Beschreibung von satisfies steht in den TypeScript-4.9-Release-Notes.

Der Aha-Effekt

Eine Annotation beantwortet: „Welchen Typ soll diese Variable haben?“ satisfies beantwortet dagegen: „Erfüllt dieser Ausdruck mindestens diesen Vertrag?“ Diese Fragen sind ähnlich, aber nicht gleich. Im zweiten Fall bleibt die konkrete Struktur verfügbar: TypeScript weiß weiterhin, dass development ein Mock mit fixtures ist und production HTTP mit baseUrl.

So macht man es falsch

Die folgende Annotation ist korrekt und keineswegs exotisch. Problematisch wird sie, wenn nachgelagerter Code Details einzelner Einträge benötigt:

// config.ts – kompiliert, verliert aber Präzision
type Environment = "development" | "staging" | "production";
type TransportConfig =
  | { kind: "mock"; fixtures: readonly string[] }
  | { kind: "http"; baseUrl: string };
type AppConfig = Record<Environment, TransportConfig>;

export const appConfig: AppConfig = {
  development: { kind: "mock", fixtures: ["users", "orders"] },
  staging: { kind: "http", baseUrl: "https://staging.api.example.test" },
  production: { kind: "http", baseUrl: "https://api.example.test" }
};

appConfig.development.fixtures;
// Fehler: "fixtures" existiert nicht auf jedem TransportConfig.

Warum ist das falsch?

Die explizite Annotation setzt den Variablentyp auf AppConfig. Damit ist jeder Wert im Record die gesamte Union TransportConfig. Das ist an einer echten Abstraktionsgrenze sinnvoll: Eine Funktion, die eine beliebige Umgebung erhält, muss über kind verengen. Für eine bekannte Eigenschaft ist es jedoch unnötig grob.

Ein Type Assertion wie as AppConfig löst das nicht. Es weist dem Ergebnis ebenfalls den breiten Typ zu und formuliert zudem eher eine Behauptung als eine Prüfung. Beobachtbar wird der Unterschied im Editor: Autovervollständigung verliert konkrete Felder, und Zugriffe brauchen Narrowing, obwohl der Schlüssel bereits feststeht.

So macht man es richtig – mit Trade-offs

Die Konfiguration darf ihren eigenen Typ behalten; satisfies kontrolliert nur die Zuweisungskompatibilität. as const hält zusätzlich Schlüsselwerte und Arrays readonly und literalgenau:

// config.ts – vollständiges, eigenständiges TypeScript-Modul
type Environment = "development" | "staging" | "production";
type TransportConfig =
  | { kind: "mock"; fixtures: readonly string[] }
  | { kind: "http"; baseUrl: string };
type AppConfig = Record<Environment, TransportConfig>;

export const appConfig = {
  development: { kind: "mock", fixtures: ["users", "orders"] },
  staging: { kind: "http", baseUrl: "https://staging.api.example.test" },
  production: { kind: "http", baseUrl: "https://api.example.test" }
} as const satisfies AppConfig;

export type ConfiguredEnvironment = keyof typeof appConfig;

export function describeTransport(env: ConfiguredEnvironment): string {
  const config = appConfig[env];
  return config.kind === "mock"
    ? `fixtures:${config.fixtures.join(",")}`
    : config.baseUrl;
}

appConfig.development.fixtures; // readonly ["users", "orders"]

Ein fehlendes production, ein Tippfehler im Schlüssel oder ein falsches Feld wird weiter abgelehnt. Der Trade-off: Konsumenten können sich nun an konkrete Einträge koppeln. Soll ein Modul absichtlich nur den abstrakten Vertrag sehen, exportiere eine Getter-Funktion mit Rückgabetyp TransportConfig oder annotiere an dieser Grenze bewusst breit. Für JSON, Umgebungsvariablen oder API-Daten brauchst du zusätzlich Runtime-Validierung; satisfies existiert nach dem Kompilieren nicht mehr.

Textuelle Erklärung: Beide Wege prüfen gegen AppConfig. Die Annotation ersetzt anschließend den Typ der Variable; satisfies bewahrt den abgeleiteten Typ des Objektliterals.

Fallstricke am Rand

  • satisfies transformiert keinen Wert und ergänzt keine Defaults.
  • Ohne as const können Literalwerte weiterhin zu string oder number verbreitert werden.
  • Zu konkrete exportierte Typen können Refactorings erschweren; abstrahiere dort, wo Austauschbarkeit Teil der API ist.

Selbst ausprobieren

Kopiere das Modul in den TypeScript Playground. Entferne zuerst satisfies AppConfig und schreibe stattdessen : AppConfig hinter appConfig: Der Zugriff auf development.fixtures scheitert. Stelle danach satisfies wieder her und vertippe production. Erwartung: Der erste Versuch verliert Präzision; der zweite bewahrt sie und meldet trotzdem den falschen Schlüssel. Das dauert etwa zehn Minuten und macht den Unterschied im Editor unmittelbar sichtbar.

Verwandte Themen

Discriminated Unions erklären das sichere Verengen innerhalb des Getters. Mapped Types zeigen, wie solche vollständigen Konfigurationsverträge entstehen. Generics helfen, die Schlüssel-Wert-Beziehung in Hilfsfunktionen zu erhalten. Für externe Daten schließt Runtime-Schema-Validierung die Lücke zwischen statischem Vertrag und tatsächlichem Wert.
