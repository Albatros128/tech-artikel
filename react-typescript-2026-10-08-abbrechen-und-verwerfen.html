Abbrechen ist nicht dasselbe wie Verwerfen

Bei schnellem Filterwechsel muss React nicht nur alte Requests stoppen. Es braucht eine ausdrückliche Regel, welcher Request den sichtbaren Zustand noch verändern darf.

Datenzugriff · React 19.3 + TypeScript · Tief · ~9 min

Eine Suche lädt „Berlin“. Noch bevor die Antwort eintrifft, wählt der Nutzer „Darmstadt“. Der zweite Request ist schnell, die richtige Liste erscheint – und wird kurz darauf von der verspäteten Berlin-Antwort überschrieben. Kein Hook ist „stale“, kein Dependency-Array fehlt. Das Problem ist simpler: Netzwerkantworten halten sich nicht an die Reihenfolge ihrer Requests.

TL;DR

Modelliere bei manuellen Requests im Effect zwei getrennte Verantwortungen: AbortController beendet nach Möglichkeit unnötige Arbeit; ein Effect-lokales active-Flag verhindert, dass ein nicht mehr relevanter asynchroner Ablauf State schreibt. Erst zusammen drücken sie die fachliche Regel „latest request wins“ aus. Bei komplexerem Datenzugriff ist ein Router-Loader oder eine Cache-Bibliothek meist die bessere Abstraktion.

Prerequisites

Vorausgesetzt sind Effects und ihre Cleanup-Funktion, Promise-Fehlerbehandlung sowie AbortController. Die React-Dokumentation beschreibt Effects als Synchronisierung mit externen Systemen und führt für manuelles Fetching ausdrücklich einen Schutz gegen falsch sortierte Antworten vor.

Der Aha-Effekt

Cancellation und Relevanz sind verschiedene Dinge. Cancellation fragt: „Kann diese Arbeit gestoppt werden?“ Relevanz fragt: „Darf ihr Ergebnis noch in die UI?“ Ein Fetch kann bereits aufgelöst sein, während danach noch JSON dekodiert, validiert oder transformiert wird. Außerdem respektiert nicht jede Promise-basierte API ein AbortSignal. Deshalb ist Abbrechen eine Ressourcenoptimierung; die Commit-Regel ist die eigentliche Korrektheitsgarantie.

So macht man es falsch

Diese Variante ist realistisch: Sie setzt einen Ladezustand, behandelt HTTP-Fehler und besitzt vollständige Dependencies. Trotzdem kann ein älterer Request den neueren Zustand überschreiben.

// UserSearch.tsx – fehlerhafter Ausschnitt
import { useEffect, useState } from "react";

type User = { id: string; name: string };

export function UserSearch({ city }: { city: string }) {
  const [users, setUsers] = useState<User[]>([]);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    setError(null);
    fetch(`/api/users?city=${encodeURIComponent(city)}`)
      .then(response => {
        if (!response.ok) throw new Error(`HTTP ${response.status}`);
        return response.json() as Promise<User[]>;
      })
      .then(setUsers)
      .catch(error => setError(String(error)));
  }, [city]);

  // Rendering gekürzt
  return <p>{error ?? `${users.length} Treffer`}</p>;
}

Warum ist das falsch?

Jeder Effect-Durchlauf erzeugt eine eigene Closure mit seinem city-Wert. React räumt den alten Effect vor dem nächsten Setup auf, aber ohne Cleanup gibt es nichts zu stoppen oder zu entwerten. Beide Promise-Ketten dürfen später setUsers aufrufen. React kennt ihre fachliche Reihenfolge nicht; „zuletzt gestartet“ ist keine eingebaute State-Update-Priorität.

Unter künstlich gleichmäßiger Latenz bleibt der Fehler unsichtbar. Beobachtbar wird er bei schnellem Wechsel, schwankender Verbindung oder unterschiedlich teuren Serverabfragen: Filter und Ergebnis passen nicht zusammen. Das ist ein Korrektheitsproblem, keine pauschale Performancebehauptung.

So macht man es richtig mit Trade-offs

Der Effect besitzt genau einen Request. Sein Cleanup entzieht diesem Request die Schreibberechtigung und sendet zusätzlich das Abort-Signal:

// UserSearch.tsx – vollständiger relevanter Ausschnitt
import { useEffect, useState } from "react";

type User = { id: string; name: string };
type SearchState =
  | { status: "loading"; city: string }
  | { status: "success"; city: string; users: User[] }
  | { status: "error"; city: string; message: string };

function isAbortError(error: unknown): boolean {
  return error instanceof DOMException && error.name === "AbortError";
}

export function UserSearch({ city }: { city: string }) {
  const [state, setState] = useState<SearchState>({ status: "loading", city });

  useEffect(() => {
    const controller = new AbortController();
    let active = true;
    setState({ status: "loading", city });

    void (async () => {
      try {
        const response = await fetch(
          `/api/users?city=${encodeURIComponent(city)}`,
          { signal: controller.signal }
        );
        if (!response.ok) throw new Error(`HTTP ${response.status}`);
        const users = await response.json() as User[]; // Boundary-Validierung ergänzen
        if (active) setState({ status: "success", city, users });
      } catch (error: unknown) {
        if (!active || isAbortError(error)) return;
        setState({ status: "error", city, message: String(error) });
      }
    })();

    return () => {
      active = false;
      controller.abort();
    };
  }, [city]);

  return <p>{state.status === "success"
    ? `${state.users.length} Treffer für ${state.city}`
    : state.status === "error" ? state.message : `Lade ${state.city} …`}</p>;
}

Laut MDN bricht abort() Fetch, das Lesen des Response-Bodys und Streams ab; das Promise wird typischerweise mit einer AbortError-DOMException abgelehnt. Das lokale Flag bleibt trotzdem die Semantikschicht. Der Preis sind Boilerplate und fehlendes Caching. React empfiehlt für produktionsweiten Datenzugriff Framework-Mechanismen oder einen Client-Cache, weil manuelles Fetching in Effects auch Preloading, Deduplizierung und Server Rendering nicht löst.

Textuelle Erklärung: Der Wechsel nach Darmstadt räumt den Berlin-Effect auf. Der neue Request darf State schreiben; eine verspätete Berlin-Antwort wird unabhängig vom tatsächlichen Abbruch verworfen.

Fallstricke am Rand

  • Ein Abort ist kein Benutzerfehler und sollte keine rote Fehlermeldung erzeugen.
  • Ein AbortSignal ist nach dem Abbruch verbraucht; erzeuge pro Effect-Durchlauf einen Controller.
  • Das Beispiel castet JSON nur der Kürze halber. Externe Daten brauchen weiterhin Runtime-Validierung.
  • Mehrere parallele Seiten eines Ergebnisses benötigen eine andere Semantik als „latest wins“.

Selbst ausprobieren

Verzögere die Berlin-Antwort im Mock um 1500 ms und Darmstadt um 100 ms. Wechsle innerhalb einer halben Sekunde. Ohne Cleanup erscheint zuerst Darmstadt und danach fälschlich Berlin. Ergänze zunächst nur active, danach auch den Controller. Erwartung: Schon das Flag schützt den sichtbaren Zustand; der Controller beendet zusätzlich die nicht mehr benötigte Fetch-Arbeit. Die Übung dauert etwa zehn Minuten.

Verwandte Themen

Effect-Lebenszyklen erklären die Setup-Cleanup-Symmetrie. Ein discriminated Union State verhindert widersprüchliche Kombinationen aus Daten, Fehler und Ladeflag. Runtime-Validierung schützt die Netzwerkgrenze. Router-Loader, Suspense-fähige Frameworks und Client-Caches verlagern Request-Koordination, Deduplizierung und Cache-Invalidierung aus einzelnen Komponenten.
