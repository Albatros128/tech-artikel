useLayoutEffect ist eine Paint-Grenze

Miss DOM-Geometrie vor dem Paint nur dann, wenn ein falscher erster Frame fachlich sichtbar wäre.

React-Render-Verhalten · React 19.3 + TypeScript · Tief · ~8 min

Ein Tooltip sitzt im Normalfall unter seinem Auslöser. Nahe am unteren Fensterrand soll er darüber erscheinen. Die Berechnung ist korrekt, trotzdem springt der Tooltip beim Öffnen für einen Frame: zuerst nach unten, dann nach oben. Das Problem ist nicht die Formel, sondern der Zeitpunkt, zu dem der Browser ihr Ergebnis sehen darf.

TL;DR

useEffect ist richtig, wenn ein zwischenzeitlicher Paint akzeptabel ist. useLayoutEffect ist für die seltene Invariante gedacht, dass React nach dem DOM-Commit messen und erneut rendern muss, bevor der Browser zeichnet. Diese Garantie verhindert beim positionsabhängigen Tooltip den falschen ersten Frame, blockiert aber das Painting. Die Wahl ist deshalb keine Stilfrage zwischen zwei Hooks, sondern eine Entscheidung über Sichtbarkeit und Render-Budget.

Prerequisites

Du solltest Effects, Refs, Portals und den Commit nach einem React-Render kennen. Die React-Dokumentation zu useLayoutEffect beschreibt die Pre-Paint-Garantie und ihren Preis. useEffect darf den Browser dagegen vorher zeichnen lassen. MDN dokumentiert getBoundingClientRect(). Der Versionsbezug ist React 19.3.

Der Aha-Effekt

Layoutmessung ist zwangsläufig ein Zwei-Pass-Verfahren: Erst muss ein DOM-Knoten existieren, dann kann seine tatsächliche Größe in die Platzierung einfließen. Du kannst den ersten Pass nicht entfernen. Du kannst nur entscheiden, ob er sichtbar wird. useLayoutEffect schiebt Messung und zustandsbedingten zweiten Render zwischen Commit und Paint.

Die zentrale Entscheidung: Verwende den blockierenden Hook nicht, weil Code „mit dem DOM arbeitet“, sondern weil der erste Paint ohne das Messergebnis falsch wäre.

So macht man es falsch

Der folgende Ausschnitt misst korrekt, aber zu spät. Das initiale top: 0 kann sichtbar werden; erst danach setzt der Effect die echte Position.

// Tooltip.tsx – lauffähiger Ausschnitt für eine Browser-React-App
import { useEffect, useRef, useState } from "react";
import { createPortal } from "react-dom";

type Point = Readonly<{ top: number; left: number }>;

export function Tooltip(props: { anchor: HTMLElement; text: string }) {
  const tipRef = useRef<HTMLDivElement>(null);
  const [point, setPoint] = useState<Point>({ top: 0, left: 0 });

  useEffect(() => {
    const tip = tipRef.current;
    if (!tip) return;
    setPoint(place(props.anchor, tip));
  }, [props.anchor, props.text]);

  return createPortal(
    <div ref={tipRef} role="tooltip" style={{ position: "fixed", ...point }}>
      {props.text}
    </div>,
    document.body,
  );
}

Warum ist das falsch?

React schreibt den Tooltip beim Commit in den DOM. Ein normaler Effect garantiert nicht, dass seine visuelle Korrektur vor dem nächsten Paint läuft. Der Browser darf daher die Startkoordinate zeigen, dann folgen Messung, setPoint, zweiter Render und ein weiterer Paint. Das beobachtbare Symptom ist ein Sprung; auf langsamen Geräten oder bei belastetem Main Thread wird er leichter sichtbar.

opacity: 0 bis zum Effect kaschiert den Sprung, verschiebt aber die Entscheidung: Der Tooltip erscheint später. Das ist eine valide Alternative, wenn verzögertes Erscheinen akzeptabler ist als blockiertes Painting.

So macht man es richtig

Für einen interaktiv geöffneten Tooltip darf der Server keine Position erraten. Im Browser misst ein Layout Effect unmittelbar nach dem Commit. React verarbeitet das darin geplante State-Update vor dem Paint. Die Hilfsfunktion bleibt unabhängig testbar.

import { useLayoutEffect, useRef, useState } from "react";
import { createPortal } from "react-dom";

type Point = Readonly<{ top: number; left: number }>;
const GAP = 8;

function place(anchor: HTMLElement, tip: HTMLElement): Point {
  const a = anchor.getBoundingClientRect();
  const t = tip.getBoundingClientRect();
  const fitsBelow = a.bottom + GAP + t.height <= window.innerHeight;
  return {
    top: fitsBelow ? a.bottom + GAP : a.top - GAP - t.height,
    left: Math.min(a.left, window.innerWidth - t.width - GAP),
  };
}

export function Tooltip(props: { anchor: HTMLElement; text: string }) {
  const tipRef = useRef<HTMLDivElement>(null);
  const [point, setPoint] = useState<Point>({ top: 0, left: 0 });

  useLayoutEffect(() => {
    const tip = tipRef.current;
    if (tip) setPoint(place(props.anchor, tip));
  }, [props.anchor, props.text]);

  return createPortal(
    <div ref={tipRef} role="tooltip" style={{ position: "fixed", ...point }}>
      {props.text}
    </div>,
    document.body,
  );
}

Der Trade-off ist konkret: Jeder Aufruf und jedes darin ausgelöste Update hält den Paint auf. Für ein kurzlebiges Overlay kann das die richtige Priorität sein. Für Datenladen, Logging oder Widget-Synchronisierung ist es unnötig; dort bleibt useEffect die bessere Grenze. Kann CSS die Platzierung ausdrücken, ist gar keine JavaScript-Messung die robustere Alternative.

Diagramm

flowchart TD
    A[Render mit Startposition] --> B[DOM-Commit]
    B --> C{Effect-Typ}
    C -- useEffect --> D[Paint kann Startposition zeigen]
    C -- useLayoutEffect --> E[Messen und erneut rendern vor Paint]

Textliche Erklärung: Beide Varianten benötigen Commit, Messung und einen zweiten Render. Nur der Layout Effect verhindert, dass der Browser den Zwischenstand zeichnet.

Fallstricke am Rand

  • Effects laufen nur im Client. Rendere messabhängige Overlays nicht als vermeintlich fertig positioniertes Server-HTML.
  • Scrollen, Zoom und Größenänderungen können die Geometrie nach dem Öffnen verändern. Dafür brauchst du ein eigenes Beobachtungsmodell, etwa ResizeObserver.
  • Ein Layout Effect ersetzt keine Messung. Prüfe Überläufe links, rechts, oben und unten statt nur die Tooltip-Höhe.

Selbst ausprobieren

Baue den Tooltip in fünf bis zehn Minuten in eine Vite-React-App ein und platziere den Auslöser am unteren Viewport-Rand. Drossele im Browser die CPU, öffne den Tooltip zuerst mit useEffect und beobachte den falschen Startpunkt. Tausche nur den Hook gegen useLayoutEffect. Erwartung: Die sichtbare Zwischenposition verschwindet; im Performance-Profil liegt die Messung nun vor dem Paint.

Verwandte Themen

  • ResizeObserver: Er modelliert Größenänderungen nach dem ersten Layout, nicht nur die Initialmessung.
  • CSS Anchor Positioning: Deklaratives Layout kann JavaScript-Messung für geeignete Overlays ersetzen.
  • Portals und Fokus: Visuelle Position und logische React-Hierarchie sind getrennte Entscheidungen.
  • Performance-Messung: Layout Effects rechtfertigen sich durch eine sichtbare Invariante, nicht durch Vermutung.
