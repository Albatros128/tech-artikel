Ein Retry braucht eine Wiederholbarkeitsgarantie

Bei einer Mutation ist „noch einmal senden“ erst dann sicher, wenn Client und Server denselben Befehl wiedererkennen.

Datenzugriff & API-Design · TypeScript 6.0 / HTTP Semantics (RFC 9110) · Tief · ~8 min

Die Bestellung wurde angelegt, doch im Browser erscheint „Netzwerkfehler“. Ein automatischer Retry wirkt wie robuste Fehlerbehandlung. Tatsächlich kann er dieselbe Bestellung ein zweites Mal erzeugen: Der Server hatte den ersten Request bereits verarbeitet, nur seine Antwort erreichte den Client nicht.

TL;DR

Ein Transportfehler sagt nicht, ob eine Mutation ausgeführt wurde. Wiederhole einen nicht-idempotenten Request deshalb nur, wenn das Anwendungsprotokoll eine stabile Befehls-ID vorsieht und der Server für dieselbe ID dasselbe Ergebnis zurückgibt. Backoff begrenzt Last; er verhindert keine Duplikate.

Prerequisites

Du solltest idempotente HTTP-Methoden nach RFC 9110, die Fetch API und TypeScripts discriminated unions kennen. Der Versionsbezug ist TypeScript 6.0; das Muster benötigt jedoch keine neue 6.0-Syntax.

Der Aha-Effekt

Retry-Sicherheit ist keine Eigenschaft deiner Schleife, sondern des gesamten Protokolls. RFC 9110 erlaubt die automatische Wiederholung idempotenter Methoden nach Kommunikationsfehlern. Eine nicht-idempotente Methode sollte ein Client dagegen nur wiederholen, wenn er ihre Semantik als idempotent kennt oder sicher weiß, dass der erste Versuch nicht angewendet wurde.

Eigene Schlussfolgerung: Der Retry-Mechanismus gehört damit fachlich näher an den Mutationsvertrag als an einen generischen Fetch-Wrapper.

So macht man es falsch

Die folgende Variante behandelt jeden Netzwerkfehler gleich. Sie erzeugt für jeden Versuch einen neuen fachlichen Befehl, obwohl der erste bereits erfolgreich gewesen sein kann.

// Ausschnitt: realistische Fehlervariante
type OrderInput = { sku: string; quantity: number };

export async function createOrder(input: OrderInput): Promise<Order> {
  for (let attempt = 0; attempt < 2; attempt++) {
    try {
      const response = await fetch("/api/orders", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify(input)
      });
      if (!response.ok) throw new Error(`HTTP ${response.status}`);
      return await response.json() as Order;
    } catch (error) {
      if (attempt === 1) throw error;
    }
  }
  throw new Error("unerreichbar");
}

Warum ist das falsch?

fetch() verwirft sein Promise bei Netzwerkfehlern, aber nicht allein wegen eines HTTP-Fehlerstatus; response.ok muss separat geprüft werden. Ein verworfenes Promise beweist trotzdem nicht, dass der Server nichts gespeichert hat. Auch ein clientseitiges Abbrechen macht eine bereits begonnene Servertransaktion nicht rückgängig.

Beobachtbar sind doppelte Bestellungen, Zahlungen oder Jobs – besonders dann, wenn Timeouts unter Last wahrscheinlicher werden. Das ist keine behauptete Performancewirkung, sondern eine Korrektheitsfolge des unklaren Commit-Zeitpunkts.

So macht man es richtig

Der Client erzeugt einmal eine Befehls-ID und verwendet sie bei allen Versuchen. Der Server speichert ID und Ergebnis atomar mit der Mutation. Idempotency-Key ist hier ein ausdrücklich vereinbarter Anwendungs-Header, keine automatische Garantie des Browsers.

// Vollständiger Client-Ausschnitt
export type OrderInput = { sku: string; quantity: number };
export type Order = { id: string; sku: string; quantity: number };

type Outcome =
  | { kind: "created"; order: Order }
  | { kind: "replayed"; order: Order };

export async function submitOrder(
  input: OrderInput,
  commandId = crypto.randomUUID(),
  request: typeof fetch = fetch
): Promise<Outcome> {
  const send = () => request("/api/orders", {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "Idempotency-Key": commandId
    },
    body: JSON.stringify(input)
  });

  for (let attempt = 0; attempt < 2; attempt++) {
    try {
      const response = await send();
      if (!response.ok) throw new Error(`HTTP ${response.status}`);
      return await response.json() as Outcome;
    } catch (error) {
      if (attempt === 1) throw error;
    }
  }
  throw new Error("unerreichbar");
}

Der Trade-off: Du brauchst Speicher, eine Aufbewahrungsfrist und eine Regel für „gleiche ID, anderer Payload“. Letzteres sollte ein Konflikt sein. Alternativ kann der Client nach einem unklaren Timeout den Status über die Befehls-ID abfragen. Für fachlich natürlich idempotente Operationen kann auch ein passendes PUT-Modell genügen.

Diagramm

Fallstricke am Rand

  • Erzeuge die Befehls-ID nicht innerhalb jedes Retry-Versuchs.
  • Speichere Schlüssel und Mutation atomar; zwei getrennte Writes öffnen erneut ein Race.
  • Wiederhole nicht pauschal jeden 4xx- oder 5xx-Status. Retry-After kann Wartezeit signalisieren, nicht die fachliche Sicherheit.

Selbst ausprobieren

Baue in 10 Minuten einen Fake-Server mit einer Map<string, Order>. Lass Versuch eins die Bestellung speichern und danach einen simulierten Verbindungsabbruch werfen. Wiederhole mit derselben ID. Erwartung: Die Map enthält genau einen Eintrag und beide erfolgreichen Antworten referenzieren dieselbe Order-ID. Ändere danach die ID beim Retry; nun wird das Duplikat sichtbar.

Verwandte Themen

  • Optimistische UI: Eine stabile Befehls-ID verbindet lokale Projektion und Serverergebnis.
  • Outbox Pattern: Es verschiebt dieselbe Zustellungsfrage an die Grenze zwischen Datenbank und Message Broker.
  • ETags und If-Match: Sie verhindern verlorene Updates, lösen aber nicht automatisch doppelte Erzeugungen.
  • Exponential Backoff mit Jitter: Er steuert Wiederholungszeitpunkte, ersetzt aber keine Idempotenz.
