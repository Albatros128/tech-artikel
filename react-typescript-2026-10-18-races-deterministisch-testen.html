Ein Race-Condition-Test muss die kritische Reihenfolge erzwingen

Warte nicht länger auf asynchronen Code. Entscheide im Test, welche Operation zuerst fertig wird.

Frontend-Tests · TypeScript + Node.js 24.19.0 · Tief · ~7 min

Eine Suche zeigt gelegentlich Ergebnisse der vorherigen Eingabe. Der Regressionstest bleibt grün: Er sucht zuerst nach „alt“, danach nach „neu“ und prüft den letzten Treffer. Dieser Test deckt beide Eingaben ab, aber nicht den Fehler. Er lässt niemals eine alte Antwort nach einer neuen eintreffen.

TL;DR

Injiziere einen Loader, dessen Promises der Test selbst auflöst. Starte beide Anfragen vor dem ersten Abschluss. Lass die neue Antwort zuerst erscheinen und danach die alte. Prüfe sowohl den Zwischenstand als auch die gesamte Veröffentlichungshistorie. So testest du eine festgelegte Ereignisfolge statt eine zufällig günstige Laufzeit.

Prerequisites

Du kennst Promises und Dependency Injection in TypeScript. Promise.withResolvers liefert Promise, Resolve- und Reject-Funktion gemeinsam. Die Beispiele verwenden den eingebauten Node-Test-Runner und wurden mit Node 24.19.0 ausgeführt. Speichere die folgenden drei Codeblöcke gemeinsam als search.test.mts und starte node --test search.test.mts.

Node kann die hier verwendeten löschbaren TypeScript-Typen direkt entfernen. Das ist laut Node-Dokumentation keine Typprüfung und berücksichtigt keine tsconfig.json. Ein separates Projekt-Typecheck mit strict, ES2024-Lib und Node-Typdefinitionen bleibt sinnvoll.

Der Aha-Effekt

Ein Race-Test braucht keine echte Parallelität und keine langsamen Requests. Er braucht zwei noch offene Operationen und die Kontrolle darüber, wann ihre Fortsetzungen laufen. Die entscheidende Aussage lautet nicht „nach 500 Millisekunden stimmt das Ergebnis“, sondern „nach Abschluss der neueren Anfrage darf die ältere nichts mehr veröffentlichen“.

Meine Designentscheidung ist deshalb eine kleine Testnaht am Loader. Die folgende Suchkoordination ist eine eigenständige, UI-unabhängige Einheit für eine React-Datenzugriffsschicht. Der Generationenzähler implementiert den Vertrag „zuletzt gestartet gewinnt“. Hier wird nur der Erfolgsweg betrachtet; Loader-Fehler werden an den Aufrufer weitergereicht.

import assert from "node:assert/strict";
import { test } from "node:test";

function createLatestSearch<T>(
  load: (query: string) => Promise<T>,
  publish: (value: T) => void,
) {
  let generation = 0;
  return async (query: string): Promise<void> => {
    const ownGeneration = ++generation;
    const result = await load(query);
    if (ownGeneration === generation) publish(result);
  };
}

So macht man es falsch

Als alleiniger Regressionstest ist der Happy Path zu schwach. Die erste Suche ist bereits vollständig beendet, bevor die zweite beginnt. Selbst ohne Generationenprüfung besteht dieser Test. Er ist nicht nutzlos; er beantwortet nur eine andere Frage.

test("zeigt das neueste Suchergebnis", async () => {
  const published: string[] = [];
  const search = createLatestSearch(
    async query => query,
    value => published.push(value),
  );

  await search("alt");
  await search("neu");
  assert.equal(published.at(-1), "neu");
});

Warum ist das falsch?

Das erste await entfernt genau die Überlappung, die den Defekt auslöst. Eine grüne Assertion beweist nur, dass zwei sequenzielle Aufrufe funktionieren. Mehr Wiederholungen desselben Ablaufs erzeugen daraus keinen Test für umgekehrte Abschlüsse.

Auch feste Wartezeiten sind kein Ersatz für die relevante Ordnung. Ein Browser-Timer garantiert keinen exakten Ausführungszeitpunkt. Vor allem aber sagt verstrichene Zeit nichts darüber aus, ob du die gefährliche Reihenfolge überhaupt hergestellt hast. Der Test sollte die Bedingung konstruieren, nicht darauf hoffen.

So macht man es richtig mit Trade-offs

Jede Anfrage bekommt ein eigenes steuerbares Promise. Der Test löst B auf und wartet auf genau den zugehörigen Suchaufruf. Erst danach löst er A auf. Diese beiden await-Grenzen sorgen dafür, dass die Assertions nach der jeweiligen Verarbeitung laufen.

test("verwirft eine verspätete ältere Antwort", async () => {
  const older = Promise.withResolvers<string>();
  const newer = Promise.withResolvers<string>();
  const published: string[] = [];
  const search = createLatestSearch(
    query => {
      if (query === "alt") return older.promise;
      if (query === "neu") return newer.promise;
      throw new Error(`Unerwartete Query: ${query}`);
    },
    value => published.push(value),
  );

  const a = search("alt");
  const b = search("neu");
  assert.deepEqual(published, []);

  newer.resolve("neuer Treffer");
  await b;
  assert.deepEqual(published, ["neuer Treffer"]);

  older.resolve("alter Treffer");
  await a;
  assert.deepEqual(published, ["neuer Treffer"]);
});

Die erste Ergebnisprüfung verhindert einen falschen Erfolg, wenn die Implementierung einfach gar nichts veröffentlicht. Die letzte prüft nicht nur einen Endwert: Die komplette Historie darf keinen alten Treffer enthalten. Das ist der eigentliche beobachtbare Vertrag dieser Einheit.

Der Trade-off ist eine bewusst kontrollierte Abhängigkeit. Sie belegt weder echte HTTP-Verarbeitung noch React-Rendering oder Cleanup beim Unmount. Dafür isoliert sie die Reihenfolge ohne Netzwerk und ohne Schlafpausen. Als Alternative passen Fake Timer, wenn Debouncing oder Timeouts selbst zum Vertrag gehören. Für reine Promise-Abschlüsse modellieren sie dagegen eine Uhr, die der Test gar nicht benötigt. Ergänzende Integrationstests bleiben für die Verdrahtung zuständig.

Fallstricke am Rand

  • Warte auf das Promise der öffentlichen Operation, nicht nur auf das aufgelöste Loader-Promise. Die Verarbeitung danach gehört zum Testziel.
  • Ein allgemeines „Microtasks leeren“ versteckt oft eine fehlende Completion-Schnittstelle. Mache das Ende der Operation beobachtbar.
  • Eine verspätete Ablehnung und das Verlassen der Ansicht brauchen eigene Vertragsentscheidungen und zusätzliche Tests.

Selbst ausprobieren

Nimm dir zehn Minuten. Führe beide Tests aus. Entferne anschließend nur if (ownGeneration === generation), sodass jeder Treffer veröffentlicht wird. Erwartung: Der sequenzielle Test bleibt grün; der kontrollierte Test scheitert mit zwei Einträgen. Stelle den Guard wieder her. Diese gezielte Mutation wurde beim Prüfen des Artikels genauso ausgeführt. Die unveränderten Tests bestanden; die Mutation wurde erkannt. Ein separater tsc-Lauf war mangels Compiler nicht möglich.

Verwandte Themen

Mutation Testing bewertet, ob Tests gezielt eingebaute Defekte erkennen. React-Integrationstests prüfen, ob Hooks und Komponenten die getestete Einheit korrekt anbinden. Debounce-Verträge benötigen kontrollierte Zeit zusätzlich zur kontrollierten Antwortreihenfolge.
