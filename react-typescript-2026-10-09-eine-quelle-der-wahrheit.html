Eine Komponente braucht genau eine Quelle der Wahrheit

Eine wiederverwendbare Eingabe darf kontrolliert oder unkontrolliert sein. Wenn ihre API beide Modelle gleichzeitig zulässt, entsteht Synchronisationscode statt Flexibilität.

React-Komponenten-APIs · React 19.3 + TypeScript · Tief · ~8 min

Ein SearchField startet als kleine Eingabe mit internem State. Später soll ein Filterformular den Wert von außen setzen können. Also kommen value, defaultValue und onValueChange hinzu. Kurz darauf synchronisiert ein Effect Prop und State. Bei einem Reset zeigt die Eingabe für einen Render den alten Wert; bei manchen Aufrufen sind sogar value und defaultValue gesetzt. Die Komponente hat nicht zu wenig State, sondern zwei Besitzer.

TL;DR

Entscheide in der öffentlichen API explizit zwischen kontrolliert und unkontrolliert. Im kontrollierten Modus besitzt der Parent den aktuellen Wert; die Komponente meldet nur Änderungen. Im unkontrollierten Modus besitzt die Komponente den Wert; defaultValue initialisiert ihn genau einmal. Eine discriminated Union macht ungültige Prop-Kombinationen unrepräsentierbar. Ein Effect zum Kopieren von value in lokalen State ist dann unnötig.

Prerequisites

Du solltest State Ownership und Lifting State Up, kontrollierte Inputs sowie Discriminated Unions kennen. Die aktuelle React-19.3-Dokumentation hält fest: Ein Input kann nicht gleichzeitig kontrolliert und unkontrolliert sein und darf während seiner Lebenszeit nicht zwischen beiden Modi wechseln.

Der Aha-Effekt

„Controlled“ beschreibt nicht, ob ein <input> technisch ein value-Attribut erhält. Es beschreibt, wer die Entscheidung über den aktuellen Wert besitzt. Sobald der Parent Besitzer ist, darf lokaler State keine zweite Wahrheit speichern. onValueChange ist dann ein Vorschlag an den Besitzer, kein interner Schreibbefehl. Das macht Datenfluss und Reset-Verhalten vorhersehbar.

So macht man es falsch

Die scheinbar bequeme API erlaubt jede Kombination. Der Effect versucht anschließend, widersprüchliche Verantwortungen zu versöhnen:

// SearchField.tsx – problematischer Ausschnitt
import { useEffect, useState } from "react";

type Props = {
  value?: string;
  defaultValue?: string;
  onValueChange?: (value: string) => void;
};

export function SearchField({ value, defaultValue = "", onValueChange }: Props) {
  const [draft, setDraft] = useState(defaultValue);

  useEffect(() => {
    if (value !== undefined) setDraft(value);
  }, [value]);

  function change(next: string) {
    setDraft(next);
    onValueChange?.(next);
  }

  return <input value={draft} onChange={event => change(event.target.value)} />;
}

Warum ist das falsch?

Props werden gerendert, Effects laufen erst nach dem Commit. Ändert der Parent value, rendert die Komponente zunächst mit dem alten draft; erst der Effect plant ein zweites Render. Noch wichtiger: Benutzereingaben verändern immer lokalen State, selbst wenn der Parent den neuen Wert ablehnen, normalisieren oder verzögert übernehmen will. Die Komponente behauptet kontrollierbar zu sein, entscheidet aber weiterhin selbst.

Auch die Aufrufseite erhält keine Hilfe. TypeScript akzeptiert value ohne Handler, beide Startwerte zugleich oder einen versehentlichen Moduswechsel. Das sind keine unabhängigen Optionen, sondern alternative Verträge.

So macht man es richtig mit Trade-offs

Ein expliziter Diskriminator wirkt etwas ausführlicher, macht dafür Besitz und erlaubte Props eindeutig:

// SearchField.tsx – vollständige Komponenten-API
import { useId, useState } from "react";

type SharedProps = { label: string; name: string };
type ControlledProps = {
  mode: "controlled";
  value: string;
  onValueChange: (value: string) => void;
  defaultValue?: never;
};
type UncontrolledProps = {
  mode: "uncontrolled";
  defaultValue?: string;
  onValueChange?: (value: string) => void;
  value?: never;
};
type SearchFieldProps = SharedProps & (ControlledProps | UncontrolledProps);

export function SearchField(props: SearchFieldProps) {
  const id = useId();
  const [draft, setDraft] = useState(() =>
    props.mode === "uncontrolled" ? props.defaultValue ?? "" : ""
  );
  const current = props.mode === "controlled" ? props.value : draft;

  function change(next: string) {
    if (props.mode === "uncontrolled") setDraft(next);
    props.onValueChange?.(next);
  }

  return (
    <label htmlFor={id}>
      {props.label}
      <input id={id} name={props.name} value={current}
        onChange={event => change(event.target.value)} />
    </label>
  );
}

Die zugrunde liegende DOM-Eingabe bleibt in beiden Fällen technisch kontrolliert, weil current immer ein String ist. Der Unterschied liegt in der Besitzgrenze der Komponente. defaultValue wird absichtlich nur beim ersten State-Aufbau gelesen; spätere Änderungen resetten nichts. Für einen Reset kann der Parent die Komponente mit einem neuen key remounten oder den kontrollierten Modus wählen.

Der Trade-off ist API-Größe. Für eine ausschließlich formularinterne Eingabe genügt oft nur die unkontrollierte Variante; für Design-Systeme kann der explizite Modus die Klarheit wert sein. Zwei getrennte Komponenten sind eine weitere, noch strengere Alternative. In jedem Fall muss der Modus über die Lebenszeit stabil bleiben.

Textuelle Erklärung: Im kontrollierten Modus bildet der Parent mit value und onValueChange den Kreis. Im unkontrollierten Modus speist ausschließlich der interne State den aktuellen Wert. Beide Quellen sind nie gleichzeitig aktiv.

Fallstricke am Rand

  • defaultValue ist ein Initialwert, kein nachträglicher Reset-Kanal.
  • Ein kontrollierter Textwert sollte nie undefined oder null werden.
  • Wechselt mode zur Laufzeit, kann alter interner State sichtbar werden; remounte bewusst oder verbiete den Wechsel organisatorisch.
  • Label und stabile ID gehören zur Komponenten-API, nicht erst zur späteren Accessibility-Reparatur.

Selbst ausprobieren

Rendere die Komponente zweimal: einmal kontrolliert mit Parent-State, einmal unkontrolliert mit defaultValue="React". Ändere danach den Default per Button. Erwartung: Das kontrollierte Feld folgt sofort seinem Parent; das unkontrollierte behält seinen aktuellen Entwurf. Versuche anschließend, im kontrollierten Aufruf zusätzlich defaultValue zu setzen. TypeScript soll den ungültigen Vertrag bereits im Editor ablehnen. Dauer: etwa zehn Minuten.

Verwandte Themen

Redundanten State vermeiden ist dieselbe Regel innerhalb einer Komponente. Compound Components übertragen State Ownership auf komplexere APIs. Reducer helfen, wenn ein kontrollierter Wert mehrere fachliche Übergänge besitzt. useId verbindet wiederverwendbare Felder barrierefrei mit ihren Labels. Form Actions oder Form-Bibliotheken sind Alternativen, wenn feldweiser React-State gar nicht nötig ist.
