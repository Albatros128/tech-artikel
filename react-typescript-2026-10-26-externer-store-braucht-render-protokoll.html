Ein externer Store braucht ein Render-Protokoll

useState plus useEffect kann zwischen erstem Lesen und Abonnieren genau die Änderung verpassen, die das UI anzeigen soll.

26.10.2026 · React-Render-Verhalten · React 19.3 + TypeScript · Tief · ~8 min

Die Statusleiste zeigt „Online“, obwohl der Browser bereits offline ist. Erst beim nächsten Wechsel korrigiert sie sich. Listener und Cleanup sehen korrekt aus, der Dependency-Linter schweigt. Der Fehler liegt in einem kurzen Fenster: Die Komponente liest den externen Wert während des Renders, abonniert Änderungen aber erst nach dem Commit.

TL;DR

Ein externer Store braucht drei zusammengehörige Operationen: Snapshot lesen, Änderungen abonnieren und für Server Rendering einen Startwert liefern. Implementiere dieses Protokoll mit useSyncExternalStore. Ein selbst gebautes Spiegelbild aus useState und useEffect kann Updates zwischen Render und Effect verlieren und kennt ohne Zusatzlogik keine konsistente Hydration.

Prerequisites

Du kennst Hooks, Effects und Browser-Events. Die offizielle Versionsseite führt React 19.3. Das Beispiel verwendet navigator.onLine sowie die online- und offline-Events. MDN warnt, dass dieser Wert auf Heuristiken beruht: Er eignet sich als Hinweis, nicht als Beweis dafür, dass eine bestimmte API erreichbar ist.

Der Aha-Effekt

Ein Abonnement ist nicht genug. React muss wissen, welcher externe Wert zu dem Render gehört, der tatsächlich committed wird. Deshalb nimmt useSyncExternalStore getrennte Funktionen für subscribe und getSnapshot entgegen. Solange sich der Store nicht ändert, muss getSnapshot denselben Wert liefern; bei einer Änderung löst ein mit Object.is verschiedener Snapshot den Render aus.

Damit verschiebt sich die Verantwortung: Dein Adapter beschreibt nicht mehr „kopiere irgendwann den Store in React-State“, sondern „so liest und beobachtet React die externe Wahrheit“. React kann den Snapshot in kritischen Phasen erneut prüfen. Das ist besonders relevant, wenn Rendering unterbrochen oder zeitlich verschoben werden darf.

So macht man es falsch

Dieser Hook ist verbreitet und wirkt vollständig. Er besitzt Initialwert, Listener und symmetrisches Cleanup.

import { useEffect, useState } from "react";

export function useOnlineStatus(): boolean {
  const [isOnline, setIsOnline] = useState(
    () => navigator.onLine
  );

  useEffect(() => {
    const update = () => setIsOnline(navigator.onLine);

    window.addEventListener("online", update);
    window.addEventListener("offline", update);
    return () => {
      window.removeEventListener("online", update);
      window.removeEventListener("offline", update);
    };
  }, []);

  return isOnline;
}

Warum ist das falsch?

Beim ersten Render liest der Initializer beispielsweise true. Bevor React den Effect ausführt, wechselt der Browser zu false und sendet offline. Noch existiert kein Listener. Danach wird zwar abonniert, aber das vergangene Event nicht wiederholt. Der gespiegelte React-State bleibt true, bis ein weiteres Event eintrifft.

Ein zusätzlicher Aufruf von update() direkt nach dem Abonnieren verkleinert den offensichtlichen Fehler, rekonstruiert aber weiterhin ein Synchronisierungsprotokoll von Hand. Außerdem laufen Effects nicht beim Server Rendering. Für externe Stores hat React deshalb eine spezialisierte Schnittstelle, die Lesen, Subscription und Hydration gemeinsam behandelt.

So macht man es richtig mit Trade-offs

Definiere die Adapterfunktionen außerhalb der Komponente. Ihre Identität bleibt dadurch stabil und React muss nicht wegen einer neuen subscribe-Funktion erneut abonnieren.

import { useSyncExternalStore } from "react";

function subscribe(onStoreChange: () => void): () => void {
  window.addEventListener("online", onStoreChange);
  window.addEventListener("offline", onStoreChange);

  return () => {
    window.removeEventListener("online", onStoreChange);
    window.removeEventListener("offline", onStoreChange);
  };
}

function getSnapshot(): boolean {
  return navigator.onLine;
}

function getServerSnapshot(): boolean {
  return true;
}

export function useOnlineStatus(): boolean {
  return useSyncExternalStore(
    subscribe,
    getSnapshot,
    getServerSnapshot
  );
}

export function NetworkHint() {
  const isOnline = useOnlineStatus();
  return isOnline ? null : (
    <p role="status">Du scheinst offline zu sein.</p>
  );
}

Der Server-Snapshot true ist hier eine bewusste Darstellungspolitik: Der Server rendert keinen Offline-Hinweis, und derselbe Wert wird für die initiale Hydration verwendet. Danach liest React den Browser-Snapshot. Wenn deine Anwendung einen initialen Storezustand serialisiert, sollte getServerSnapshot stattdessen genau diesen übertragenen Wert liefern.

Der Trade-off ist ein strengerer Store-Vertrag. Bei einem Boolean ist der Snapshot automatisch stabil. Liefert dein Store Objekte, musst du unveränderliche Snapshots cachen und nur bei echten Änderungen ersetzen. Als Alternative bleibt React-eigener State sinnvoll, wenn React den Wert selbst besitzt: Dann kannst du State anheben, Context oder einen Reducer verwenden. useSyncExternalStore ist für Daten gedacht, deren Lebenszyklus außerhalb von React liegt.

Fallstricke am Rand

  • Erzeuge in getSnapshot nicht bei jedem Aufruf ein neues Objekt. React interpretiert eine neue Referenz als Änderung und kann eine Render-Schleife melden.
  • Wird subscribe innerhalb der Komponente neu erzeugt, kann React bei jedem Render neu abonnieren. Extrahiere die Funktion oder stabilisiere sie begründet.
  • Nutze navigator.onLine nicht, um Speichern oder Navigation hart zu sperren. Ein „online“-Wert garantiert keine erreichbare Ziel-API.

Selbst ausprobieren

Nimm dir zehn Minuten. Baue einen minimalen Store mit getSnapshot, subscribe und einer steuerbaren set-Funktion. Simuliere beim Effect-Ansatz eine Änderung zwischen initialem Lesen und Listener-Registrierung. Erwartung: Der Spiegel-State bleibt alt. Wiederhole den Ablauf als Protokoll aus „lesen, abonnieren, erneut lesen“. Erwartung: Der zweite Snapshot erkennt die Änderung. Gib danach aus getSnapshot immer ein neues Objekt zurück und beobachte die Warnung in einem React-Testprojekt.

Prüfstand: Das verlorene Änderungsfenster und die erneute Snapshot-Prüfung wurden in einem ausführbaren Zustandsmodell geprüft. React-Pakete und TypeScript-Compiler waren lokal nicht verfügbar; ein React-Integrations- oder Compile-Test wird nicht behauptet.

Verwandte Themen

External-Store-Selectoren begrenzen, welcher Snapshot eine Komponente betrifft. Hydration verlangt identische initiale Server- und Client-Snapshots. Immutable Snapshots machen Änderungen per Referenzvergleich sichtbar. Context-Ownership ist die passende Alternative für React-eigenen, baumgebundenen State.
