Compound Components brauchen einen Datenkanal, keine Kind-Manipulation

Tabs wirken flexibel, bis ein harmloser Layout-Wrapper verhindert, dass der aktive Zustand seine eigentlichen Empfänger erreicht.

29.10.2026 · React-Komponenten-APIs · React 19.3 + TypeScript 6.0 · Tief · ~9 min

Deine Tabs funktionieren im Storybook. Dann verschiebt ein Consumer die Schaltflächen in eine Toolbar und die Panels in einen responsiven Container. Das Markup ist gültig, doch kein Tab wird mehr aktiv. Die Komponente hatte ihre Daten nicht an semantische Teilnehmer verteilt, sondern an eine bestimmte Form des JSX-Baums.

TL;DR

Nutze Children.map und cloneElement nicht als verborgenes Prop-Routing für Compound Components. React traversiert dabei empfangene JSX-Knoten, nicht das später gerenderte Ergebnis innerer Komponenten. Stelle gemeinsamen Zustand und Aktionen über einen privaten Context bereit. So hängt die API an der Provider-Grenze statt an direkter Kindposition. Der Trade-off sind eine implizite Abhängigkeit und Context-bedingte Re-Renders.

Prerequisites

Du kennst children, Hooks und kontrollierten Zustand. Die Beispiele beziehen sich auf React 19.3 und TypeScript 6.0. Relevant sind die offiziellen Hinweise zu Children, cloneElement, createContext und useContext.

Der Aha-Effekt

JSX ist keine bereits gerenderte Komponentenstruktur. Ein Element wie <TabList /> ist für seinen Parent zunächst ein einzelner, opaker Knoten. Laut React-Dokumentation geht die Children-Traversal nicht tiefer als React-Elemente; deren spätere Ausgabe ist nicht enthalten. Auch Fragmente werden dabei nicht traversiert.

Eine Compound-Component-API verspricht dagegen semantische Zugehörigkeit: Jeder Tab unter demselben Tabs-Owner soll denselben aktiven Wert lesen können. Context modelliert genau diese Beziehung. Er sucht den nächstgelegenen Provider oberhalb eines Consumers, unabhängig davon, wie viele Layout-Komponenten dazwischenliegen.

So macht man es falsch

Diese Variante injiziert interne Props nur in direkte Tab-Kinder. Sie sieht kompakt aus, koppelt aber Verhalten und Layout:

import {
  Children, cloneElement, isValidElement, useState,
  type ReactElement, type ReactNode
} from "react";

type InjectedTabProps = {
  value: string;
  active?: boolean;
  onSelect?: (value: string) => void;
};

export function Tabs({ children }: { children: ReactNode }) {
  const [active, setActive] = useState("overview");

  return Children.map(children, child => {
    if (!isValidElement<InjectedTabProps>(child) || child.type !== Tab) {
      return child;
    }
    return cloneElement(child as ReactElement<InjectedTabProps>, {
      active: child.props.value === active,
      onSelect: setActive
    });
  });
}

function Tab(props: InjectedTabProps) {
  return <button onClick={() => props.onSelect?.(props.value)}>
    {props.value}
  </button>;
}

Schon <Tabs><TabList><Tab value="overview" /></TabList></Tabs> bricht den Vertrag: Tabs sieht TabList, nicht dessen Renderausgabe. Rekursive Elementinspektion löst das nicht zuverlässig, weil sie weiterhin keine Funktionskomponenten ausführt.

Warum ist das falsch?

Der Parent errät anhand von child.type, welche Elemente am Protokoll teilnehmen, und überschreibt deren Props. Dadurch wird der Datenfluss schwerer nachzuverfolgen; React bezeichnet cloneElement selbst als selten und potenziell fragil. Wrapper, Fragmente, Lazy Components oder Design-System-Abstraktionen werden zu unerwarteten API-Grenzen.

Beobachtbar sind Tabs ohne active oder Handler, obwohl sie visuell innerhalb von Tabs stehen. TypeScript kann das nicht verhindern: Der eigentliche Fehler ist eine Laufzeitannahme über Baumform, keine fehlende Property im öffentlichen Typ.

So macht man es richtig mit Trade-offs

Ein privater Context transportiert nur das gemeinsame Protokoll. Öffentliche Komponenten behalten verständliche Fach-Props; injizierte Props verschwinden aus ihrer API:

import {
  createContext, useContext, useId, useMemo, useState,
  type ReactNode
} from "react";

type TabsValue = {
  active: string;
  select: (value: string) => void;
  idBase: string;
};

const TabsContext = createContext<TabsValue | null>(null);

function useTabs(): TabsValue {
  const value = useContext(TabsContext);
  if (!value) throw new Error("Tab muss innerhalb von Tabs stehen");
  return value;
}

export function Tabs(props: { defaultValue: string; children: ReactNode }) {
  const [active, select] = useState(props.defaultValue);
  const idBase = useId();
  const value = useMemo(() => ({ active, select, idBase }), [active, idBase]);
  return <TabsContext value={value}>{props.children}</TabsContext>;
}

export function TabList({ children }: { children: ReactNode }) {
  return <div role="tablist">{children}</div>;
}

export function Tab({ value, children }: { value: string; children: ReactNode }) {
  const tabs = useTabs();
  const selected = tabs.active === value;
  return <button role="tab" aria-selected={selected}
    id={`${tabs.idBase}-tab-${value}`}
    aria-controls={`${tabs.idBase}-panel-${value}`}
    tabIndex={selected ? 0 : -1}
    onClick={() => tabs.select(value)}>{children}</button>;
}

export function TabPanel({ value, children }: { value: string; children: ReactNode }) {
  const tabs = useTabs();
  return <div role="tabpanel" hidden={tabs.active !== value}
    id={`${tabs.idBase}-panel-${value}`}
    aria-labelledby={`${tabs.idBase}-tab-${value}`}>{children}</div>;
}

In React 19 darf der Context direkt als Provider gerendert werden; ältere React-Versionen verwenden <TabsContext.Provider>. Die API bleibt nun durch Wrapper hindurch funktionsfähig. Sie hat aber eine implizite Voraussetzung: Tab muss unter Tabs stehen. Der absichtliche Fehler im Custom Hook macht diese Verletzung früh sichtbar.

Wenn Consumers den Zustand kontrollieren müssen, ergänze value und onValueChange statt eine zweite State-Quelle einzubauen. Für kleine, starre Komponenten kann explizites Prop-Passing einfacher sein. Eine Daten-Prop wie items ist die bessere Alternative, wenn die Bibliothek Reihenfolge und Rendering vollständig besitzen soll. Context aktualisiert alle lesenden Consumer bei geändertem Wert; eine Optimierung solltest du erst nach einer Messung begründen.

Fallstricke am Rand

  • Der gezeigte Ausschnitt implementiert keine Pfeiltasten-Navigation. Produktionsreife Tabs brauchen zusätzlich das vollständige Tastaturverhalten und Fokusmanagement.
  • Ein sinnvoller Context-Default fehlt absichtlich. null plus Guard verhindert, dass ein falsch platzierter Consumer scheinbar funktioniert.
  • IDs aus frei gewählten Werten können normalisiert werden müssen, wenn sie später in Selektoren oder URLs auftauchen.

Selbst ausprobieren

Nimm dir zehn Minuten. Baue beide Varianten in einer kleinen React-19.3-App. Rendere zunächst direkte Tabs, dann verschiebe sie in TabList und die Panels in eine eigene Layout-Komponente. Erwartung: Die Clone-Variante verliert ihre injizierten Props, während die Context-Variante weiter denselben aktiven Wert liest. Entferne anschließend den Provider; der Guard muss eine eindeutige Fehlermeldung auslösen.

Prüfstand: HTML-Struktur, Codeklammern, Diagrammanzahl und Quellen wurden lokal geprüft. React-Pakete und TypeScript-Compiler waren in dieser Umgebung nicht verfügbar; deshalb wird kein Integrations- oder Compile-Test behauptet.

Verwandte Themen

Kontrollierte Komponenten klären, wem der aktive Wert gehört. Reducer helfen, wenn Tabs mehr Übergänge als bloßes Auswählen besitzen. Context-Splitting trennt häufig und selten wechselnde Werte. ARIA Authoring Practices ergänzt das vollständige Tastatur- und Fokusprotokoll.
