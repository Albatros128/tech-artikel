Der zugängliche Name gehört zur Komponenten-API

Ein Test, der nur ein data-testid findet, kann grün sein, obwohl Nutzer den Button nicht finden können.

Accessibility & Tests · React 19.3 + Testing Library · Tief · ~8 min

Im Projektboard steht hinter jeder Zeile ein Papierkorb-Icon. Der Klicktest ist grün, der Lösch-Callback wird exakt einmal aufgerufen. Trotzdem meldet das Accessibility-Audit einen namenlosen Button. Der Test hat die Implementierung gefunden – nicht das Bedienelement, das ein Mensch über Tastatur oder assistive Technologie wahrnimmt.

TL;DR

Behandle Rolle und zugänglichen Namen als öffentlichen Vertrag einer interaktiven React-Komponente. Frage in Tests mit getByRole("button", { name: ... }) ab. So scheitert derselbe Test sowohl bei einer kaputten Interaktion als auch dann, wenn das Element aus dem Accessibility Tree verschwindet oder seinen Namen verliert. data-testid bleibt eine sinnvolle Ausnahme, aber kein Standard-Selektor für bedienbare UI.

Prerequisites

Du solltest React-Komponenten und Vitest oder Jest kennen. Relevant sind außerdem die Query-Priorität von Testing Library, die Semantik von getByRole und die Accessible Name and Description Computation. Der Artikel bezieht sich auf React 19.3; das Prinzip selbst stammt aus der Webplattform.

Der Aha-Effekt

Ein zugänglicher Name ist kein zusätzlicher Test-Hook. Browser leiten ihn nach einer definierten Priorität aus Textinhalt, verknüpften Labels und ARIA-Attributen ab. Genau diese Repräsentation nutzen assistive Technologien. Eine Rollenabfrage testet deshalb nicht bloß ein anderes Attribut, sondern den semantischen Ausgang deiner Komponente.

Der Testselektor und die zugängliche Bedienoberfläche können derselbe Vertrag sein. Dann wird fehlende Accessibility zu einem normalen, sichtbaren Testfehler.

So macht man es falsch

Das folgende Beispiel ist realistisch: Das Icon ist rein visuell, der Selektor stabil und der Callback korrekt. Der Button hat jedoch keinen Namen. Der Test kann diesen Defekt nicht erkennen, weil data-testid unabhängig von der Accessibility-Berechnung existiert.

// DeleteProjectButton.tsx
type Props = { onDelete: () => void };

export function DeleteProjectButton({ onDelete }: Props) {
  return (
    <button data-testid="delete-project" onClick={onDelete}>
      <svg aria-hidden="true" viewBox="0 0 24 24">…</svg>
    </button>
  );
}

// DeleteProjectButton.test.tsx
import { fireEvent, render, screen } from "@testing-library/react";
import { vi } from "vitest";
import { DeleteProjectButton } from "./DeleteProjectButton";

it("löscht das Projekt", () => {
  const onDelete = vi.fn();
  render(<DeleteProjectButton onDelete={onDelete} />);
  fireEvent.click(screen.getByTestId("delete-project"));
  expect(onDelete).toHaveBeenCalledOnce();
});

Warum ist das falsch?

Ein <button> liefert seine Rolle bereits aus nativer HTML-Semantik. Sein zugänglicher Name stammt normalerweise aus dem Text zwischen den Tags. Ein ausschließlich grafischer Inhalt, der mit aria-hidden="true" korrekt aus dem Accessibility Tree entfernt wird, hinterlässt hier aber keinen Namen. MDN nennt einen Icon-Button ausdrücklich als Fall für aria-label.

fireEvent.click beweist nur, dass ein synthetisches Click-Ereignis den Handler erreicht. Die dokumentierte Leitidee von Testing Library ist näher an echter Nutzung: semantisch auffinden, dann über user-event interagieren. Das ist kein vollständiger Screenreader-Test, aber es deckt eine wichtige gemeinsame Schnittstelle ab.

So macht man es richtig – mit Trade-offs

Der Projektname gehört in den Vertrag der Komponente. Dadurch unterscheidet der zugängliche Name mehrere Lösch-Buttons auf derselben Seite. Das Icon bleibt dekorativ; das native button-Element behält Fokus-, Tastatur- und Form-Semantik.

// DeleteProjectButton.tsx
type Props = {
  projectName: string;
  onDelete: () => void;
};

export function DeleteProjectButton({ projectName, onDelete }: Props) {
  return (
    <button
      type="button"
      aria-label={`Projekt ${projectName} löschen`}
      onClick={onDelete}
    >
      <svg aria-hidden="true" focusable="false" viewBox="0 0 24 24">
        {/* Pfade ausgelassen */}
      </svg>
    </button>
  );
}
// DeleteProjectButton.test.tsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { vi } from "vitest";
import { DeleteProjectButton } from "./DeleteProjectButton";

it("löscht das eindeutig benannte Projekt", async () => {
  const user = userEvent.setup();
  const onDelete = vi.fn();

  render(
    <DeleteProjectButton projectName="Atlas" onDelete={onDelete} />
  );

  await user.click(
    screen.getByRole("button", { name: "Projekt Atlas löschen" })
  );
  expect(onDelete).toHaveBeenCalledOnce();
});

Der Trade-off ist bewusst: Eine redaktionelle Änderung am Namen kann den Test brechen. Wenn der Name Produktverhalten ist, ist das erwünscht. Für Übersetzungen kannst du dieselbe Übersetzungsfunktion im Test nutzen oder gezielt mit einem regulären Ausdruck arbeiten. Kopiere jedoch nicht die komplette Komponentenlogik in den Test – sonst können beide gemeinsam falsch sein.

Diagramm

Fallstricke am Rand

  • Hat das Element sichtbaren Beschriftungstext, bevorzuge ihn. MDN empfiehlt aria-labelledby, wenn bereits sichtbarer Text referenziert werden kann.
  • aria-label repariert keine falsche Rolle. Ein div wird dadurch nicht zum tastaturbedienbaren Button.
  • Nutze findByRole, wenn das Element asynchron erscheint; getByRole wartet nicht.
  • data-testid bleibt passend für nicht-semantische Details, die Nutzer weder sehen noch bedienen.

Selbst ausprobieren

Plane zehn Minuten ein. Führe beide Tests zunächst grün aus. Entferne dann nur aria-label aus der verbesserten Komponente. Der Test mit getByRole soll fehlschlagen und die verfügbaren Rollen ausgeben; der alte Test mit getByTestId bleibt grün. Ergänze anschließend zwei Projekte und prüfe, dass du über den vollständigen Namen gezielt nur „Atlas“ löschst. Die erwartete Beobachtung: Semantik macht sowohl den Defekt als auch die Mehrdeutigkeit messbar.

Verwandte Themen

  • Fokusmanagement in Dialogen: Rollenabfragen finden den Dialog; ein vollständiger Vertrag umfasst zusätzlich initialen und zurückgegebenen Fokus.
  • Native Elemente vor ARIA: Semantik, Tastaturverhalten und Browserintegration entstehen gemeinsam.
  • Component Tests versus E2E: Derselbe zugängliche Name kann auf beiden Ebenen als stabiler Nutzervertrag dienen.
  • Lokalisierte Tests: Übersetzte Namen brauchen eine Strategie, die echte Copy-Regressions von bloßer Testduplizierung trennt.
