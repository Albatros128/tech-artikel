Trenne Effects nach ihrem Synchronisierungsgrund

Die Dependency-Liste kann vollständig korrekt sein – und der Effect trotzdem zwei unpassende Lebenszyklen koppeln.

React-Effects · React 19.3-Dokumentation + TypeScript · Tief · ~7 min

Dein Posteingang zeigt neue Nachrichten im Browser-Tab an. Mit jeder Nachricht steigt der Ungelesen-Zähler, gleichzeitig protokolliert der Server eine neue WebSocket-Verbindung. Der Hook hat ein Cleanup, der Dependency-Linter meldet nichts. Die Verbindung wird trotzdem immer wieder beendet, weil ihr Lebenszyklus versehentlich an den Titel gekoppelt ist.

TL;DR

Ein Effect sollte einen zusammenhängenden Synchronisierungsprozess beschreiben. Die Verbindung folgt ihrer URL, der Tab-Titel dem Zähler. Teile diese Prozesse in getrennte Effects mit vollständigen Dependencies auf. Entferne keine benötigte Dependency, nur um einen Neustart zu unterdrücken. Ändere zuerst, welche Arbeit überhaupt gemeinsam neu starten soll.

Prerequisites

Du kennst Hooks, Closures und funktionale State-Updater. Die offizielle Versionsseite führt React 19.3. Relevant sind useEffect und die Lebenszyklen reaktiver Effects. Lege jeweils eine der folgenden Varianten als useInbox.ts in ein bestehendes React-TypeScript-Projekt mit strict und DOM-Typen. Rufe den Hook in einer Komponente mit einer gültigen WebSocket-URL auf.

Das Beispiel zählt empfangene Message-Ereignisse. Es implementiert weder Nachrichtenvalidierung noch Wiederverbindung nach Netzfehlern. Außerdem setzt es voraus, dass während seiner Laufzeit nur dieser Hook den Dokumenttitel verwaltet.

Der Aha-Effekt

Ein Effect ist kein Sammelbehälter für alles, was nach einem Render passieren soll. Er formuliert einen Start-Stopp-Vertrag mit einem externen System. Die React-Dokumentation empfiehlt, unabhängig synchronisierbare Prozesse zu trennen. Ein Hook darf deshalb mehrere Effects besitzen, obwohl er fachlich nur einen Posteingang anbietet.

Meine Designprobe lautet: Sollte Prozess A weiterlaufen, wenn ausschließlich die Eingabe von Prozess B wechselt? Falls ja, sollten beide nicht denselben Neustart teilen. Ein steigender Zähler verändert den Tab-Titel, aber nicht die Identität des Nachrichtenkanals.

So macht man es falsch

Die gemeinsame Umsetzung wirkt kompakt. Sie benötigt tatsächlich sowohl url als auch unread, also ist die Dependency-Liste korrekt. Genau diese Korrektheit macht die unerwünschte Kopplung sichtbar.

import { useEffect, useState } from "react";

export function useInbox(url: string) {
  const [unread, setUnread] = useState(0);

  useEffect(() => {
    const previousTitle = document.title;
    const socket = new WebSocket(url);
    const onMessage = () => setUnread(count => count + 1);
    socket.addEventListener("message", onMessage);
    document.title = `Posteingang (${unread})`;

    return () => {
      socket.removeEventListener("message", onMessage);
      socket.close();
      document.title = previousTitle;
    };
  }, [url, unread]);

  return { unread, markRead: () => setUnread(0) };
}

Warum ist das falsch?

Nach einer Nachricht fordert der funktionale Updater einen neuen Zählerstand an. React vergleicht Dependencies mit Object.is. Wenn sich unread geändert hat, führt React zuerst das bisherige Cleanup und dann das neue Setup aus. Hier entfernt das Cleanup den Listener und initiiert mit close() das Schließen der bisherigen Verbindung. Danach entsteht ein neues Socket-Objekt.

Beobachtbare Symptome sind wiederholte Verbindungsaufbauten trotz unveränderter URL und derselbe Effekt beim „Als gelesen markieren“. Ob dabei Nachrichten fehlen, hängt vom Zustell- und Wiederaufnahmeprotokoll ab; das folgt nicht automatisch aus dem Reconnect. Die Ursache ist keine zu großzügige React-Reaktivität, sondern eine gemeinsame Neustartgrenze für unabhängige Arbeit.

So macht man es richtig mit Trade-offs

Der Socket-Effect liest den Zähler nicht. Sein Handler beschreibt nur eine Transformation des dann gültigen States. Der zweite Effect schreibt den Dokumenttitel und stellt seinen vorherigen Wert beim Cleanup wieder her.

import { useEffect, useState } from "react";

export function useInbox(url: string) {
  const [unread, setUnread] = useState(0);

  useEffect(() => {
    const socket = new WebSocket(url);
    const onMessage = () => setUnread(count => count + 1);
    socket.addEventListener("message", onMessage);

    return () => {
      socket.removeEventListener("message", onMessage);
      socket.close();
    };
  }, [url]);

  useEffect(() => {
    const previousTitle = document.title;
    document.title = `Posteingang (${unread})`;
    return () => { document.title = previousTitle; };
  }, [unread]);

  return { unread, markRead: () => setUnread(0) };
}

Jetzt erneuert ein Zählerwechsel nur die Titel-Synchronisierung. Ein URL-Wechsel beendet den alten Kanal und öffnet den neuen. Es wurde keine Dependency versteckt; die geänderte Struktur benötigt weniger gemeinsame Eingaben. Das React-Kapitel zum Entfernen von Effect-Dependencies beschreibt diese Trennung ausdrücklich als eigenständige Synchronisierungsprozesse.

Der Trade-off ist mehr Struktur statt eines kurzen Sammel-Effects. Trenne deshalb nicht jede einzelne Anweisung: Listener-Registrierung und Socket-Cleanup gehören zusammen, weil sie dieselbe Ressource verwalten. Sollen zwei Schritte immer gemeinsam beginnen und enden, ist ein gemeinsamer Effect weiterhin passend.

Als Alternative kann ein übergeordneter Verbindungsdienst den Socket besitzen, wenn mehrere Ansichten denselben Kanal teilen müssen. Dann verwaltet der Hook nur ein Abonnement. Das verschiebt Ownership, Fehlerpolitik und Lebenszeit in eine zusätzliche Abstraktion; für eine einzelne Ansicht ist das nicht automatisch besser. Einen neuen Ref oder Memo-Wrapper brauchst du für die gezeigte Trennung nicht.

Diagramm

Fallstricke am Rand

  • Strict Mode kann in der Entwicklung einen zusätzlichen Setup-Cleanup-Zyklus ausführen. Prüfe danach die Reaktion auf Zähleränderungen, statt den initialen Zusatzzyklus mit diesem Fehler zu verwechseln.
  • Ein gemeinsam genutzter Dokumenttitel braucht einen zentralen Besitzer. Unabhängige Hooks können sonst gegenseitig ihre Wiederherstellung überschreiben.
  • Der Zähler zählt hier seit Mount, auch über URL-Wechsel hinweg. Ein kanalbezogener Zähler benötigt eine ausdrückliche Reset- oder Datenmodell-Entscheidung.

Selbst ausprobieren

Nimm dir zehn Minuten. Zähle Socket-Konstruktionen und Close-Aufrufe in einem Test-Double. Simuliere Setup, ein Message-Ereignis und das anschließende Effect-Update. Erwartung: Die Fehlervariante konstruiert ein zweites Socket; die getrennte Variante behält das erste. Ändere danach die URL: Jetzt muss auch die verbesserte Variante wechseln. Prüfe beim abschließenden Cleanup, dass alle Listener entfernt und der ursprüngliche Titel wiederhergestellt sind.

Prüfstand: Dieser Ablauf wurde mit den gezeigten Hook-Bodies in einem Node-Lebenszyklusmodell geprüft. Das ist kein React-Integrationstest und simuliert keinen WebSocket-Handshake. React-Pakete und TypeScript-Compiler waren lokal nicht verfügbar; ein bestandener Compile- oder Browser-Test wird nicht behauptet.

Verwandte Themen

Effect-Ownership klärt, welche Ansicht eine Ressource wirklich besitzen soll. Abonnement-Tests prüfen Setup und symmetrisches Cleanup gemeinsam. Funktionale Updater vermeiden, dass ein Event-Handler den aktuellen Zähler selbst lesen muss.
