Ein Conditional Type prüft nicht automatisch die ganze Union

„Jedes Mitglied einzeln transformieren“ und „alle Mitglieder gemeinsam zulassen“ sind zwei verschiedene Verträge.

TypeScript-Typsystem · Conditional Types seit TypeScript 2.8 · Tief · ~7 min

Dein Frontend bündelt erzeugte und gelöschte Dokumente zu einem Event-Batch. Einzelne Event-Arten funktionieren, doch die gemischte Liste passt plötzlich nicht mehr zum Hilfstyp. Du ergänzt keine Laufzeitprüfung und keinen Cast: Zuerst musst du herausfinden, ob der Typ wirklich einen Batch von Events beschreibt – oder eine Union sortenreiner Batches.

TL;DR

Ein Conditional Type mit einem alleinstehenden Typparameter links von extends verteilt sich über Union-Mitglieder. Aus T[] kann dadurch eine Union mehrerer Array-Typen werden. Willst du die gesamte Union auf Zuweisbarkeit prüfen und anschließend genau ein Array modellieren, verwende [T] extends [Erlaubt]. Entscheide nach dem Vertrag, nicht nach einem reflexhaften Tuple-Trick.

Prerequisites

Du solltest Generics, Unions und never kennen. Die Release Notes zu TypeScript 2.8 beschreiben die Verteilung über einen „naked type parameter“. Das aktuelle Handbook zu Conditional Types zeigt auch die nichtdistributive Tuple-Variante. Die folgenden Blöcke gehören gemeinsam in batch.ts; Imports und Runtime-Bibliotheken sind nicht nötig.

Der Aha-Effekt

Eine Union ist hier nicht bloß ein Argument, das einmal in eine Bedingung eingesetzt wird. Bei einem distributiven Hilfstyp wird die Operation für jedes Mitglied ausgewertet; danach werden die Ergebnisse wieder vereinigt. Die Position der Array-Hülle entscheidet deshalb, ob ein Container verschiedene Event-Arten aufnehmen darf oder sich auf eine Art festlegt.

Meine Designfolgerung: Schreibe vor einem komplexeren Typ-Helfer einen gültigen gemischten Wert und einen unzulässigen Typfall auf. Diese beiden Beispiele zwingen dich, zwischen Transformation einzelner Varianten und einer Bedingung über den Gesamtvertrag zu unterscheiden.

So macht man es falsch

Der Name BrokenBatch soll einen Batch beliebiger erlaubter Events versprechen. Seine Definition liefert aber für jede Event-Art ein eigenes Array. Die Variablen im Beispiel vermeiden, dass Literal-Inferenz den eigentlichen Unterschied verdeckt.

type Created = { kind: "created"; id: string; title: string };
type Deleted = { kind: "deleted"; id: string };
type DomainEvent = Created | Deleted;
type Internal = { kind: "internal"; diagnostic: string };

type BrokenBatch<T> =
  T extends DomainEvent ? readonly T[] : never;

const created: Created = { kind: "created", id: "a", title: "Plan" };
const deleted: Deleted = { kind: "deleted", id: "b" };
const mixedItems: readonly DomainEvent[] = [created, deleted];

// @ts-expect-error: Der Hilfstyp verlangt sortenreine Arrays.
const rejected: BrokenBatch<DomainEvent> = mixedItems;

type Unexpected = BrokenBatch<Created | Internal>;
// readonly Created[] – Internal verschwindet aus dem Ergebnis.

Warum ist das falsch?

Für DomainEvent wird die Bedingung separat auf Created und Deleted angewendet. Das Ergebnis lautet readonly Created[] | readonly Deleted[], nicht readonly (Created | Deleted)[]. Eine Liste mit beiden Varianten erfüllt keinen der beiden sortenreinen Zweige.

Noch tückischer ist der zweite Typfall: Das erlaubte Mitglied ergibt ein Array, das unerlaubte ergibt never. In der Ergebnisunion bleibt nur der erlaubte Teil übrig. Diese Mechanik ist als Filter sinnvoll; als Prüfung „dieser ganze Typ ist erlaubt“ beantwortet sie die falsche Frage. Das ist ausschließlich eine Typberechnung: Zur Laufzeit wird dadurch kein Objekt aus einer Liste entfernt.

So macht man es richtig mit Trade-offs

Die Tuple-Hülle verhindert die Verteilung. Jetzt muss der gesamte Eingabetyp zum erlaubten Event-Typ passen; erst danach entsteht das Array. Die Klammern erzeugen kein Runtime-Tuple.

type Batch<T> =
  [T] extends [DomainEvent] ? readonly T[] : never;

const accepted: Batch<DomainEvent> = mixedItems;

// @ts-expect-error: Die gesamte Union ist nicht erlaubt.
const invalid: Batch<Created | Internal> = [created];

// Kleine Typ-Assertions für denselben Vertrag:
type Same<A, B> =
  [A] extends [B] ? ([B] extends [A] ? true : false) : false;
type Expect<T extends true> = T;

type MixedIsAllowed = Expect<
  Same<Batch<DomainEvent>, readonly DomainEvent[]>
>;
type InvalidUnionIsRejected = Expect<
  Same<Batch<Created | Internal>, never>
>;

Der Trade-off: Du verlierst bewusst die Filterwirkung. Wenn ein Typ-Helfer exportierbare Varianten aus einer größeren Union auswählen soll, wäre diese Änderung falsch. Extract beziehungsweise Exclude drücken solche mitgliedsweisen Auswahloperationen bereits aus.

Für einen einfachen Batch ist sogar eine Generic-Constraint klarer. Sie meldet einen unzulässigen Typparameter direkt, statt als Ergebnis never zu liefern:

// Alternative, wenn kein bedingtes Ergebnis benötigt wird:
type DirectBatch<T extends DomainEvent> = readonly T[];
const direct: DirectBatch<DomainEvent> = mixedItems;

// @ts-expect-error: Internal verletzt die Constraint.
type InvalidDirect = DirectBatch<Created | Internal>;

Die Conditional-Variante lohnt sich vor allem beim Zusammensetzen von Typfunktionen, die mit einem never-Ergebnis weiterrechnen. An einer öffentlichen API ist ein früher Constraint-Fehler oft verständlicher. Keine Variante ersetzt die Validierung unbekannter JSON-Events.

Fallstricke am Rand

  • Die Verteilung hängt vom alleinstehenden Typparameter ab. Eine ausgeschriebene konkrete Union links von extends verteilt sich nicht automatisch.
  • never verdient einen eigenen Test: Die distributive Variante ergibt hier never, die gezeigte nichtdistributive Variante readonly never[].
  • Die gezeigten Typ-Assertions sind für diese konkreten Typen gedacht, kein universeller Gleichheitstest für any und alle TypeScript-Sonderfälle.

Selbst ausprobieren

Plane zehn Minuten im TypeScript Playground mit strict ein. Vergleiche die Typanzeigen beider Batch-Helfer. Entferne die @ts-expect-error-Kommentare einzeln: Erwartet sind Fehler am gemischten BrokenBatch und an den beiden unzulässigen Gesamtverträgen. Ergänze danach Batch<never> und entscheide ausdrücklich, ob ein leerer Array-Typ in deiner Typfunktion sinnvoll ist.

Prüfstand: HTML-Struktur und Beispielaufbau wurden kontrolliert. Lokal war kein TypeScript-Compiler verfügbar; die angegebenen Typ-Assertions wurden deshalb nicht als bestandener Compile-Test gewertet. Ein Laufzeittest könnte diese rein statische Unterscheidung nicht bestätigen.

Verwandte Themen

Union-Filter nutzen die Verteilung absichtlich, um Varianten auszuwählen. API-Fehlermeldungen entscheiden, ob ein Constraint oder ein never-Ergebnis Verbrauchern besser hilft. Exhaustive Checks geben never eine andere Aufgabe: unerreichbare Restfälle sichtbar machen.
