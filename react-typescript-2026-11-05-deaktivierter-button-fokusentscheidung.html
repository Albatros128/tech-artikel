Ein deaktivierter Button braucht eine bewusste Fokusentscheidung

disabled und aria-disabled beschreiben nicht nur einen Zustand, sondern zwei verschiedene Interaktionsverträge.

05.11.2026 · Accessibility & Komponenten-APIs · React 19.3 / WAI-ARIA 1.2 · Tief · ~8 min

Im Veröffentlichungsdialog bleibt der primäre Button grau, bis Titel, Freigabe und Zielgruppe vollständig sind. Mit der Maus erscheint über title ein Hinweis. Wer jedoch per Tab navigiert, überspringt den Button und erfährt nicht, welche Bedingung noch fehlt. Technisch ist die Aktion deaktiviert; fachlich ist ihre Unerreichbarkeit das eigentliche Problem.

TL;DR

Nutze natives disabled, wenn ein Form-Control wirklich aus Bedienung, Fokusreihenfolge und Formularübermittlung verschwinden soll. Soll eine wichtige, momentan nicht ausführbare Aktion auffindbar bleiben, verwende auf dem nativen <button> bewusst aria-disabled="true", eine sichtbare und über aria-describedby verknüpfte Begründung sowie einen Handler, der die Aktion tatsächlich verhindert. ARIA liefert Semantik, nicht Verhalten.

Prerequisites

Du kennst React-Eventhandler, semantisches HTML und discriminated unions. Das Beispiel bezieht sich auf React 19.3 und die normative WAI-ARIA-1.2-Definition von aria-disabled. Die Unterschiede zum nativen Attribut dokumentiert außerdem MDN zu disabled.

Der Aha-Effekt

„Kann nicht aktiviert werden“ ist nur eine Hälfte der Entscheidung. Die andere lautet: „Soll diese Aktion beim Erkunden der Oberfläche gefunden werden?“ Ein natives deaktiviertes Form-Control ist nicht fokussierbar und wird nicht mit dem Formular übertragen. aria-disabled meldet Assistenztechnik lediglich den deaktivierten Zustand; es entfernt den Button weder aus der Fokusreihenfolge noch unterbindet es Klicks.

Damit wird die Wahl zu einer Produktentscheidung. Ein „Speichern“-Button während eines bereits laufenden Saves darf oft vollständig aus der Interaktion fallen. Ein „Veröffentlichen“-Button, dessen Voraussetzungen der Nutzer noch erfüllen muss, sollte dagegen auffindbar sein und den Grund erklären.

So macht man es falsch

Die verbreitete Kombination aus nativem disabled und title wirkt plausibel, macht die Erklärung aber von einem Element abhängig, das per Tastatur keinen Fokus erhält:

import type { ReactElement } from "react";

type PublishButtonProps = {
  canPublish: boolean;
  onPublish: () => void;
};

export function PublishButton({
  canPublish,
  onPublish,
}: PublishButtonProps): ReactElement {
  const reason = "Titel und Zielgruppe fehlen noch";

  return (
    <button
      type="button"
      disabled={!canPublish}
      title={!canPublish ? reason : undefined}
      onClick={onPublish}
    >
      Veröffentlichen
    </button>
  );
}

Warum ist das falsch?

Für das Verhindern der Aktion ist der Code korrekt: Der Browser übernimmt Semantik und Verhalten. Falsch ist die Annahme, der Button könne zugleich als fokussierbarer Träger seiner Erklärung dienen. Das native Attribut entfernt ihn aus der Tab-Reihenfolge; eine reine Hover-Erklärung erreicht Tastaturnutzer nicht zuverlässig.

Das Symptom zeigt sich nicht als Exception, sondern als Informationslücke: Der Fokus springt vom letzten Eingabefeld zur nächsten Aktion. Die zentrale Schaltfläche und ihr Grund bleiben unsichtbar. Ein Wrapper mit Tooltip verschiebt das Problem häufig nur, weil dann der Wrapper fokussierbar und benannt werden müsste.

So macht man es richtig mit Trade-offs

Die Komponenten-API modelliert Verfügbarkeit und Grund als Union. Dadurch kann ein nicht verfügbarer Zustand nicht ohne Erklärung erzeugt werden. Der sichtbare Text ist zugleich die zugängliche Beschreibung:

import { useId, type ReactElement } from "react";

type PublishState =
  | { status: "ready"; onPublish: () => void }
  | { status: "unavailable"; reason: string };

export function PublishButton({ state }: { state: PublishState }): ReactElement {
  const reasonId = useId();
  const unavailable = state.status === "unavailable";

  function handleClick(): void {
    if (state.status === "unavailable") return;
    state.onPublish();
  }

  return (
    <div>
      <button
        type="button"
        aria-disabled={unavailable || undefined}
        aria-describedby={unavailable ? reasonId : undefined}
        onClick={handleClick}
      >
        Veröffentlichen
      </button>
      {state.status === "unavailable" && (
        <p id={reasonId}>{state.reason}</p>
      )}
    </div>
  );
}

Die Guard Clause ist zwingend: aria-disabled ändert nur die Accessibility-Semantik. Der native Button bleibt fokussierbar und erzeugt bei Maus- oder Tastaturaktivierung weiterhin ein Click-Ereignis. Style den Zustand zusätzlich mit [aria-disabled="true"], aber entferne nicht einfach per pointer-events: none nur einen Eingabepfad.

Der Trade-off ist mehr Verantwortung: Verhalten, Darstellung und Tests liegen bei deiner Komponente. Wenn die Aktion nicht erklärt oder entdeckt werden muss, ist natives disabled robuster. Für mehrere zusammenhängende Form-Controls kann ein deaktiviertes <fieldset> die semantisch bessere Alternative sein.

Diagramm

Fallstricke am Rand

  • Setze aria-disabled nicht unbedacht auf Container: Der Zustand gilt semantisch auch für fokussierbare Nachfahren.
  • Verwende weiterhin ein echtes <button>; ein <div role="button"> erzeugt zusätzliche Tastatur- und Fokusarbeit.
  • Eine Beschreibung erklärt den Zustand, ersetzt aber keine sichtbare Validierung an den verursachenden Feldern.

Selbst ausprobieren

Rendere beide Varianten nebeneinander, setze den Status auf nicht verfügbar und navigiere fünf Minuten lang ausschließlich mit Tab und Enter. Erwartung: Das native disabled wird übersprungen. Die ARIA-Variante erhält Fokus, bleibt bei Enter wirkungslos und verweist über aria-describedby auf den sichtbaren Grund. Teste danach den Ready-Zustand: Der Handler darf genau einmal laufen.

Prüfstand: HTML-Struktur, Diagrammanzahl, Codeklammern und die Zustands-Guard wurden lokal geprüft. Ein Browser-/Screenreader-Integrationstest oder TypeScript-Compile-Test war lokal nicht verfügbar und wird nicht behauptet.

Verwandte Themen

Zugängliche Beschreibungen ergänzen Namen um Kontext. Fokusmanagement entscheidet, was per Tastatur erkundbar ist. Formularvalidierung verankert Ursachen an Feldern statt nur am Submit-Button. Discriminated unions machen unvollständige Komponenten-Zustände unformulierbar.
