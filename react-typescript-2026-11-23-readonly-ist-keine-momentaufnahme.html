Readonly beschreibt Zugriff, nicht Besitz

Langlebige Caches brauchen eine Momentaufnahme – eine schreibgeschützte Sicht reicht nicht.

TypeScript-Typsystem · TypeScript 6.0 + ECMAScript 2025 · Tief · ~8 min

Ein Warenkorb wird an einen Preis-Cache übergeben. Der Parameter heißt Readonly<Cart>, also scheint der Cache vor späteren Änderungen geschützt. Minuten danach ändert die Oberfläche die Menge eines Artikels. Plötzlich liefert derselbe Cache-Eintrag andere Positionen, obwohl sein gespeicherter Gesamtpreis unverändert blieb. Der Typ war korrekt – nur das Besitzmodell war falsch.

TL;DR

Readonly<T> verbietet Zuweisungen über diesen typisierten Zugriffspfad. Es erzeugt weder eine Kopie noch Runtime-Schutz und ist nur flach. Wenn eine Funktion Daten länger aufbewahrt als der Aufruf dauert, muss sie entscheiden: Speichert sie eine live veränderliche Sicht oder übernimmt sie eine Momentaufnahme? Für einen Snapshot kopierst du an der Besitzgrenze die relevanten Ebenen; Object.freeze kann zusätzlich Runtime-Schreibversuche sichtbar machen, bleibt aber ebenfalls flach.

Prerequisites

Du solltest strukturelle Typisierung, Objekt-Aliase und Utility Types kennen. Das TypeScript-Handbuch dokumentiert, dass Readonly<T> Properties auf readonly setzt. Entscheidend ist der ergänzende Hinweis zu readonly-Properties und Aliasing: Der Modifier ändert kein Runtime-Verhalten, und kompatible veränderliche Aliase können dasselbe Objekt weiterhin verändern. Der Versionsbezug ist TypeScript 6.0.

Der Aha-Effekt

readonly ist eine Fähigkeitseinschränkung des Betrachters, keine Eigenschaft des betrachteten JavaScript-Objekts. Zwei Variablen können auf dieselbe Identität zeigen: Eine erlaubt Schreiben, die andere nicht. Der Compiler prüft nur den jeweiligen Pfad. Deshalb ist Readonly<T> hervorragend für lokale API-Absichten, aber kein Beleg dafür, dass ein gespeicherter Wert zeitlich stabil bleibt.

Die Designfrage lautet nicht: „Darf diese Funktion mutieren?“ Sondern: „Darf eine andere Stelle die Daten verändern, während diese Funktion sie aufbewahrt?“

So macht man es falsch

Der Cache akzeptiert eine schreibgeschützte Sicht, speichert aber dieselbe Referenz. Außerdem schützt das Utility Type nur die oberste Ebene: Das Array und seine Artikel bleiben über andere Aliase veränderlich.

// Vollständiges TypeScript-Modul; keine Imports erforderlich.
type CartItem = { sku: string; quantity: number; unitPrice: number };
type Cart = { customerId: string; items: CartItem[] };
type Quote = { cart: Readonly<Cart>; total: number };

const quotes = new Map<string, Quote>();

function rememberQuote(cart: Readonly<Cart>): void {
  const total = cart.items.reduce(
    (sum, item) => sum + item.quantity * item.unitPrice,
    0,
  );
  quotes.set(cart.customerId, { cart, total });
}

const cart: Cart = {
  customerId: "c-17",
  items: [{ sku: "A", quantity: 1, unitPrice: 20 }],
};

rememberQuote(cart);
cart.items[0].quantity = 3; // erlaubt: veränderlicher Alias

// Gespeicherte Position sagt 60, gespeicherter total bleibt 20.

Warum ist das falsch?

Beim Aufruf wird kein neues Objekt erzeugt. cart und quote.cart zeigen auf dieselbe Objektgrafik. TypeScript entfernt Typen beim Emit; der JavaScript-Heap kennt den Modifier nicht. Selbst ein eigenes DeepReadonly würde nur weitere Schreibpfade im TypeScript-Code sperren, aber weiterhin weder kopieren noch fremde JavaScript-Aufrufer, Typumgehungen oder bereits vorhandene veränderliche Aliase kontrollieren.

Die Symptome sind kausal: Der Cache speichert einen berechneten Wert und eine live veränderliche Eingabe unter derselben semantischen Annahme „Quote“. Das Objekt kann dadurch intern widersprüchlich werden. Der Fehler hängt nicht von Last ab und ist keine Performancefrage; er entsteht bereits bei einem einzigen Alias.

So macht man es richtig

Eine Quote ist ein historischer Wert. Die Cache-Grenze übernimmt deshalb eine domänenspezifische Momentaufnahme. Kopiere genau die Ebenen, deren spätere Änderung die Aussage der Quote verändern würde, und drücke die neue Besitzlage anschließend mit readonly-Typen aus.

type CartItemSnapshot = Readonly<CartItem>;
type CartSnapshot = Readonly<{
  customerId: string;
  items: readonly CartItemSnapshot[];
}>;
type Quote = Readonly<{ cart: CartSnapshot; total: number }>;

function snapshotCart(cart: Cart): CartSnapshot {
  return {
    customerId: cart.customerId,
    items: cart.items.map(item => ({ ...item })),
  };
}

function rememberQuote(cart: Cart): void {
  const snapshot = snapshotCart(cart);
  const total = snapshot.items.reduce(
    (sum, item) => sum + item.quantity * item.unitPrice,
    0,
  );
  quotes.set(snapshot.customerId, { cart: snapshot, total });
}

Der Preis ist zusätzlicher Speicher und das Kopieren kostet proportional zur Zahl der Positionen. Dafür besitzt der Cache eine stabile Aussage. Alternative: Speichere nur normalisierte primitive Felder oder serialisiere am Rand. structuredClone ist für kompatible Daten bequem, kopiert aber bewusst nach Plattformregeln und ersetzt keine Domänenentscheidung. Object.freeze verhindert Änderungen am eingefrorenen Objekt zur Laufzeit, ist jedoch flach; rekursives Einfrieren kostet Traversierung und kann bei fremden Objektgraphen unerwünscht sein.

    C --> D[Spätere Mutation verändert Cache-Daten]
    B -- ja --> E[Domänensnapshot mit neuen Identitäten]

Textliche Erklärung: Ohne Kopie bleibt der Cache an die veränderliche Identität des Aufrufers gekoppelt. Erst neue Identitäten an der Besitzgrenze machen die gespeicherte Quote zu einer Momentaufnahme.

Fallstricke am Rand

  • Readonly<T> ist flach; verschachtelte Arrays und Objekte brauchen eigene readonly-Typen.
  • Ein Spread kopiert ebenfalls nur eine Ebene. Die benötigte Tiefe folgt der Domäne, nicht einem universellen Rezept.
  • Getter, Klasseninstanzen, Maps und zyklische Graphen verlangen eine bewusste Snapshot-Strategie.

Selbst ausprobieren

Führe das erste Beispiel in fünf Minuten aus und protokolliere nach der Mutation quotes.get("c-17"). Erwartung: total ist 20, die gespeicherte Position berechnet inzwischen 60. Ersetze anschließend die Referenz durch snapshotCart(cart). Die Mutation am ursprünglichen Warenkorb verändert den Cache nicht mehr. Ergänze testweise nur Object.freeze(cart): Die verschachtelte Menge bleibt änderbar und demonstriert den flachen Runtime-Schutz.

Verwandte Themen

  • Defensive Copies: Sie machen Besitzübertragung explizit, besonders an Modul- und Worker-Grenzen.
  • Strukturelle Gleichheit: Snapshots erleichtern Vergleiche nur, wenn ihre Identitätsstrategie konsistent ist.
  • Serialisierung: JSON kann einen Snapshot erzeugen, verliert aber Typen und besondere JavaScript-Werte.
  • Persistente Datenstrukturen: Sie teilen unveränderte Teilbäume und tauschen Implementierungskomplexität gegen günstigere Versionierung.
