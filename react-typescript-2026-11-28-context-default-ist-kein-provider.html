Ein Context-Default ersetzt keinen Provider

Wenn Infrastruktur verpflichtend ist, darf ihr Fehlen nicht wie ein gültiger Anwendungszustand aussehen.

React-Context & State-Modellierung · React 19.3 + TypeScript 6.0 · Tief · ~8 min

Nach einer Router-Umstellung verschwindet in einem Teilbaum der „Speichern“-Button. Es gibt keinen Fehler, keinen fehlgeschlagenen Test und keinen auffälligen Logeintrag. Die Komponente hängt außerhalb des Berechtigungs-Providers und liest deshalb den freundlichen Context-Default: einen anonymen Benutzer, der nichts bearbeiten darf. Die Oberfläche reagiert konsistent – auf eine Konfiguration, die niemals gültig sein sollte.

TL;DR

Der Wert in createContext(defaultValue) ist kein initialer Provider-State. React verwendet ihn nur, wenn oberhalb des Consumers kein passender Provider existiert; er bleibt statisch. Für optionale Semantik wie ein Standardfarbschema kann das sinnvoll sein. Bei verpflichtender Infrastruktur – Authentifizierung, Berechtigungen, Query-Client oder Router – maskiert ein Dummy-Objekt dagegen einen Strukturfehler. Nutze null als Sentinel und entferne ihn in einem eigenen Hook durch eine Laufzeitprüfung. So wird ein fehlender Provider am ersten Zugriff sichtbar.

Prerequisites

Du solltest Context, Hooks und TypeScript-Unions kennen. Die aktuelle React-Dokumentation zu createContext bezeichnet den Default als statischen „last resort“-Fallback und empfiehlt null, wenn kein sinnvoller Default existiert. React: Using TypeScript zeigt den prüfenden Consumer-Hook. Versionsbezug sind React 19.3 und TypeScript 6.0.

Der Aha-Effekt

Ein Default entscheidet über die Fehlersemantik deiner Komponenten-API. Mit einem Dummy-Wert sagt die API: „Dieser Consumer funktioniert auch ohne Provider.“ Mit null und Guard sagt sie: „Der Provider ist Teil der Vorbedingung.“ Das ist keine Geschmacksfrage, sondern eine Modellierungsentscheidung zwischen gültigem Fallback und verletzter Baumstruktur.

Die zentrale Entscheidung: Verwende einen nicht-null Default nur, wenn das Verhalten ohne Provider fachlich vollständig und dauerhaft gültig ist.

So macht man es falsch

Der Dummy erleichtert isolierte Tests, weil keine Hülle nötig ist. Gleichzeitig kann Produktionscode denselben Pfad versehentlich nehmen. Das No-op-Verhalten verschluckt die Ursache und zeigt lediglich deren Folge.

// access-context.tsx – problematische, aber lauffähige API
import { createContext, useContext } from "react";

type Access = {
  userId: string;
  canEdit(documentId: string): boolean;
};

const AccessContext = createContext<Access>({
  userId: "anonymous",
  canEdit: () => false,
});

export function SaveButton({ documentId }: { documentId: string }) {
  const access = useContext(AccessContext);
  if (!access.canEdit(documentId)) return null;
  return <button type="button">Speichern</button>;
}

// Ein fehlender Provider kompiliert und rendert kommentarlos null.
export function DetachedPanel() {
  return <SaveButton documentId="contract-42" />;
}

Warum ist das falsch?

React sucht den nächsten Provider oberhalb des Consumers. Findet es keinen, liefert useContext exakt den beim Erzeugen angegebenen Default. Der Wert wird nicht zu einem Provider, erhält keine Updates und beweist nicht, dass der Teilbaum korrekt verdrahtet ist. Ein Test, der nur die Abwesenheit des Buttons erwartet, bestätigt daher aus Versehen den Fehlerpfad.

Auch ein Default mit Funktionen, die werfen, ist nur eine verstreute Teilreparatur: Jeder Zugriff muss die richtige Funktion treffen. Ein Consumer, der ausschließlich userId liest, bleibt unbemerkt. Die Vorbedingung gehört an eine einzige Zugriffsstelle.

So macht man es richtig mit Trade-offs

Der Context bildet die Realität als Access | null ab. Der öffentliche Hook prüft sie einmal und gibt danach den präzisen Typ Access zurück. Consumer importieren den Hook, nicht den rohen Context.

// access-context.tsx – vollständiger React-19.3-Ausschnitt
import {
  createContext,
  useContext,
  type ReactNode,
} from "react";

export type Access = {
  userId: string;
  canEdit(documentId: string): boolean;
};

const AccessContext = createContext<Access | null>(null);

export function AccessProvider({
  value,
  children,
}: {
  value: Access;
  children: ReactNode;
}) {
  return <AccessContext value={value}>{children}</AccessContext>;
}

export function useAccess(): Access {
  const value = useContext(AccessContext);
  if (value === null) {
    throw new Error("useAccess benötigt einen AccessProvider");
  }
  return value;
}

export function SaveButton({ documentId }: { documentId: string }) {
  const access = useAccess();
  if (!access.canEdit(documentId)) return null;
  return <button type="button">Speichern</button>;
}

Der Trade-off ist bewusst laut: Storybook-Stories und Tests müssen einen Provider setzen oder den Fehler ausdrücklich erwarten. Dafür testen sie denselben Vertrag wie die Anwendung. Eine Alternative sind Props; für wiederverwendbare Blätter machen sie Abhängigkeiten sichtbarer und vermeiden globalen Baumzustand. Ein echter Default bleibt sinnvoll, wenn „ohne Provider“ eine vollständige Semantik besitzt – etwa ein optionales Farbschema "system". Dann ist Fail-fast nicht automatisch besser.

Diagramm

flowchart TD
    A[Consumer ruft Hook] --> B{Provider oberhalb?}
    B -- ja --> C[bereitgestellter Wert]
    B -- nein --> D[statischer Default null]
    D --> E[Guard meldet Strukturfehler]

Textliche Erklärung: Der Consumer erhält entweder den Wert des nächsten Providers oder den statischen Default. Der Null-Guard verwandelt den zweiten Pfad sofort in einen benannten Architekturfehler.

Fallstricke am Rand

  • Ein vorhandener Provider mit value={undefined} aktiviert den Default nicht; React liefert undefined.
  • Der Provider muss oberhalb des aufrufenden Consumers stehen. Ein Provider, den dieselbe Komponente erst zurückgibt, beeinflusst ihren eigenen Hook-Aufruf nicht.
  • Exportiere den Context nur, wenn externe Provider wirklich Teil der API sein sollen; sonst bleibt der Guard leicht umgehbar.

Selbst ausprobieren

Rendere in fünf bis zehn Minuten SaveButton einmal innerhalb und einmal außerhalb von AccessProvider. Mit dem Dummy-Default verschwindet der zweite Button still. Mit dem Null-Sentinel soll der zweite Render die benannte Fehlermeldung erzeugen. Ergänze anschließend einen Error-Boundary-Test oder einen Test-Helper, der bewusst einen Access-Wert bereitstellt.

Verwandte Themen

  • Provider-Lebenszeit: Seine Position bestimmt, wann Context-State erhalten bleibt oder zurückgesetzt wird.
  • Error Boundaries: Sie können den fail-fast Fehler an einer fachlich sinnvollen Grenze darstellen.
  • Dependency Injection über Props: Explizite Abhängigkeiten verbessern die Wiederverwendbarkeit kleiner Komponenten.
  • Context-Splitting: Getrennte Daten- und Aktions-Contexts können unnötig breite Abonnements vermeiden.
