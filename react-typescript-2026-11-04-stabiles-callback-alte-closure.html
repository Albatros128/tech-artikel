Ein stabiles Callback kann eine stabile alte Closure sein

Funktionsidentität und Aktualität sind zwei verschiedene Eigenschaften.

04.11.2026 · React-Closures · React 19.3 · Tief · ~8 min

Nach dem Sprachwechsel zeigt der Editor weiterhin „Gespeichert“ statt „Saved“. Der Autosave selbst arbeitet korrekt. Nur der Listener, den ein Hook beim ersten Render registriert hat, ruft noch das damalige onSaved auf. Im Versuch, unnötige Re-Subscriptions zu vermeiden, wurde das Callback mit useCallback([]) „stabilisiert“ – und damit der erste Render-Snapshot konserviert.

TL;DR

useCallback hält eine Funktionsdefinition nur so lange fest, wie ihre Dependencies unverändert bleiben. Eine leere Liste macht gelesene Props nicht aktuell, sondern friert die erste Closure ein. Entscheide bei externen Subscriptions zuerst, welche Werte die Subscription selbst definieren: Sie gehören in die Effect-Dependencies. Logik, die bei einem späteren Ereignis lediglich die neuesten committed Props oder States lesen soll, kann in React 19.3 als useEffectEvent modelliert werden.

Prerequisites

Du kennst Effects, Closures und Dependency-Arrays. Die Beispiele beziehen sich auf React 19.3. React dokumentiert, dass useCallback jede im Callback gelesene reaktive Dependency benötigt. useEffectEvent liest beim Aufruf die neuesten committed Werte, darf aber nur aus Effects oder anderen Effect Events heraus aufgerufen werden.

Der Aha-Effekt

„Stabil“ beantwortet nur: Ist es dieselbe Funktionsreferenz? „Aktuell“ beantwortet: Aus welchem Render stammen die geschlossenen Werte? Eine Funktion kann stabil und veraltet sein. Genau das passiert, wenn sie beim ersten Render erzeugt und danach dauerhaft wiederverwendet wird.

Für eine Subscription brauchst du deshalb zwei Kategorien. documentId bestimmt, welchem Dokument der Hook zuhört; ändert es sich, muss React ab- und neu abonnieren. Die aktuelle Sprache oder ein neues onSaved ändern dagegen nicht die Quelle. Sie sollen erst dann gelesen werden, wenn das externe Ereignis eintritt. Das ist nicht-reaktive Effect-Logik.

So macht man es falsch

Das leere Dependency-Array verschweigt, dass onSaved aus jedem Render neu kommt. Der Bus behält dadurch indirekt immer den ersten Callback:

import { useCallback, useEffect, useState, type ReactElement } from "react";

type SaveResult = { version: number };
type AutosaveBus = {
  subscribe(id: string, listener: (result: SaveResult) => void): () => void;
};
declare const autosaveBus: AutosaveBus;

function useAutosave(documentId: string, onSaved: (r: SaveResult) => void): void {
  const stableOnSaved = useCallback(onSaved, []); // erste Closure bleibt erhalten

  useEffect(() => {
    return autosaveBus.subscribe(documentId, result => stableOnSaved(result));
  }, [documentId, stableOnSaved]);
}

export function Editor(props: { documentId: string; locale: "de" | "en" }): ReactElement {
  const [message, setMessage] = useState("");
  useAutosave(props.documentId, result => {
    setMessage(`${props.locale === "de" ? "Gespeichert" : "Saved"} v${result.version}`);
  });
  return <output>{message}</output>;
}

Warum ist das falsch?

Beim ersten Render schließt onSaved die damaligen Props ein. useCallback(onSaved, []) gibt bei späteren Renderings weiterhin genau diese Funktion zurück. Der Effect wird für dieselbe Dokument-ID nicht neu synchronisiert, und jedes Bus-Ereignis läuft durch die alte Sprachlogik.

Das beobachtbare Symptom tritt zeitversetzt auf: Render und UI zeigen bereits die neue Sprache, während WebSocket-, Timer- oder Bus-Callbacks alte Werte verwenden. Der React-Linter würde die fehlende Dependency melden. Ihn zu unterdrücken beseitigt nicht die Kausalität, sondern nur den Hinweis.

So macht man es richtig mit Trade-offs

Das Effect Event bleibt direkt neben dem Effect, der es aufruft. Die Subscription reagiert auf documentId; das spätere Autosave-Ereignis liest dagegen das neueste onSaved:

import { useEffect, useEffectEvent, useState, type ReactElement } from "react";

type SaveResult = { version: number };
type AutosaveBus = {
  subscribe(id: string, listener: (result: SaveResult) => void): () => void;
};
declare const autosaveBus: AutosaveBus;

function useAutosave(documentId: string, onSaved: (r: SaveResult) => void): void {
  const notifySaved = useEffectEvent((result: SaveResult) => {
    onSaved(result); // liest das onSaved des neuesten committed Renders
  });

  useEffect(() => {
    return autosaveBus.subscribe(documentId, result => notifySaved(result));
  }, [documentId]);
}

export function Editor(props: { documentId: string; locale: "de" | "en" }): ReactElement {
  const [message, setMessage] = useState("");
  useAutosave(props.documentId, result => {
    setMessage(`${props.locale === "de" ? "Gespeichert" : "Saved"} v${result.version}`);
  });
  return <output aria-live="polite">{message}</output>;
}

notifySaved gehört absichtlich nicht ins Dependency-Array. Laut React besitzt eine Effect-Event-Funktion selbst keine stabile Identität; sie ist ein besonderer nicht-reaktiver Teil der Effect-Logik, keine Memoisierungsstrategie. Übergib sie deshalb weder an Komponenten noch an andere Hooks.

Die einfachste Alternative ist, onSaved als normale Dependency aufzunehmen. Das ist korrekt, führt bei einem inline erzeugten Callback aber bei jedem Render zu einer Ab- und Anmeldung. Wenn genau diese Neu-Synchronisierung fachlich erwünscht ist, ist sie die bessere Lösung. Für ältere React-Versionen kann ein manuell aktualisiertes Ref den neuesten Callback halten; es ist jedoch leichter, Abhängigkeiten und Commit-Zeitpunkt falsch zu modellieren.

Fallstricke am Rand

  • Nutze Effect Events nicht als pauschalen Ausweg aus Dependency-Warnungen.
  • Werte, welche die externe Verbindung oder Subscription bestimmen, bleiben reaktive Dependencies.
  • Rufe Effect Events nicht während des Renderns auf und reiche sie nicht durch Props weiter.

Selbst ausprobieren

Baue in zehn Minuten einen kleinen Event-Bus mit subscribe und emit. Rendere den Editor zunächst mit locale="de", wechsle danach auf en und löse erst dann das Save-Event aus. Erwartung: Die fehlerhafte Variante meldet weiterhin „Gespeichert“, die Effect-Event-Variante „Saved“. Ändere anschließend documentId; nun muss genau die Subscription wechseln.

Prüfstand: Das Closure-Modell wurde mit erstem und neuestem Callback unter Node ausgeführt. HTML-Struktur, Diagrammanzahl und Codeklammern wurden geprüft. Ein React-Integrations- oder TypeScript-Compile-Test war lokal nicht verfügbar und wird nicht behauptet.

Verwandte Themen

Effect-Dependencies beschreiben Synchronisierungsursachen. Funktionale State-Updates lösen veraltete Berechnungen aus vorherigem State. Refs speichern mutable Werte außerhalb des Render-Snapshots. Subscription-Tests erzwingen die Reihenfolge Render, Prop-Wechsel und externes Ereignis.
