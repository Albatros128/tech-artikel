Eine Typangabe validiert keine API-Antwort

Warum fetchJson<User>() nur Vertrauen ausdrückt – und wie eine Boundary-Funktion aus unknown belastbare Domänendaten macht.

05.10.2026 · API-Modellierung · TypeScript 6.0 / Fetch API · Tief · ~8 min

Die Benutzerliste läuft seit Monaten. Dann liefert das Backend nach einem Deployment für eine einzelne Rolle plötzlich "owner" statt "admin". Der TypeScript-Build bleibt grün. Erst im Browser fällt eine Verzweigung in den falschen Pfad.

Das ist kein Versagen des Typsystems. Der Compiler hat nur den Vertrag geprüft, den der Client selbst behauptet hat. Die entscheidende Frage lautet deshalb nicht: „Welchen Typ möchte ich hier haben?“, sondern: „An welcher Stelle wird eine fremde Laufzeitstruktur nachweislich zu meinem Domänentyp?“

TL;DR

Behandle Daten aus HTTP, Storage, postMessage oder URL-Parametern zunächst als unknown. Validiere sie einmal an der Systemgrenze und gib erst danach einen präzisen Typ zurück. Ein as User und ein generisches fetchJson<User> erzeugen keine Laufzeitprüfung.

Prerequisites

Du solltest unknown, Narrowing und Type Predicates sowie Response.json() kennen. Der Artikel bezieht sich auf die TypeScript-6.0-Dokumentation; das gezeigte Boundary-Muster ist nicht an eine neue 6.0-Funktion gebunden.

Der Aha-Effekt

Ein TypeScript-Typ existiert während der Prüfung des Quellcodes. Eine JSON-Antwort existiert erst zur Laufzeit. Zwischen beiden liegt keine automatische Verbindung. Type Assertions werden beim Kompilieren entfernt und verändern das Laufzeitverhalten nicht. [1]

unknown macht diese Grenze sichtbar. Der Typ kann jeden Wert repräsentieren, erlaubt aber keine Nutzung, bevor Code ihn eingegrenzt hat. [2] Das wirkt zunächst umständlich. Genau diese Reibung zwingt die Anwendung dazu, Beweise dort zu erzeugen, wo Vertrauen beginnt.

So macht man es falsch

Der folgende Helper sieht wiederverwendbar aus. Tatsächlich entscheidet allein der Aufrufer, was T sein soll. Die Implementierung kann diese Behauptung weder prüfen noch aus der Antwort ableiten:

Wenn displayName fehlt, meldet der Compiler nichts. Der Fehler erscheint erst bei toUpperCase() – weit entfernt von der eigentlichen Ursache.

Warum ist das falsch?

Response.json() liest den Body und parst JSON. Das Ergebnis kann laut MDN jeder durch JSON darstellbare Wert sein: Objekt, Array, String, Zahl und mehr. [3] JSON-Syntaxprüfung ist daher keine Schemaprüfung.

Auch Promise<User> hilft nicht. Die Return-Type-Angabe kontrolliert nur, ob der Funktionskörper aus Sicht des Compilers einen kompatiblen Wert liefert. Das as T liefert genau diese – unbelegte – Kompatibilität. Ein falscher Wert wandert anschließend als scheinbar vertrauenswürdiger User durch Cache, State und UI. Je später er auffällt, desto schlechter ist der Fehlerkontext.

So macht man es richtig

Die Boundary-Funktion akzeptiert unknown, prüft Struktur und erlaubte Werte und konstruiert anschließend ein neues User-Objekt. HTTP-Status, JSON-Syntax und Domänenschema bleiben drei getrennte Fehlerklassen.

Die Funktion erlaubt zusätzliche Eingabefelder, gibt sie aber nicht weiter. Das ist eine bewusste Kompatibilitätsentscheidung: Das Backend darf additive Änderungen liefern, während der Client nur sein bekanntes Modell übernimmt. Wer exakte Objekte verlangt, müsste auch unbekannte Schlüssel ablehnen.

Der Trade-off ist Wartung: Manuelle Validatoren werden bei verschachtelten Modellen schnell repetitiv. Für viele oder komplexe Schemas ist eine etablierte Runtime-Schema-Bibliothek oft angemessener. Sie ändert aber nicht das Prinzip: Die Eingabe bleibt unknown, bis eine Laufzeitprüfung erfolgreich war. Type Predicates können Narrowing kapseln, sind jedoch selbst nur so korrekt wie ihre Implementierung. [4]

Diagramm

flowchart TD
  A[HTTP response] --> B[JSON parser]
  B --> C[unknown]
  C --> D{Boundary validator}
  D -->|valid| E[User]
  D -->|invalid| F[Schema error]

Der JSON-Parser beweist nur gültige JSON-Syntax. Erst der Boundary-Validator entscheidet, ob der Wert dem Domänenvertrag entspricht.

Fallstricke am Rand

  • response.ok: Ein gültiger Fehlerbody ist noch kein erfolgreicher Request. Prüfe den HTTP-Status separat.
  • null: typeof null ist "object"; ein Objekt-Guard muss null ausdrücklich ausschließen.
  • Semantik: typeof id === "string" prüft noch nicht, ob der String leer ist oder einem ID-Format entspricht.
  • Fehlerdetails: In Produktcode können strukturierte Issues mit Pfad und Fehlercode hilfreicher sein als der erste geworfene TypeError.

Selbst ausprobieren

Kopiere parseUser in ein TypeScript-Projekt und teste sieben Fälle: einen gültigen User, null, ein Array, eine numerische ID, eine unbekannte Rolle, eine leere ID und ein gültiges Objekt mit Zusatzfeld. Erwartung: Nur der gültige User und die additive Variante werden akzeptiert; das Zusatzfeld erscheint nicht im Ergebnis.

Erweitere danach User.role um "auditor", ohne den Parser zu ändern. Der Compiler kann diese Diskrepanz nicht automatisch erkennen, weil Parser und Union getrennte Logik enthalten. Das ist der zentrale Trade-off manueller Validierung und ein guter Anlass für einen gezielten Test oder ein gemeinsam abgeleitetes Schema.

Prüfstand: Die Parser-Implementierung wurde unter Node.js 24 mit sieben Laufzeitfällen ausgeführt; alle Erwartungen bestanden. Ein TypeScript-Compiler war in der Ausführungsumgebung nicht verfügbar, daher wird kein bestandener Typecheck behauptet.

Verwandte Themen

Schema-first APIs können Laufzeitvalidatoren und Typen aus einer gemeinsamen Quelle ableiten. Discriminated Unions für API-Ergebnisse modellieren Erfolg und verschiedene Fehlerkörper. Branded Types unterscheiden validierte IDs von beliebigen Strings. Property-based Tests prüfen Validatoren mit vielen unerwarteten Eingaben statt nur mit einigen Fixtures.
