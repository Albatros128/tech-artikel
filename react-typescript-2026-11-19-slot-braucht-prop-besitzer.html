Ein Slot braucht einen Besitzer für seine Props

ReactNode, ComponentType und Render-Funktion sind keine austauschbaren Schreibweisen.

React-Komponenten-APIs · React 19.2 + TypeScript 6.0 · Tief · ~8 min

Eine Datentabelle akzeptiert eine frei gestaltbare Leerseite. Später soll sie diesem Slot compact und onRetry übergeben. Die API nimmt jedoch bereits fertiges JSX entgegen. Also klont die Tabelle das Element und injiziert Props – bis jemand einen String, ein Fragment oder eine Komponente mit anderen Props übergibt.

TL;DR

Nutze ReactNode, wenn der Aufrufer fertigen Inhalt besitzt und der Empfänger ihn nur platziert. Nutze ComponentType<P>, wenn der Empfänger eine Komponente instanziiert und ihre Props kontrolliert. Soll der Aufrufer Markup und Props verknüpfen, ist eine Render-Funktion (props: P) => ReactNode die expliziteste Grenze. Vermeide APIs, die einen beliebigen Node annehmen und später per cloneElement umschreiben.

Prerequisites

Du solltest Props und JSX-Slots sowie TypeScript-Funktionstypen kennen. React dokumentiert ReactNode als Typ für alle Werte, die React rendern kann. Der Artikel bezieht sich auf React 19.2 und TypeScript 6.0.

Der Aha-Effekt

Ein React-Element ist bereits das Ergebnis einer Elementerzeugung: Es enthält einen Typ und die Props dieses konkreten Renderings. Eine Komponentenreferenz ist dagegen noch instanziierbar. Wer ComponentType<P> entgegennimmt, kann beim Rendern ein neues Element mit exakt den vereinbarten Props erzeugen. Die Typwahl entscheidet damit über Eigentum, nicht nur über Syntax.

Prüffrage fürs API-Review: Darf der Empfänger Props hinzufügen? Dann darf der Parameter nicht bloß „irgendetwas Renderbares“ sein.

So macht man es falsch

Die Tabelle verspricht zunächst maximale Freiheit mit ReactNode. Intern benötigt sie aber eine engere Schnittstelle und erzwingt diese nachträglich durch Laufzeitprüfung und Assertion.

import {
  cloneElement,
  isValidElement,
  type ReactNode,
} from "react";

type EmptyStateProps = {
  compact: boolean;
  onRetry(): void;
};

type DataTableProps = {
  emptyState: ReactNode;
  compact: boolean;
  onRetry(): void;
};

export function DataTable(props: DataTableProps) {
  if (!isValidElement(props.emptyState)) {
    return <div>{props.emptyState}</div>;
  }

  return cloneElement(
    props.emptyState,
    {
      compact: props.compact,
      onRetry: props.onRetry,
    } as Partial<EmptyStateProps>
  );
}

Warum ist das falsch?

ReactNode umfasst mehr als Elemente: unter anderem Strings, Zahlen, leere Werte, Arrays und Portale. Selbst ein gültiges Element garantiert nicht, dass sein Komponententyp compact oder onRetry akzeptiert. Die Assertion beseitigt genau die Prüfung, die die öffentliche API leisten sollte.

React bezeichnet cloneElement selbst als selten und potenziell fragil. Das Klonen erschwert den Datenfluss, überschreibt gleichnamige Props und behandelt key sowie ref besonders. Das beobachtbare Symptom ist eine API, deren Signatur mehr erlaubt als ihre Implementierung tatsächlich unterstützt.

So macht man es richtig

Wenn die Tabelle die Props besitzt, akzeptiert sie einen Komponententyp mit genau diesem Vertrag. JSX erzeugt daraus ein neues Element; TypeScript prüft beide Seiten der Grenze.

import type { ComponentType, ReactNode } from "react";

type EmptyStateProps = {
  compact: boolean;
  onRetry(): void;
};

type DataTableProps = {
  EmptyState: ComponentType<EmptyStateProps>;
  compact: boolean;
  onRetry(): void;
};

export function DataTable({
  EmptyState,
  compact,
  onRetry,
}: DataTableProps) {
  return <EmptyState compact={compact} onRetry={onRetry} />;
}

// Der Aufrufer übergibt den Typ, nicht <ProductEmptyState />.
<DataTable EmptyState={ProductEmptyState} {...tableProps} />;

// Alternative: Der Aufrufer besitzt das Markup.
type RenderSlot = (props: EmptyStateProps) => ReactNode;

ComponentType setzt eine feste Prop-Schnittstelle voraus und erzeugt eine sichtbare Komponenten-Grenze. Eine Render-Funktion ist flexibler, weil sie Props in beliebiges Markup übersetzen kann; dafür wird sie bei jedem Aufruf als normale Funktion der API ausgeführt. Für rein statischen Inhalt bleibt ReactNode die einfachste Alternative – solange der Empfänger ihn unverändert rendert.

Fallstricke am Rand

  • Eine Komponentenreferenz muss stabil außerhalb des Renderpfads definiert sein, sonst kann React ihre Identität als neuen Komponententyp behandeln.
  • ComponentType<P> erlaubt Funktions- und Klassenkomponenten; eine reine Funktionssignatur kann absichtlich enger sein.
  • Ein optionaler Slot braucht eine explizite Default-Strategie statt eines erzwungenen Dummy-Elements.

Selbst ausprobieren

Ersetze in zehn Minuten in einer kleinen Panel-Komponente den Prop footer: ReactNode durch Footer: ComponentType<{ onClose(): void }>. Übergib zuerst eine kompatible Komponente, danach eine ohne onClose. Erwartung: Die zweite Variante scheitert bereits beim Typecheck. Wechsle anschließend zu renderFooter und beobachte, dass der Aufrufer die Props explizit in sein JSX einbindet.

Verwandte Themen

  • Compound Components: Context verteilt Slot-Daten, wenn JSX-Komposition wichtiger als ein einzelner Prop ist.
  • Polymorphe Komponenten: Ein as-Prop verschiebt ebenfalls Verantwortung für gültige Props.
  • Refs: Imperative Fähigkeiten benötigen einen eigenen, expliziten Vertrag.
  • Discriminated Props: Alternative Slot-Varianten lassen sich als gegenseitig ausschließende API modellieren.
