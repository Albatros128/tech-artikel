Ein Effect Event trennt Aktualität von Reaktivität

Nicht jeder Wert, den ein Callback lesen muss, soll auch die zugrunde liegende Synchronisierung neu starten.

React-Effects · React 19.3, useEffectEvent seit 19.2 · Tief · ~8 min

Ein Chat verbindet sich mit Raum „support“. Während die Verbindung steht, wechselt der Nutzer vom hellen zum dunklen Theme. Plötzlich trennt und öffnet die Komponente den Socket neu – nur weil die „Verbunden“-Meldung in der neuen Farbe erscheinen soll.

TL;DR

Ein Effect synchronisiert mit einem externen System; seine Dependencies bestimmen, wann diese Synchronisierung erneuert wird. Ein Effect Event liest dagegen die zuletzt committeten Props und States, ohne selbst die Re-Synchronisierung auszulösen. Verwende useEffectEvent nur für Logik, die tatsächlich durch ein Ereignis aus dem Effect ausgelöst wird – nie, um echte Dependencies zu verstecken.

Prerequisites

Vorausgesetzt sind der Lebenszyklus reaktiver Effects, useEffect und die Regel exhaustive-deps. Die aktuelle Referenz dokumentiert useEffectEvent für React 19.3; stabil veröffentlicht wurde der Hook mit React 19.2.

Der Aha-Effekt

„Aktuell“ und „reaktiv“ sind zwei verschiedene Anforderungen. Die Benachrichtigung soll beim später eintreffenden connected-Ereignis das aktuelle Theme sehen. Das Theme entscheidet aber nicht, zu welchem Raum der Socket gehört. roomId ist deshalb reaktiv für die Verbindung; theme ist nur eine aktuelle Eingabe für die Ereignisreaktion.

Dokumentierter Fakt: Ein Effect Event sieht die neuesten committeten Renderwerte. Es darf nur aus Effects oder anderen Effect Events aufgerufen, nicht an Kinder weitergereicht und nicht in eine Dependency-Liste aufgenommen werden.

So macht man es falsch

Die ehrliche Dependency-Liste ist hier formal korrekt, koppelt aber zwei verschiedene Lebenszyklen. Jeder Theme-Wechsel zerstört die Verbindung und erzeugt eine neue.

// ChatRoom.tsx – problematischer Ausschnitt
import { useEffect } from "react";
import { createConnection } from "./chat";

type Theme = "light" | "dark";
type Props = { roomId: string; theme: Theme };

export function ChatRoom({ roomId, theme }: Props) {
  useEffect(() => {
    const connection = createConnection(roomId);
    connection.on("connected", () => {
      showNotification("Verbunden", theme);
    });
    connection.connect();
    return () => connection.disconnect();
  }, [roomId, theme]);

  return <p>Raum: {roomId}</p>;
}

Das häufige „Gegenmittel“, theme aus der Liste zu löschen oder den Linter zu deaktivieren, ist schlechter: Der Callback kann dann ein altes Theme aus seiner Closure lesen. Die Komponente enthält weiterhin dieselbe Abhängigkeit, sie wird nur unsichtbar.

Warum ist das falsch?

React führt vor einer Re-Synchronisierung zunächst das Cleanup des vorherigen Effects aus und startet anschließend das neue Setup. Das beobachtbare Symptom ist daher nicht bloß ein zusätzlicher Render, sondern ein fachlicher Disconnect/Connect-Zyklus. Je nach System kann dieser Präsenzstatus, Subscriptions oder laufende Nachrichten beeinflussen. Eine konkrete Lastwirkung wird hier nicht behauptet; sie müsste im realen System gemessen werden.

So macht man es richtig

Ziehe nur den nicht-reaktiven Ereignisteil in ein Effect Event. Der Effect behält alle Werte, die seine externe Ressource definieren.

// chat.ts – benötigter Vertrag
export type Connection = {
  on(event: "connected", listener: () => void): void;
  connect(): void;
  disconnect(): void;
};
export declare function createConnection(roomId: string): Connection;

// ChatRoom.tsx – verbesserter Ausschnitt
import { useEffect, useEffectEvent } from "react";
import { createConnection } from "./chat";

type Theme = "light" | "dark";
type Props = { roomId: string; theme: Theme };

export function ChatRoom({ roomId, theme }: Props) {
  const onConnected = useEffectEvent(() => {
    showNotification("Verbunden", theme);
  });

  useEffect(() => {
    const connection = createConnection(roomId);
    connection.on("connected", onConnected);
    connection.connect();
    return () => connection.disconnect();
  }, [roomId]);

  return <p>Raum: {roomId}</p>;
}

Der Trade-off ist eine schärfere semantische Grenze: onConnected ist kein allgemeines Callback. Soll eine Funktion aus einem Click-Handler laufen oder an ein Kind gehen, ist eine normale Funktion beziehungsweise useCallback die passendere API. In React-Versionen vor 19.2 kann ein Ref den neuesten Wert bereitstellen, verlangt aber manuelle Synchronisierung und entzieht die Beziehung weitgehend dem Dependency-Linter.

Diagramm

Fallstricke am Rand

  • Ein Effect Event darf echte Synchronisierungsparameter nicht verstecken.
  • Seine Funktionsidentität ist absichtlich nicht stabil; nimm es nicht in Dependencies auf.
  • Definiere und verwende es lokal beim zugehörigen Effect, statt es durch Komponenten oder Hooks zu reichen.

Selbst ausprobieren

Ersetze createConnection für zehn Minuten durch einen Fake, der connect und disconnect zählt. Rendere mit roomId="support", ändere fünfmal das Theme und danach einmal die Raum-ID. Erwartung mit Effect Event: Der Theme-Wechsel erzeugt keinen neuen Verbindungszyklus; erst die neue Raum-ID führt zu genau einem Disconnect und einem weiteren Connect. Die spätere „Verbunden“-Meldung nutzt trotzdem das letzte Theme.

Verwandte Themen

  • Stale Closures: Sie erklären, warum das bloße Weglassen einer Dependency alte Werte konserviert.
  • useCallback: Es stabilisiert eine weitergegebene Identität, trennt aber nicht automatisch Reaktivität.
  • Effect-Cleanup: Seine Symmetrie entscheidet, ob Re-Synchronisierung Ressourcen korrekt ersetzt.
  • External Stores: Für gemeinsam genutzte Subscriptions kann useSyncExternalStore die passendere Grenze sein.
