Memoisierung ist eine Hypothese, kein Refactoring-Ziel

Erst ein reproduzierbarer Profiler-Vergleich zeigt, ob memo eine teure Wiederholung verhindert oder nur neue Komplexität einführt.

27.10.2026 · Performance-Messung · React 19.3 + TypeScript · Tief · ~8 min

Eine Suchseite fühlt sich beim Öffnen des Hilfetexts träge an. Im Review erhält die Ergebnisliste vorsorglich memo, jede Berechnung wandert in useMemo. Der Code wird länger, doch niemand kann sagen, ob die relevante Interaktion schneller wurde. Schlimmer: Das Array-Prop wird bei jedem Render neu erzeugt, sodass die vermeintliche Optimierung gar keinen Render überspringen kann.

TL;DR

Formuliere Memoisierung als überprüfbare Hypothese: „Bei Interaktion X rendert Teilbaum Y teuer, obwohl seine fachlichen Eingaben gleich bleiben.“ Messe denselben Ablauf vor und nach der Änderung mit Reacts <Profiler> oder den React Developer Tools. Stabilisiere Props nur dann, wenn die Messung genau diese Ursache zeigt. Entferne die Änderung, wenn der Effekt nicht reproduzierbar ist.

Prerequisites

Du kennst Renderzyklen, referenzielle Gleichheit und Hooks. Die Versionsseite führt React 19.3. Relevant sind Profiler, memo und useMemo. Das Beispiel setzt ein React-TypeScript-Projekt mit strict voraus. Es enthält bewusst keine erfundenen Zeitwerte: Die Resultate hängen von Daten, Gerät, Build und Interaktion ab.

Der Aha-Effekt

memo beantwortet keine Performancefrage. Es stellt eine Bedingung auf: Wenn ein Elternteil rendert und alle Props nach Object.is gleich geblieben sind, darf React den Kindrender normalerweise überspringen. Schon ein neues Array, Objekt oder eine neue Funktion macht diese Bedingung falsch.

Der Profiler trennt dabei zwei Größen. actualDuration beschreibt die Renderzeit des profilierten Teilbaums für den aktuellen Commit. baseDuration schätzt die Kosten eines vollständigen Renders ohne Optimierungen aus den jüngsten Komponentenzeiten. Der Vergleich zeigt, ob Memoisierung in diesem Teilbaum greift; er misst nicht automatisch Netzwerk, Effects oder den vollständigen Zeitraum bis zum nächsten Paint.

So macht man es falsch

Die Ergebnisliste ist memoisiert. Trotzdem erhält sie bei jedem Render ein neues Array. Auch das Öffnen der Hilfe erzeugt deshalb ein anderes items-Prop.

import { memo, useState } from "react";

type Product = { id: string; name: string };
type Props = { products: readonly Product[] };

const Results = memo(function Results(
  { items }: { items: readonly Product[] }
) {
  return (
    <ul>
      {items.map(item => <li key={item.id}>{item.name}</li>)}
    </ul>
  );
});

export function SearchPage({ products }: Props) {
  const [query, setQuery] = useState("");
  const [showHelp, setShowHelp] = useState(false);
  const visible = products.filter(product =>
    product.name.toLowerCase().includes(query.toLowerCase())
  );

  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <button onClick={() => setShowHelp(value => !value)}>Hilfe</button>
      {showHelp && <p>Tippe einen Produktnamen.</p>}
      <Results items={visible} />
    </>
  );
}

Warum ist das falsch?

Array.prototype.filter liefert bei jedem Aufruf ein neues Array. Inhaltlich identische Ergebnisse sind daher nicht referenziell identisch. Die Standardprüfung von memo sieht ein verändertes Prop und rendert Results erneut. Der Wrapper ist nicht kaputt; seine Voraussetzung wurde nie erfüllt.

Ohne Baseline bleibt außerdem unklar, ob dieser Render überhaupt das wahrgenommene Problem verursacht. Vielleicht ist die Liste klein, während ein Layout-Schritt, ein Effect oder eine Browser-Erweiterung dominiert. Mehr Memoisierung kann Lesbarkeit verschlechtern und Dependency-Fehler begünstigen, ohne die relevante Interaktion messbar zu verändern.

So macht man es richtig mit Trade-offs

Instrumentiere zunächst den verdächtigen Teilbaum. Wiederhole eine klar benannte Interaktion – hier zehnmal „Hilfe öffnen/schließen“ bei unveränderter Suche – mit denselben Daten und demselben Build. Sammle nicht nur einen Ausreißer, sondern mehrere Commits.

import {
  memo, Profiler, useMemo, useState,
  type ProfilerOnRenderCallback
} from "react";

type Product = { id: string; name: string };
type Props = { products: readonly Product[] };

const reportRender: ProfilerOnRenderCallback = (
  id, phase, actualDuration, baseDuration
) => {
  console.table({ id, phase, actualDuration, baseDuration });
};

const Results = memo(function Results(
  { items }: { items: readonly Product[] }
) {
  return <ul>{items.map(item =>
    <li key={item.id}>{item.name}</li>
  )}</ul>;
});

export function SearchPage({ products }: Props) {
  const [query, setQuery] = useState("");
  const [showHelp, setShowHelp] = useState(false);
  const normalizedQuery = query.toLowerCase();
  const visible = useMemo(
    () => products.filter(product =>
      product.name.toLowerCase().includes(normalizedQuery)
    ),
    [products, normalizedQuery]
  );

  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <button onClick={() => setShowHelp(value => !value)}>Hilfe</button>
      {showHelp && <p>Tippe einen Produktnamen.</p>}
      <Profiler id="results" onRender={reportRender}>
        <Results items={visible} />
      </Profiler>
    </>
  );
}

Diese Änderung stabilisiert visible, solange products und Suchtext gleich bleiben. Ob sie sich lohnt, entscheidet der Vorher-nachher-Vergleich. Profiling selbst verursacht Overhead und ist im normalen Production-Build standardmäßig deaktiviert; für Produktionsmessungen brauchst du einen dafür vorgesehenen Profiling-Build.

Eine oft einfachere Alternative ist strukturell: Verschiebe den Hilfe-State in eine kleine Geschwisterkomponente. Dann rendert der Suchseiten-Elternteil beim Umschalten nicht erneut, und die Ergebnisliste benötigt möglicherweise weder memo noch stabile Array-Props. Der Trade-off ist eine zusätzliche Komponentengrenze; dafür verschwinden Memo-Abhängigkeiten.

Fallstricke am Rand

  • Entwicklungsmodus und Strict Mode können zusätzliche Arbeit sichtbar machen. Vergleiche immer unter denselben Bedingungen.
  • Ein eigener arePropsEqual-Vergleich kann teurer oder fehleranfälliger sein als der Render. Messe auch ihn und vergleiche jede funktionale Prop.
  • useMemo ist keine semantische Garantie. Wenn der Code ohne Cache falsch wäre, brauchst du State, Ref oder eine andere Ownership-Grenze.

Selbst ausprobieren

Nimm dir fünfzehn Minuten. Profiliere zehn Hilfe-Umschaltungen mit der Fehlervariante und notiere die actualDuration-Werte des Ergebnis-Teilbaums. Führe danach exakt denselben Ablauf mit stabilisiertem Array durch. Erwartung: Prüfe zuerst, ob die Ergebnisliste beim unveränderten Suchtext überhaupt noch committed wird; bewerte erst dann die Zeitverteilung. Ändere anschließend den Suchtext: Jetzt muss die Liste wieder rendern.

Prüfstand: Die referenzielle Ursache wurde mit einem Node-Modell geprüft: wiederholtes filter erzeugt neue Referenzen, eine abhängigkeitsbasierte Memo-Funktion hält sie bei unveränderten Eingaben stabil. Mangels React-Paketen wurde kein Profiler-Benchmark ausgeführt; es werden keine Zeitgewinne behauptet.

Verwandte Themen

React Developer Tools Profiler liefert eine interaktive Commit-Ansicht. User Timing misst anwendungsdefinierte Zeiträume jenseits reiner Renderarbeit. State-Colocation vermeidet unnötige Elternrenders strukturell. Virtualisierung begrenzt die tatsächlich gerenderte Listenmenge, wenn Messungen die Listengröße als Ursache bestätigen.
