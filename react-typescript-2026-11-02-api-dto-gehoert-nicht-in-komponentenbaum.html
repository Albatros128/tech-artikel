Ein API-DTO gehört nicht in deinen Komponentenbaum

Übersetze den Transportvertrag einmal an der Feature-Grenze, statt seine Sonderfälle in jeder Komponente zu wiederholen.

02.11.2026 · Frontend-Architektur · TypeScript 6.0 + Web APIs · Tief · ~8 min

Das Backend benennt created in open um und liefert den Bestellzeitpunkt bei historischen Datensätzen gelegentlich als null. Plötzlich ändern fünf Komponenten ihre Fallunterscheidungen. Eine Karte zeigt „Ungültiges Datum“, ein Dialog deaktiviert den Storno-Button anders als die Übersicht. Der Transportvertrag ist unbemerkt zur Sprache der gesamten Oberfläche geworden.

TL;DR

Behandle ein API-DTO als externes Format, nicht als internes Anwendungsmodell. Lies JSON als unknown, prüfe es an der Datenzugriffsgrenze und übersetze es dort in einen Typ mit den Invarianten, die dein Feature tatsächlich braucht. Komponenten erhalten dann ein stabiles Modell statt Netzwerk-Sonderfälle. Die zusätzliche Abbildung kostet Code und kann für sehr einfache CRUD-Oberflächen unnötig sein; sie lohnt sich, sobald Transport- und UI-Semantik auseinanderlaufen.

Prerequisites

Du kennst fetch, Union-Typen und Type Guards. Die Beispiele beziehen sich auf TypeScript 6.0. TypeScripts Handbuch erklärt Narrowing; MDN weist darauf hin, dass Response.json() zu jedem JSON-repräsentierbaren JavaScript-Wert auflösen kann.

Der Aha-Effekt

Ein DTO ist nicht „das gleiche Objekt mit schlechteren Namen“. Es beschreibt, wie Daten eine technische Grenze passieren. Dein internes Modell beschreibt dagegen, welche Zustände die Anwendung akzeptiert. Wenn beide Typen identisch sind, ist das eine bewusste Vereinfachung – keine Naturgesetzlichkeit.

Die Übersetzungsfunktion ist eine Anti-Corruption-Grenze im Kleinen. Sie konzentriert drei Entscheidungen: Ist die Antwort strukturell gültig? Wie werden Backend-Begriffe in Feature-Begriffe übersetzt? Welche Invarianten gelten danach? Hinter dieser Grenze muss keine Komponente mehr wissen, dass Geld als total_cents, Zeit als String und Status als Backend-Code ankommt.

So macht man es falsch

Der Transporttyp wird direkt zum Prop-Typ. Dadurch tragen alle Konsumenten Nullable-Felder, Backend-Namen und Konvertierungslogik:

import type { ReactElement } from "react";

type OrderDto = {
  id: string;
  total_cents: number | null;
  currency: string;
  placed_at: string | null;
  status: "created" | "paid" | "sent" | "cancelled";
};

export function OrderCard({ dto }: { dto: OrderDto }): ReactElement {
  const total = dto.total_cents == null
    ? "–"
    : new Intl.NumberFormat("de-DE", {
        style: "currency", currency: dto.currency
      }).format(dto.total_cents / 100);

  const canCancel = dto.status === "created" || dto.status === "paid";
  const date = dto.placed_at ? new Date(dto.placed_at).toLocaleDateString("de-DE") : "–";

  return <article>
    <strong>{total}</strong> · <time>{date}</time>
    <button disabled={!canCancel}>Stornieren</button>
  </article>;
}

Warum ist das falsch?

Die TypeScript-Annotation beweist nicht, dass die Netzwerkantwort diesen Typ besitzt. Noch wichtiger: Selbst bei korrektem DTO müssen mehrere Komponenten dieselben fachlichen Ableitungen reproduzieren. Aus status wird überall erneut canCancel; aus Cent und Währung wird Geld; aus einem optionalen String wird ein Zeitpunkt.

Die beobachtbaren Symptome sind Drift und breite Änderungen. Zwei Komponenten interpretieren einen neuen Status unterschiedlich, ungültige Zeitstrings werden erst beim Rendern sichtbar, und ein Backend-Rename erzeugt Änderungen in UI-Dateien ohne fachlichen Grund. Der Komponentenbaum kennt damit mehr über die Transportebene als über das Feature.

So macht man es richtig mit Trade-offs

Das Datenmodul akzeptiert unknown, validiert die tatsächlich benötigten Felder und liefert ein kleineres internes Modell. Der Ausschnitt ist ohne Schema-Bibliothek vollständig; in größeren Projekten kann dieselbe Grenze durch einen Runtime-Schema-Validator implementiert werden:

import type { ReactElement } from "react";

type Currency = "EUR" | "USD";
type OrderStatus = "open" | "paid" | "shipped" | "cancelled";

export type Order = {
  id: string;
  total: { minor: number; currency: Currency };
  placedAt: Date;
  status: OrderStatus;
  canCancel: boolean;
};

function record(value: unknown): Record<string, unknown> {
  if (typeof value !== "object" || value === null || Array.isArray(value)) {
    throw new Error("Order muss ein Objekt sein");
  }
  return value as Record<string, unknown>;
}

function text(value: unknown, field: string): string {
  if (typeof value !== "string") throw new Error(`${field} muss Text sein`);
  return value;
}

export function parseOrder(input: unknown): Order {
  const dto = record(input);
  const minor = dto.total_cents;
  if (!Number.isSafeInteger(minor) || (minor as number) < 0) {
    throw new Error("total_cents muss eine nichtnegative Ganzzahl sein");
  }

  const currency = text(dto.currency, "currency");
  if (currency !== "EUR" && currency !== "USD") throw new Error("Währung unbekannt");

  const rawStatus = text(dto.status, "status");
  const statusMap = {
    created: "open", paid: "paid", sent: "shipped", cancelled: "cancelled"
  } as const;
  if (!(rawStatus in statusMap)) throw new Error("Status unbekannt");
  const status = statusMap[rawStatus as keyof typeof statusMap];

  const placedAt = new Date(text(dto.placed_at, "placed_at"));
  if (Number.isNaN(placedAt.getTime())) throw new Error("Zeitpunkt ungültig");

  return {
    id: text(dto.id, "id"), total: { minor: minor as number, currency },
    placedAt, status, canCancel: status === "open" || status === "paid"
  };
}

export async function loadOrder(id: string, signal: AbortSignal): Promise<Order> {
  const response = await fetch(`/api/orders/${encodeURIComponent(id)}`, { signal });
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return parseOrder(await response.json() as unknown);
}

export function OrderCard({ order }: { order: Order }): ReactElement {
  const total = new Intl.NumberFormat("de-DE", {
    style: "currency", currency: order.total.currency
  }).format(order.total.minor / 100);
  return <article>
    <strong>{total}</strong>
    <time dateTime={order.placedAt.toISOString()}>
      {order.placedAt.toLocaleDateString("de-DE")}
    </time>
    <button disabled={!order.canCancel}>Stornieren</button>
  </article>;
}

Nach parseOrder existieren weder null-Beträge noch unbekannte Währungen oder ungültige Zeitpunkte. Ein Backend-Rename betrifft Parser und Vertragstests, nicht jede Komponente. Formatierung bleibt bewusst in der UI, weil Locale eine Darstellungsentscheidung ist; Intl.NumberFormat verwendet dafür Währung und Locale.

Der Preis ist eine zweite Typwelt samt Mapping und Tests. Für ein internes Admin-CRUD, dessen Oberfläche den Backendvertrag exakt spiegelt, kann ein generierter Client direkt genügen. Eine weitere Alternative ist ein generiertes DTO plus Schema-Parser; Codegenerierung ersetzt jedoch nicht die semantische Übersetzung, wenn das Feature andere Begriffe oder Invarianten benötigt.

Fallstricke am Rand

  • Ein Type Predicate ist nur so vertrauenswürdig wie seine Prüfungen; ein bloßer Cast im Predicate validiert nichts.
  • Formatiere Geld nicht schon im Datenmodul, wenn Locale oder Währungsdarstellung zur Laufzeit wechseln können.
  • Wirf nicht jedes unbekannte DTO-Feld weg, wenn spätere Schreiboperationen es unverändert zurücksenden müssen.

Selbst ausprobieren

Nimm dir zehn Minuten und führe parseOrder mit vier Eingaben aus: einer gültigen Bestellung, total_cents: null, placed_at: "gestern" und status: "refunded". Erwartung: Nur die erste Eingabe erzeugt ein Order; jede andere scheitert an der Feature-Grenze mit einer konkreten Meldung. Ergänze danach refunded absichtlich als internen Status und entscheide explizit, ob Stornieren erlaubt ist.

Prüfstand: Die gültige Abbildung sowie drei ungültige Grenzfälle wurden mit Node ausgeführt. HTML-Struktur, Diagrammanzahl und Codeklammern wurden geprüft. Ein TypeScript-Compile- oder React-Integrationstest war lokal nicht verfügbar und wird nicht behauptet.

Verwandte Themen

Runtime-Schemas skalieren Feldprüfungen und Fehlermeldungen. Generated Clients synchronisieren Transporttypen mit OpenAPI. View Models reduzieren fachliche Modelle auf einen konkreten Screen. Contract Tests erkennen Änderungen zwischen Backend und Adapter früh.
