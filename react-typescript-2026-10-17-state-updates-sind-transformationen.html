Ein State-Update ist manchmal eine Transformation, kein neuer Wert

Ein asynchroner Handler behält seinen Render-Snapshot. Die Update-Queue muss ihn nicht behalten.

React-State & Closures · React 19.3-Dokumentation + TypeScript · Tief · ~7 min

Du startest zwei Dokumentimporte. Beide melden Erfolg, beide liefern unterschiedliche IDs, im Ergebnisbereich erscheint trotzdem nur ein Dokument. Im Netzwerk gibt es keinen verlorenen Request. Verloren geht ein bereits sichtbares Ergebnis, weil der zweite Callback eine Liste auf Basis eines alten Render-Snapshots ersetzt.

TL;DR

Wenn der nächste State aus dem bisherigen State entstehen soll, übergib dem Setter eine reine Funktion: setCompleted(previous => [...previous, result]). Übergib einen fertigen Wert, wenn du bewusst ersetzen willst. Der Unterschied ist fachlich: „Ergänze den dann gültigen Zustand“ ist ein anderer Auftrag als „Setze genau diese Liste“.

Prerequisites

Du solltest Closures, Promises und unveränderliche Array-Updates kennen. Die offizielle Versionsseite nennt React 19.3; der Artikel bezieht sich auf dessen Dokumentation, nicht auf eine neue API dieser Version. Relevant sind State as a Snapshot und die useState-Referenz. Nutze ein bestehendes React-TypeScript-Projekt mit strict und jsx: "react-jsx"; die folgenden TSX-Beispiele benötigen keine weiteren Pakete.

Der Aha-Effekt

Der Setter ist keine Zuweisung an die Variable deines Handlers. React erzeugt bei jedem Render einen neuen Satz lokaler Werte und Handler. Ein bereits gestarteter Handler arbeitet weiter mit den Werten seines eigenen Renders – auch hinter einem await. Das ist nützlich, wenn du wissen möchtest, welches Dokument der Nutzer beim Start gewählt hatte.

Meine Designfolgerung: Unterscheide den Startkontext einer Operation von ihrem Zustandsübergang bei Abschluss. Die Dokument-ID darf eingefroren bleiben. Die Ergebnisliste soll dagegen alle inzwischen abgeschlossenen Importe enthalten.

So macht man es falsch

Lege diesen vollständigen Demonstrator in App.tsx ab. Starte beide Importe, bevor der erste fertig ist. Die unterschiedlichen Verzögerungen machen die Abschlussreihenfolge nachvollziehbar; sie simulieren keinen bestimmten Server.

import { useState } from "react";

type ImportResult = { id: string; title: string };

async function importItem(id: string): Promise<ImportResult> {
  await new Promise<void>(resolve =>
    setTimeout(resolve, id === "A" ? 1200 : 600));
  return { id, title: `Dokument ${id}` };
}

export default function App() {
  const [completed, setCompleted] = useState<ImportResult[]>([]);

  async function handleImport(id: string) {
    const result = await importItem(id);
    setCompleted([...completed, result]);
  }

  return (
    <section aria-label="Dokumentimporte">
      <button onClick={() => void handleImport("A")}>Import A</button>
      <button onClick={() => void handleImport("B")}>Import B</button>
      <ul>{completed.map((item, index) =>
        <li key={`${item.id}-${index}`}>{item.title}</li>)}</ul>
    </section>
  );
}

Warum ist das falsch?

Beim Start beider Operationen ist completed leer. B beendet zuerst und setzt die Liste auf [B]. Der dadurch ausgelöste Render erstellt neue Handler, verändert aber den noch laufenden A-Handler nicht. Dieser berechnet später aus seinem alten leeren Array den Wert [A]. Das ist kein paralleler Schreibzugriff zweier JavaScript-Threads, sondern zweimaliges Ersetzen aus veraltetem Wissen.

Die Dokumentation zur Update-Queue unterscheidet Wert-Updates und Updater-Funktionen: Ein Wert ersetzt, eine Funktion berechnet den nächsten Zustand aus dem vorangehenden Queue-Ergebnis. Batching erklärt, wann React Updates zusammen verarbeitet; es macht aus einem alten Snapshot keinen aktuellen Wert. Ein zusätzliches await oder ein anderer Timer behebt die Ursache nicht.

So macht man es richtig mit Trade-offs

Ersetze ausschließlich den Handler. Typ, Hilfsfunktion, Import und JSX bleiben unverändert. Der Callback schließt weiterhin result ein, liest die Liste aber aus dem Updater-Argument.

// App.tsx – Ersatz für handleImport
async function handleImport(id: string) {
  const result = await importItem(id);
  setCompleted(previous => [...previous, result]);
}

Damit hängt A an [B] an, statt diese Liste zu überschreiben. Die Abschlussreihenfolge bleibt B, A. Falls die Oberfläche Startreihenfolge verlangt, brauchst du zusätzlich eine beim Start vergebene Sequenz oder vorab angelegte Einträge. Ein funktionaler Updater liefert keine Sortier-, Deduplizierungs- oder Fehlerstrategie.

Der Updater muss rein bleiben: Kein Request, kein Toast und keine Mutation des bisherigen Arrays gehören hinein. React kann ihn im Entwicklungs-Strict-Mode zur Prüfung erneut ausführen, wie die Referenz zu reinen Updatern erklärt. Erzeuge nebenwirkende Dinge vor dem Setter und übergib anschließend das Ergebnis.

Als Alternative eignet sich ein Reducer, sobald mehrere Ereignisse dieselben Invarianten verändern: gestartet, erfolgreich, fehlgeschlagen, entfernt. Er zentralisiert Übergänge, kostet aber Action-Typen und zusätzliche Struktur. Bei einem einzelnen Append ist der funktionale Setter präziser. Ein fertiger Wert bleibt richtig, wenn du beispielsweise nach einem bewussten Reset die gesamte Ergebnisliste ersetzen möchtest.

Fallstricke am Rand

  • Nur das Updater-Argument ist hier der Queue-Zustand. Andere eingefangene Props bleiben Werte des ursprünglichen Renders.
  • Ein Updater verhindert keinen Abschluss im falschen Benutzer- oder Projektkontext. Dafür brauchst du eine separate Relevanzentscheidung.
  • Mehrfachklicks erzeugen hier absichtlich weitere Einträge. Die Demo identifiziert Listenvorkommen mit ID und Index; bei entfernbaren oder sortierbaren Zeilen brauchst du stabile Vorgangs-IDs.

Selbst ausprobieren

Plane zehn Minuten ein. Starte A und unmittelbar danach B. Beobachte zuerst B, dann nur A. Ersetze den Handler: Jetzt bleiben B und A erhalten. Starte anschließend A erst nach B-Abschluss; auch die Fehlervariante kann dann korrekt wirken, weil der neue Handler bereits B kennt. Dieser Gegenversuch erklärt, warum der Fehler im manuellen Einzeltest leicht verschwindet.

Prüfstand: Ein deterministischer Node-Modelltest führt die gezeigten Handler mit kontrollierten Promises aus und bestätigt Verlust beziehungsweise Erhalt beider Ergebnisse. Er ist kein React-Integrationstest. React- und TypeScript-Pakete waren lokal nicht verfügbar; ein TSX-Compile- oder Browser-Verhaltenstest wurde nicht durchgeführt.

Verwandte Themen

Reducer-Invarianten helfen, wenn mehrere Zustandsfelder gemeinsam wechseln müssen. Request-Relevanz entscheidet, ob ein Ergebnis überhaupt noch übernommen werden darf. Idempotente Ereignisse verhindern doppelte Einträge bei Wiederholungen, statt nur verlorene Ergänzungen zu vermeiden.
