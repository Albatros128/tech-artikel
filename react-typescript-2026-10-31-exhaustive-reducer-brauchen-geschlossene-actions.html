Exhaustive Reducer brauchen ein geschlossenes Action-Protokoll

Ein freundliches default: return state kann eine neue, korrekt typisierte Action lautlos verschlucken.

31.10.2026 · TypeScript-Discriminated-Unions · TypeScript 6.0 + React 19.3 · Tief · ~8 min

Das Team ergänzt im Checkout die Action shipping.selected. Der Dispatch kompiliert, DevTools zeigen die Action, aber die Versandart ändert sich nicht. Der Reducer besitzt einen Default-Zweig, der den bisherigen State zurückgibt. Was als defensive Programmierung gedacht war, hat eine unvollständige Implementierung in gültiges Verhalten verwandelt.

TL;DR

Ist die Action-Union eines lokalen Reducers vollständig unter deiner Kontrolle, behandle sie als geschlossenes Protokoll und prüfe den Switch mit never auf Vollständigkeit. Eine neue Action erzeugt dann am fehlenden Case einen Compilerfehler. Für offene Protokolle – etwa ungeprüfte Nachrichten oder fremde Actions – ist ein toleranter Default dagegen legitim. Die entscheidende Frage lautet nicht „throw oder return“, sondern „ist diese Grenze geschlossen?“

Prerequisites

Du kennst Discriminated Unions, switch und useReducer. Die Beispiele beziehen sich auf TypeScript 6.0 und React 19.3. TypeScripts Handbuch dokumentiert Exhaustiveness Checking mit never; React beschreibt Actions als Eingaben, aus denen ein reiner Reducer den nächsten State berechnet.

Der Aha-Effekt

never ist hier keine besondere Runtime-Funktion. TypeScript verengt die Action nach jedem behandelten case. Sind alle Mitglieder einer geschlossenen Union entfernt, bleibt im Default-Zweig never übrig. Ergänzt jemand ein neues Union-Mitglied ohne passenden Case, bleibt genau dieser Typ übrig – und ist nicht mehr never.

Damit wird eine Architekturannahme ausführbar: Dieser Reducer kennt jede Action, die ihn erreichen darf. Ein default: return state macht die gegenteilige Aussage: Unbekannte Actions gehören zum normalen Protokoll und sollen ignoriert werden. Beide Entscheidungen können richtig sein, aber nicht gleichzeitig an derselben Grenze.

So macht man es falsch

Die Union enthält bereits die neue Versand-Action. Weil der Default jeden nicht implementierten Fall akzeptiert, meldet TypeScript keinen Fehler:

import { useReducer } from "react";

type CheckoutState = {
  quantity: number;
  coupon: string | null;
  shipping: "standard" | "express";
};

type CheckoutAction =
  | { type: "quantity.changed"; quantity: number }
  | { type: "coupon.applied"; code: string }
  | { type: "shipping.selected"; mode: "standard" | "express" };

function checkoutReducer(
  state: CheckoutState,
  action: CheckoutAction
): CheckoutState {
  switch (action.type) {
    case "quantity.changed":
      return { ...state, quantity: action.quantity };
    case "coupon.applied":
      return { ...state, coupon: action.code };
    default:
      return state; // shipping.selected wird lautlos ignoriert
  }
}

export function Checkout() {
  const [state, dispatch] = useReducer(checkoutReducer, {
    quantity: 1, coupon: null, shipping: "standard"
  });
  return <button onClick={() => dispatch({
    type: "shipping.selected", mode: "express"
  })}>Express: {state.shipping}</button>;
}

Warum ist das falsch?

Der Typ des Dispatches und der Typ des Reducers versprechen, dass shipping.selected Teil des internen Protokolls ist. Der Default-Zweig hebt diese Zusage semantisch wieder auf. Das beobachtbare Symptom ist besonders tückisch: kein Crash, keine TypeScript-Diagnose, nur unveränderter State.

Ein Test für die Versandart würde den Fehler finden, aber erst nachdem jemand den Test geschrieben und ausgeführt hat. Exhaustiveness verschiebt die Rückmeldung an die Stelle, an der die Union erweitert wird. Sie ersetzt keine Verhaltenstests; sie verhindert eine ganze Klasse vergessener Verzweigungen.

So macht man es richtig mit Trade-offs

Für den lokalen Checkout ist die Action-Union geschlossen. Jeder Case wird implementiert, und ein assertNever markiert die Restmenge als unmöglich:

import { useReducer } from "react";

type CheckoutState = {
  quantity: number;
  coupon: string | null;
  shipping: "standard" | "express";
};

type CheckoutAction =
  | { type: "quantity.changed"; quantity: number }
  | { type: "coupon.applied"; code: string }
  | { type: "shipping.selected"; mode: "standard" | "express" };

function assertNever(value: never): never {
  throw new Error(`Unbekannte Checkout-Action: ${JSON.stringify(value)}`);
}

export function checkoutReducer(
  state: CheckoutState,
  action: CheckoutAction
): CheckoutState {
  switch (action.type) {
    case "quantity.changed":
      return { ...state, quantity: action.quantity };
    case "coupon.applied":
      return { ...state, coupon: action.code };
    case "shipping.selected":
      return { ...state, shipping: action.mode };
    default:
      return assertNever(action);
  }
}

export function Checkout() {
  const [state, dispatch] = useReducer(checkoutReducer, {
    quantity: 1, coupon: null, shipping: "standard"
  });
  return <button onClick={() => dispatch({
    type: "shipping.selected", mode: "express"
  })}>Express: {state.shipping}</button>;
}

Entfernst du jetzt den Versand-Case oder ergänzt eine vierte Action, ist action im Default nicht mehr never; TypeScript meldet die unvollständige Behandlung. Die Runtime-Exception bleibt sinnvoll, falls untypisiertes JavaScript oder eine fehlerhafte Assertion die Grenze umgeht.

Der Trade-off ist Strenge. Kommen Events aus postMessage, WebSocket oder einer Plugin-Schnittstelle, ist die Welt offen. Übergib dort kein gecastetes unknown direkt an den Domain-Reducer. Validiere zuerst und übersetze bekannte Nachrichten in CheckoutAction; unbekannte Nachrichten darf die äußere Integrationsschicht protokollieren oder ignorieren. Muss der Reducer selbst fremde Actions akzeptieren, ist default: return state Teil seines offenen Vertrags.

Eine Alternative ist ein Switch ohne Default zusammen mit explizitem Rückgabetyp und noImplicitReturns. Das kann fehlende Pfade melden, ist aber weniger lokal und hängt an der Compiler-Konfiguration. Eine Handler-Map kann ebenfalls exhaustiv typisiert werden, lohnt sich jedoch eher, wenn Handler als Daten konfiguriert werden.

Diagramm

Fallstricke am Rand

  • action as never beseitigt die Prüfung und macht assertNever wertlos.
  • Ein zu breiter Diskriminator wie type: string kann nicht exhaustiv verengt werden; verwende Literaltypen.
  • Reducer müssen rein bleiben. Logging oder Telemetrie für unbekannte externe Events gehört an die Integrationsgrenze.

Selbst ausprobieren

Nimm dir zehn Minuten und kopiere die korrekte Variante in den TypeScript Playground mit Version 6.0. Ergänze { type: "gift.wrap.toggled"; enabled: boolean } zur Union, aber noch keinen Case. Erwartung: Der Fehler erscheint bei assertNever(action). Implementiere danach den Case; der Fehler verschwindet. Übergib zur Laufzeit testweise ein unbekanntes Objekt aus JavaScript und beobachte die bewusste Exception.

Prüfstand: Die drei bekannten Übergänge und der Runtime-Fehler für eine unbekannte Action wurden mit Node ausgeführt. HTML-Struktur, Diagrammanzahl und Codeklammern wurden geprüft. Ein TypeScript-Compile- oder React-Integrationstest war lokal nicht verfügbar und wird nicht behauptet.

Verwandte Themen

Runtime-Validierung schließt offene Eingabegrenzen. Discriminated State Unions verhindern unmögliche Zustandskombinationen. Command-Handler-Maps bilden exhaustive Verteilung als Daten ab. Reducer-Tests prüfen die fachlichen Ergebnisse jedes erlaubten Übergangs.
