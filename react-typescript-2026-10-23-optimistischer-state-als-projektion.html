Optimistischer State ist eine Projektion, keine zweite Wahrheit

Ein Rollback auf einen alten Array-Snapshot wirkt sicher – bis zwei Mutationen gleichzeitig laufen.

23.10.2026 · React-State-Modellierung · React 19.3 · Tief · ~8 min

Du legst zwei Aufgaben schnell hintereinander an. Die zweite Anfrage gelingt, die erste scheitert. Trotzdem verschwindet anschließend auch die erfolgreiche Aufgabe aus der Liste. Der Server kennt sie, erst ein Reload bringt sie zurück. Das Problem ist nicht „Optimistic UI“ an sich, sondern ein State-Modell, das vorläufige und bestätigte Daten in demselben veränderlichen Verlauf vermischt.

TL;DR

Behandle bestätigten Serverzustand als Basis und optimistische Änderungen als temporäre Projektion darüber. Ein Snapshot-Rollback kann neuere Erfolge überschreiben. useOptimistic modelliert stattdessen die sichtbare Variante während einer Action; endet sie mit einem Fehler, fällt die Ansicht auf den dann aktuellen bestätigten Wert zurück. Das ersetzt keine Cache- oder Konfliktstrategie, macht aber die Besitzverhältnisse im lokalen State explizit.

Prerequisites

Du kennst Hooks, funktionale Updater und asynchrone Formularaktionen. Die offizielle Versionsseite führt React 19.3. Relevant sind die Referenzen zu useOptimistic und zu React-Formularaktionen. Das Beispiel setzt ein React-TypeScript-Projekt mit strict, DOM-Typen und einer Funktion createTodo voraus, die entweder das gespeicherte Todo liefert oder einen Fehler wirft.

Der Aha-Effekt

Optimistischer State ist kein zweiter Datenspeicher. Er beantwortet eine engere Frage: „Wie sähe die bestätigte Basis aus, wenn diese noch laufenden Absichten bereits gelungen wären?“ Daraus folgt eine andere Rollback-Semantik. Bei einem Fehler stellst du keinen alten Gesamtzustand wieder her; du entfernst nur die fehlgeschlagene Absicht aus der Projektion.

React beschreibt useOptimistic(value, updateFn) genau in diesen Begriffen: Ohne laufende Action entspricht der Rückgabewert der Basis. Während einer Action entsteht er durch die reine Update-Funktion. Der entscheidende Architekturgewinn liegt daher weniger in einer kurzen Hook-API als in der Trennung zwischen bestätigtem Besitz und vorläufiger Darstellung.

So macht man es falsch

Die folgende Variante ist realistisch: Sie zeigt sofort eine Zeile und merkt sich für den Fehlerfall den bisherigen Array-Wert.

import { useState } from "react";
import { createTodo } from "./todo-api";

type Todo = { id: string; title: string; pending?: boolean };

export function TodoList({ initialTodos }: { initialTodos: Todo[] }) {
  const [todos, setTodos] = useState(initialTodos);
  const [error, setError] = useState<string | null>(null);

  async function add(title: string) {
    const snapshot = todos;
    const temporary = {
      id: crypto.randomUUID(), title, pending: true
    };
    setTodos([...todos, temporary]);

    try {
      const saved = await createTodo({ title });
      setTodos(current =>
        current.map(todo => todo.id === temporary.id ? saved : todo)
      );
    } catch {
      setTodos(snapshot);
      setError("Aufgabe konnte nicht gespeichert werden.");
    }
  }

  // Formular und Liste verwenden add() beziehungsweise todos.
}

Warum ist das falsch?

Angenommen, Action A merkt sich [Alt] und fügt „A“ vorläufig hinzu. Action B startet danach mit [Alt, A?]. B gelingt und ersetzt ihre temporäre Zeile durch „B“. Wenn A später scheitert, schreibt ihr Catch-Block trotzdem den älteren Snapshot [Alt]. Damit löscht er den Erfolg von B aus dem lokalen State.

Funktionale Updater in den Erfolgszweigen beheben das nicht. Das Problem liegt im Rollback: Ein kompletter Snapshot trägt keine Information darüber, welche Änderung rückgängig gemacht werden soll. Beobachtbar sind verschwundene Erfolge, ein UI, das vom Server abweicht, und Fehler, die nur bei bestimmter Antwortreihenfolge auftreten. Eine künstliche Serialisierung würde den Fehler vermeiden, aber auch unabhängige Eingaben unnötig blockieren.

So macht man es richtig mit Trade-offs

Halte die vom Server bestätigten Einträge separat. Die Action ergänzt nur die optimistische Projektion. Weil sie als action des Formulars läuft, darf sie den optimistischen Setter aufrufen. Laut React muss dessen Update-Funktion rein sein.

import { useOptimistic, useState } from "react";
import { createTodo } from "./todo-api";

type Todo = { id: string; title: string };
type VisibleTodo = Todo & { pending: boolean };
type AddTodo = { clientId: string; title: string };
type Props = { initialTodos: Todo[] };

function projectTodo(
  current: VisibleTodo[],
  addition: AddTodo
): VisibleTodo[] {
  return [
    ...current,
    { id: addition.clientId, title: addition.title, pending: true }
  ];
}

export function TodoList({ initialTodos }: Props) {
  const [confirmed, setConfirmed] = useState<VisibleTodo[]>(
    initialTodos.map(todo => ({ ...todo, pending: false }))
  );
  const [visible, addOptimistic] = useOptimistic(
    confirmed,
    projectTodo
  );
  const [error, setError] = useState<string | null>(null);

  async function submit(formData: FormData) {
    const title = String(formData.get("title") ?? "").trim();
    if (!title) return;

    const clientId = crypto.randomUUID();
    setError(null);
    addOptimistic({ clientId, title });

    try {
      const saved = await createTodo({ title });
      setConfirmed(current => [
        ...current,
        { ...saved, pending: false }
      ]);
    } catch {
      setError("Aufgabe konnte nicht gespeichert werden.");
    }
  }

  return (
    <>
      <form action={submit}>
        <label>Neue Aufgabe <input name="title" required /></label>
        <button type="submit">Anlegen</button>
      </form>
      {error && <p role="alert">{error}</p>}
      <ul>
        {visible.map(todo => (
          <li key={todo.id} aria-busy={todo.pending}>
            {todo.title}{todo.pending ? " – wird gespeichert" : ""}
          </li>
        ))}
      </ul>
    </>
  );
}

Gelingt die Anfrage, erweitert sie die Basis. Scheitert sie, endet die Action; React zeigt wieder die zu diesem Zeitpunkt aktuelle Basis, in der parallele Erfolge bereits enthalten sein können. Der Preis ist, dass du bestätigte Daten weiterhin korrekt fortschreiben und Fehler sichtbar machen musst. Außerdem kann eine serverseitig vergebene ID dazu führen, dass die vorläufige Zeile durch eine neue bestätigte Zeile ersetzt wird.

Als Alternative bietet sich eine Daten- oder Cache-Bibliothek mit optimistischen Mutationen an, sobald mehrere Komponenten dieselben Entitäten lesen, Invalidierung nötig ist oder Offline-Warteschlangen entstehen. Sie zentralisiert Abgleich und Rollback, bringt aber eigene Cache-Schlüssel, Lebenszyklen und Fehlerregeln mit. Für einen lokal besessenen Formular-State ist die Projektion oft die kleinere Abstraktion.

Diagramm

Fallstricke am Rand

  • Rufe den optimistischen Setter innerhalb einer Action auf, etwa über eine Formular-Action oder startTransition. Außerhalb warnt React und der optimistische Zustand kann nur kurz erscheinen.
  • Die Projektionsfunktion darf weder IDs erzeugen noch Requests starten. Solche Seiteneffekte gehören vor ihren Aufruf beziehungsweise in die Action.
  • Ein Erfolg braucht weiterhin eine fachliche Konfliktregel. Wenn der Server Titel normalisiert oder Duplikate zusammenführt, ist seine Antwort maßgeblich.

Selbst ausprobieren

Nimm dir zehn Minuten und verzögere zwei createTodo-Aufrufe gezielt. Lass B nach 100 Millisekunden gelingen und A nach 500 Millisekunden scheitern. Erwartung bei der Snapshot-Variante: B verschwindet lokal. Erwartung bei der Projektionsvariante: Während beide laufen sind A und B sichtbar; nach den Antworten verschwindet nur A, B bleibt als bestätigter Eintrag stehen. Kehre danach die Reihenfolge um und prüfe denselben Invariant.

Prüfstand: Die beschriebene Reihenfolge wurde mit einem ausführbaren Zustandsmodell geprüft. Es bestätigt die Rollback-Kausalität, ersetzt aber keinen Browser- oder React-Integrationstest. Der TSX-Ausschnitt wurde in dieser Umgebung nicht kompiliert; ein bestandener Compile-Test wird nicht behauptet.

Verwandte Themen

Idempotente Mutationen verhindern doppelte Servereinträge bei Wiederholungen. Client-generierte Korrelations-IDs verbinden vorläufige und bestätigte Entitäten. Cache-Invalidierung wird relevant, sobald mehrere Leser dieselbe Basis besitzen. Property-basierte Tests können unterschiedliche Abschlussreihenfolgen systematisch gegen den Invariant prüfen.
