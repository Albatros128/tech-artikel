Ein Ref sollte Fähigkeiten freigeben, nicht den DOM-Knoten

Eine schmale imperative API schützt State-Invarianten und hält die interne Darstellung austauschbar.

10.11.2026 · React-Komponenten-APIs · React 19.3 · Tief · ~8 min

Eine Suchkomponente verwaltet ihren Text selbst. Nach dem Absenden will die übergeordnete Seite das Feld leeren und erneut fokussieren. Also reicht die Komponente ihren <input>-Knoten per Ref nach außen. Der Aufrufer setzt ref.current.value = "". Im Browser wirkt das zunächst korrekt – bis ein späterer Render den alten React-State wieder in das kontrollierte Feld schreibt. Die sichtbare Leere war nie Teil des Zustandsmodells.

TL;DR

Ein öffentlicher Ref ist eine Komponenten-API. Wenn du den DOM-Knoten weiterreichst, veröffentlichst du mehr Operationen als beabsichtigt: Wert, Styles, Attribute und Struktur lassen sich außerhalb der State-Logik verändern. Behalte den Knoten intern und expose mit useImperativeHandle nur fachlich erlaubte Befehle wie focus() und clear(). Zustände, die sich als Props ausdrücken lassen, bleiben dagegen deklarativ.

Prerequisites

Du kennst kontrollierte Eingaben, useState und useRef. Die Beispiele beziehen sich auf React 19.3. Seit React 19 ist ref als Prop verfügbar; für React 18 und älter brauchst du forwardRef. Die API und ihre Abhängigkeitsregeln beschreibt die offizielle Referenz zu useImperativeHandle.

Der Aha-Effekt

Die Frage lautet nicht: „Welches Element steckt in der Komponente?“, sondern: „Was darf ein Aufrufer mit ihr tun?“ Ein Ref, der auf HTMLInputElement zeigt, koppelt Consumer an eine Implementierung. Ein Ref vom Typ SearchFieldHandle definiert dagegen ein Protokoll. Die Komponente darf später ein anderes Eingabeelement verwenden, Fokus intern umleiten oder beim Leeren zusätzlich Validierungszustand zurücksetzen.

React setzt Refs in der Commit-Phase. Sie sind ein Escape Hatch für imperative Aktionen wie Fokus, Scrollen oder Selektion, nicht ein zweiter Datenkanal neben Props und State. Diese Trennung ist der eigentliche Architekturgewinn; useImperativeHandle ist nur das Werkzeug dafür.

So macht man es falsch

Die folgende React-19-Komponente veröffentlicht ihren DOM-Knoten. Der Elternteil kann dadurch den kontrollierten Wert am State vorbei verändern:

// Ausschnitt: SearchPage.tsx
import { type Ref, useRef, useState } from "react";

function SearchField({ ref }: { ref?: Ref<HTMLInputElement> }) {
  const [value, setValue] = useState("Ada");

  return (
    <input
      ref={ref}
      value={value}
      onChange={event => setValue(event.currentTarget.value)}
    />
  );
}

export function SearchPage() {
  const fieldRef = useRef<HTMLInputElement>(null);

  function resetAfterSubmit() {
    if (!fieldRef.current) return;
    fieldRef.current.value = ""; // DOM leer, State weiterhin "Ada"
    fieldRef.current.focus();
  }

  return <SearchField ref={fieldRef} />;
}

Warum ist das falsch?

Die direkte Zuweisung ändert laut MDN den aktuellen Wert des DOM-Elements. Sie ruft aber weder den React-Handler auf noch aktualisiert sie value im Komponenten-State. Beim nächsten Render gleicht React das DOM wieder an seine Ausgabe an: „Ada“ erscheint erneut. Das Symptom wirkt zufällig, weil irgendein unabhängiges Update den Rücksprung auslösen kann.

Zusätzlich ist der Consumer nun von HTMLInputElement abhängig. Ein Wechsel auf eine zusammengesetzte Autocomplete-Struktur wird zur Breaking Change. React warnt generell davor, von React verwaltete DOM-Knoten destruktiv zu verändern, weil dadurch inkonsistente Darstellung oder Fehler entstehen können.

So macht man es richtig mit Trade-offs

Definiere eine minimale Handle-Schnittstelle. Die Komponente führt jede Mutation durch ihre eigene State-Grenze und kapselt den echten Knoten:

// Vollständiger Komponentenausschnitt für React 19
import {
  type Ref,
  useImperativeHandle,
  useRef,
  useState,
} from "react";

export type SearchFieldHandle = {
  focus(): void;
  clear(): void;
};

type SearchFieldProps = {
  ref?: Ref<SearchFieldHandle>;
};

export function SearchField({ ref }: SearchFieldProps) {
  const inputRef = useRef<HTMLInputElement>(null);
  const [value, setValue] = useState("Ada");

  useImperativeHandle(ref, () => ({
    focus: () => inputRef.current?.focus(),
    clear: () => setValue(""),
  }), []);

  return (
    <input
      ref={inputRef}
      value={value}
      onChange={event => setValue(event.currentTarget.value)}
    />
  );
}

export function SearchPage() {
  const fieldRef = useRef<SearchFieldHandle>(null);

  function resetAfterSubmit() {
    fieldRef.current?.clear();
    fieldRef.current?.focus();
  }

  return <SearchField ref={fieldRef} />;
}

Der Trade-off ist eine zusätzliche API, die versioniert und getestet werden muss. Wenn der Elternteil den Suchtext ohnehin fachlich besitzt, ist die bessere Alternative eine kontrollierte Komponente mit value und onChange; dann wird „Leeren“ als Prop-Änderung modelliert und nur der Fokus bleibt imperativ. React empfiehlt ausdrücklich, per Prop ausdrückbare Zustände nicht hinter Ref-Methoden zu verstecken.

Diagramm

Fallstricke am Rand

  • Handle-Methoden dürfen nicht während des Renderns aufgerufen werden; Refs werden erst beim Commit gesetzt.
  • Reaktive Werte, die ein Handle verwendet, gehören in die Dependency-Liste von useImperativeHandle.
  • Ein Handle ist kein Ersatz für disabled, value oder andere deklarative Zustands-Props.

Selbst ausprobieren

Setze in der Fehlervariante den DOM-Wert auf leer und löse danach mit einem zusätzlichen Counter-State einen Render aus. Beobachtung: „Ada“ kehrt zurück. Ersetze anschließend den Ref-Typ durch SearchFieldHandle und rufe clear() auf; der Wert bleibt leer, weil State und DOM übereinstimmen. Die Übung dauert etwa zehn Minuten. Ein vollständiger React-DOM-Integrationstest wurde lokal nicht ausgeführt; die Aussage folgt dem dokumentierten Modell kontrollierter DOM-Ausgabe.

Verwandte Themen

Controlled versus uncontrolled Components entscheidet, wem der Wert gehört. Fokusmanagement verbindet imperative Handles mit Accessibility. Ref-Callbacks eignen sich für dynamische Knotenmengen. Komponenten-SemVer behandelt Handle-Methoden als öffentliche Oberfläche statt als Implementierungsdetail.
