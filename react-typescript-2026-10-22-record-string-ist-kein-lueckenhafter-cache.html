Record<string, T> ist kein lückenhafter Cache

Wer beliebige String-Schlüssel als vorhanden typisiert, versteckt genau den Cache-Miss, den der aufrufende Code behandeln müsste.

22.10.2026 · TypeScript-Typsystem · TypeScript 7.0 · Tief · ~8 min

Ein Profil-Cache ist beim Start leer. Trotzdem behauptet die Signatur von getCachedUser, für jede beliebige ID einen User zu liefern. Im Editor sieht alles sauber aus. Erst der erste Cache-Miss produziert Cannot read properties of undefined.

Der Fehler liegt nicht im Cache-Algorithmus, sondern im Typvertrag: Record<string, User> beschreibt keine möglicherweise lückenhafte Tabelle.

TL;DR

Record<K, V> ordnet jedem Schlüssel aus K einen Wert V zu. Ist K eine endliche Union, ist das ideal für eine vollständige Zuordnung. Ist K dagegen string, wirkt der Typ wie eine Index-Signatur und kann ohne zusätzliche Prüfung einen vorhandenen Wert suggerieren. Modelliere einen Cache als Partial<Record<string, V>>, als Map<string, V> oder aktiviere noUncheckedIndexedAccess.

Prerequisites

Du solltest Indexzugriffe, Union-Typen und Narrowing kennen. Relevant sind die offiziellen Seiten zu Record, Index Signatures und noUncheckedIndexedAccess. Der Versionsbezug ist die stabile Veröffentlichung von TypeScript 7.0 vom 8. Juli 2026.

Der Aha-Effekt

Der Schlüsseltyp entscheidet über die Vollständigkeit des Vertrags. Record<"admin" | "editor", View> verlangt zwei bekannte Einträge und ist dafür präzise. Record<string, User> hat keine endliche Schlüsselmenge, die der Compiler beim Objektliteral abhaken könnte. Beim Lesen über einen beliebigen String liefert der Typ deshalb den deklarierten Werttyp – sofern keine strengere Option eingreift.

Ein Cache besitzt aber absichtlich nur eine Teilmenge aller möglichen IDs. „Für diesen Schlüssel existiert vielleicht ein Wert“ ist Teil seiner Domäne und gehört in den Rückgabetyp.

So macht man es falsch

Die folgende Implementierung ist realistisch: Schreiben funktioniert, und die Rückgabesignatur wirkt bequem. Ohne noUncheckedIndexedAccess wird der fehlende Zweig jedoch aus dem Vertrag gelöscht.

Warum ist das falsch?

Die Utility-Dokumentation definiert Record<Keys, Type> als Objekttyp, dessen Schlüssel Keys und dessen Werte Type sind. Bei einer Index-Signatur beschreibt TypeScript den Rückgabetyp des Indexzugriffs. JavaScript prüft diese Behauptung nicht: Ein nicht vorhandener Property-Key ergibt weiterhin undefined.

Damit entsteht eine Lücke zwischen Compile-Time und Runtime. Die explizite Rückgabe User macht sie sogar zu einem öffentlichen API-Versprechen. Ein Non-Null-Assertion-Operator würde das Problem nur verdecken; er erzeugt keinen Cache-Eintrag.

So macht man es richtig mit Trade-offs

Formuliere die Lücke dort, wo sie fachlich entsteht. Eine sparsame Objektstruktur kann sie direkt im Typ tragen:

findCachedUser erlaubt dem Aufrufer, selbst zu laden oder einen leeren Zustand zu zeigen. requireCachedUser ist eine bewusste Alternative für Codepfade, in denen ein Miss eine verletzte Vorbedingung darstellt. Eine Map<string, User> modelliert dieselbe Unsicherheit über get(): User | undefined bereits in ihrer API. Dafür ist ein Objekt einfacher als JSON zu serialisieren; eine Map braucht eine explizite Konvertierung.

Als projektweite Leitplanke ergänzt "noUncheckedIndexedAccess": true bei nicht deklarierten Indexzugriffen undefined. Das schützt auch andere Dictionaries und Arrayzugriffe, kann in einem bestehenden Codebestand aber viele Stellen gleichzeitig aufdecken. Der lokale, ehrliche Datentyp bleibt deshalb wertvoll – selbst wenn die Option aktiviert ist.

Der Cache-Miss ist kein exotischer Fehlerpfad, sondern ein reguläres Ergebnis des Lesens. Der Typ sollte die Verzweigung sichtbar machen, bevor ein Property-Zugriff stattfindet.

Fallstricke am Rand

  • Endliche Union: Bei bekannten Schlüsseln ist Record<Role, View> gerade wegen seiner Vollständigkeit passend. Verwende dort nicht reflexhaft Partial.
  • Gespeichertes undefined: Soll undefined selbst ein Cache-Wert sein, reicht der Rückgabewert nicht zur Unterscheidung; nutze has bei einer Map oder ein eigenes Ergebnisobjekt.
  • Objekt-Schlüssel: Nutze für ein Dictionary ohne Prototyp gegebenenfalls Object.create(null) oder eine Map. Das Typproblem und das Laufzeitobjekt sind getrennte Entscheidungen.

Selbst ausprobieren

Kopiere die Fehlervariante in ein kleines Projekt und fahre mit der Maus über usersById[id]. Aktiviere danach noUncheckedIndexedAccess in der tsconfig.json. Erwartete Beobachtung: Der Zugriff wechselt von User zu User | undefined, und die Rückgabe von getCachedUser ist nicht mehr zulässig. Ersetze anschließend den Typ durch Partial<Record<string, User>> und prüfe, dass der Miss auch ohne versteckte Annahme im Funktionsvertrag steht.

Der Laufzeitfall wurde mit Node.js 24 geprüft: Ein unbekannter Schlüssel liefert undefined, der direkte Property-Zugriff wirft. Ein TypeScript-7-Compiler war lokal nicht installiert; ein bestandener Typecheck wird daher nicht behauptet.

Verwandte Themen

Branded IDs verhindern das Vermischen verschiedener String-Identitäten. Runtime-Validierung schützt Cache-Einträge an der Netzwerkgrenze. Discriminated Unions können Treffer, Miss und Fehler explizit benennen. Negative Caching unterscheidet „nicht geladen“ von „nachweislich nicht vorhanden“. Eviction-Strategien definieren, wann ein vorhandener Eintrag wieder verschwindet.
