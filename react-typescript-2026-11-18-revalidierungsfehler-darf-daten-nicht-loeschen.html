Ein Revalidierungsfehler darf brauchbare Daten nicht löschen

Der Zustand deiner Daten ist nicht derselbe wie der Zustand des letzten Ladeversuchs.

Datenzugriff & State-Modellierung · React 19.2 + Fetch API · Tief · ~8 min

Eine Produktliste ist geladen. Beim Zurückkehren in den Tab startet ein Hintergrund-Refresh, das WLAN bricht kurz ab – und die gesamte Liste wird durch „Laden fehlgeschlagen“ ersetzt. Der Server hat keine Daten widerrufen. Nur der jüngste Aktualisierungsversuch ist gescheitert.

TL;DR

Modelliere „nutzbare Daten vorhanden?“ getrennt von „Request läuft oder ist fehlgeschlagen?“. Ein Fehler beim initialen Laden ist ein blockierender Zustand. Ein Fehler bei der Revalidierung ist dagegen Metadatum zu weiterhin nutzbaren, nun möglicherweise veralteten Daten. Behalte diese Daten sichtbar und biete einen erneuten Versuch an.

Prerequisites

Du solltest React-State strukturiert modellieren, useReducer einsetzen und Requests mit der Fetch API ausführen können. Der Versionsbezug ist React 19.2; die Entscheidung selbst ist nicht an eine spezielle React-API gebunden.

Der Aha-Effekt

„Fehler“ beantwortet nur, wie ein Versuch endete. Er beantwortet nicht, ob darstellbare Daten existieren. Bei der ersten Anfrage fallen beide Fragen zusammen. Nach einem erfolgreichen Laden können sie auseinanderlaufen: Die Daten sind vorhanden, während die Revalidierung läuft oder scheitert.

Eigene Schlussfolgerung: Ein State-Modell sollte den sichtbaren Informationsbestand beschreiben, nicht bloß den Lebenszyklus des zuletzt gestarteten Promises.

So macht man es falsch

Diese übliche Union ist für ein einmaliges Laden korrekt. Sobald dieselbe Funktion auch einen Hintergrund-Refresh ausführt, vernichtet loading beziehungsweise error die Information, dass bereits Daten vorhanden waren.

// Ausschnitt: Fehlervariante
type LoadState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; error: Error };

const asError = (value: unknown): Error =>
  value instanceof Error ? value : new Error(String(value));

async function refresh() {
  setState({ status: "loading" });
  try {
    const response = await fetch("/api/products");
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    setState({ status: "success", data: await response.json() });
  } catch (error) {
    setState({ status: "error", error: asError(error) });
  }
}

if (state.status === "loading") return <Spinner />;
if (state.status === "error") return <FullPageError />;

Warum ist das falsch?

Der zweite Request ersetzt den gesamten fachlichen Zustand durch einen Transportzustand. Dadurch flackert die Oberfläche schon während des Refreshs; bei einem Fehler verschwinden Daten, die wenige Millisekunden zuvor noch als gültig galten. React empfiehlt, widersprüchliche oder unnötig duplizierte Zustände durch eine passende State-Struktur zu vermeiden. Hier ist das Problem umgekehrt: Eine einzige Achse wurde zu stark vereinfacht.

Auch fetch() macht diese Unterscheidung nicht für dich. Laut MDN wird sein Promise bei HTTP-Fehlerstatus wie 404 nicht automatisch abgelehnt; Response.ok muss geprüft werden. Ob ein solcher Fehler vorhandene Daten unbrauchbar macht, bleibt eine fachliche Entscheidung.

So macht man es richtig

Die Union unterscheidet initiales Scheitern von einer fehlgeschlagenen Revalidierung. Im ready-Zweig bleiben die Daten immer erhalten; Request-Metadaten verändern nur die Darstellung daneben.

import { useReducer } from "react";

type ResourceState<T> =
  | { status: "initial-loading" }
  | { status: "initial-error"; error: Error }
  | {
      status: "ready";
      data: T;
      refreshing: boolean;
      refreshError?: Error;
    };

type Action<T> =
  | { type: "requested" }
  | { type: "succeeded"; data: T }
  | { type: "failed"; error: Error };

function reducer<T>(
  state: ResourceState<T>,
  action: Action<T>
): ResourceState<T> {
  switch (action.type) {
    case "requested":
      return state.status === "ready"
        ? { ...state, refreshing: true, refreshError: undefined }
        : { status: "initial-loading" };
    case "succeeded":
      return { status: "ready", data: action.data, refreshing: false };
    case "failed":
      return state.status === "ready"
        ? { ...state, refreshing: false, refreshError: action.error }
        : { status: "initial-error", error: action.error };
  }
}

Ein Reducer ist nicht zwingend; dieselbe Invariante lässt sich mit einem Query-Cache oder einer kleineren Union abbilden. Der Trade-off sind mehr Zustände und eine bewusste UI für „veraltet, Refresh fehlgeschlagen“. Dafür bleibt der Informationsverlust ausgeschlossen. Wenn Daten aus Sicherheits- oder Korrektheitsgründen nach Ablauf zwingend frisch sein müssen, ist das Ausblenden eine legitime Alternative – dann sollte die Gültigkeitsfrist Teil des Modells sein.

Diagramm

Fallstricke am Rand

  • Ein AbortError beim Unmount ist kein anzuzeigender Refresh-Fehler.
  • Alte Daten brauchen eine erkennbare Aktualisierungszeit, wenn ihre Frische fachlich relevant ist.
  • Ein erfolgreicher leerer Datensatz ist nicht dasselbe wie „noch keine Daten“.

Selbst ausprobieren

Baue in zehn Minuten einen Reducer-Test: Starte mit initial-loading, dispatch danach succeeded mit zwei Produkten, anschließend requested und failed. Erwartung: Der Endzustand ist weiterhin ready, enthält beide Produkte und zusätzlich refreshError. Wiederhole denselben Fehler ohne vorherigen Erfolg; nun muss initial-error entstehen.

Verwandte Themen

  • Stale-while-revalidate: Ein Cache kann alte Daten sofort liefern und parallel aktualisieren.
  • Error Boundaries: Sie behandeln Renderfehler, nicht automatisch asynchrone Fetch-Fehler.
  • Request-Abbruch: AbortController verhindert unnötige Arbeit, ersetzt aber keine State-Invariante.
  • Observability: Hintergrundfehler sollten messbar bleiben, auch wenn die UI weiterhin Daten zeigt.
