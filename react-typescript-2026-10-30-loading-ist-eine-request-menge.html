Loading ist eine Menge laufender Requests, kein Boolean

Zwei korrekte finally-Blöcke können gemeinsam einen falschen Ladezustand erzeugen.

30.10.2026 · Datenzugriff & Race Conditions · React 19.3 + TypeScript 6.0 · Tief · ~8 min

Ein Nutzer startet den CSV-Export und aktualisiert direkt danach die Bestellliste. Der Export ist schnell fertig, die Liste lädt noch. Trotzdem verschwindet der globale Spinner und beide Buttons werden wieder aktiv. Kein Request ist fehlgeschlagen. Das UI lügt, weil der erste abgeschlossene Request einen Zustand beendet, den der zweite weiterhin benötigt.

TL;DR

Ein gemeinsames isLoading darf bei parallelen Operationen nicht von jedem Request unabhängig auf false gesetzt werden. Modelliere stattdessen die Identitäten aller laufenden Operationen und leite isLoading aus pending.size > 0 ab. Ein Zähler ist möglich, eine Menge ist robuster gegen doppelte Abschlussereignisse und besser diagnostizierbar. Das löst den Ladeindikator, nicht automatisch veraltete Antwortdaten oder Abbruch.

Prerequisites

Du kennst Promises, async/await und React Hooks. Die Beispiele beziehen sich auf die aktuelle React-Version 19.3 und TypeScript 6.0. Relevant sind useReducer für den sichtbaren Zustand, useRef für eine renderunabhängige Sequenznummer und das dokumentierte Verhalten von Promise.prototype.finally.

Der Aha-Effekt

isLoading sieht wie ein primitiver Zustand aus, ist aber meist eine abgeleitete Frage: „Existiert mindestens eine relevante, noch nicht abgeschlossene Operation?“ Bei genau einem Request sind Boolean und Menge äquivalent. Sobald sich Lebenszeiten überlappen, verliert der Boolean die Information, welcher Request ihn gesetzt hat.

Das Problem liegt nicht in finally. Laut MDN läuft es nach Erfüllung oder Ablehnung und eignet sich genau für Cleanup. Falsch ist nur die Cleanup-Aktion: setLoading(false) behauptet, dass keine Operation mehr läuft, obwohl der Callback lediglich über seine eigene Operation Bescheid weiß.

So macht man es falsch

In einer Toolbar teilen Aktualisierung und Export denselben Ladezustand. Beide Funktionen sind einzeln plausibel und setzen ihn zuverlässig zurück:

import { useState } from "react";
import { exportOrders, loadOrders, type Order } from "./orders-api";

export function OrdersToolbar() {
  const [orders, setOrders] = useState<Order[]>([]);
  const [isLoading, setLoading] = useState(false);

  async function refresh(): Promise<void> {
    setLoading(true);
    try {
      setOrders(await loadOrders());
    } finally {
      setLoading(false);
    }
  }

  async function exportCsv(): Promise<void> {
    setLoading(true);
    try {
      await exportOrders();
    } finally {
      setLoading(false);
    }
  }

  return <div aria-busy={isLoading}>
    <button onClick={refresh}>Aktualisieren</button>
    <button onClick={exportCsv}>CSV exportieren</button>
    <span>{orders.length} Bestellungen</span>
  </div>;
}

Warum ist das falsch?

Startet A vor B und endet A zuerst, schreibt A false, obwohl B noch pending ist. Die Reihenfolge der Abschlüsse ist legitimes asynchrones Verhalten, kein Sonderfall. Sichtbare Symptome sind flackernde Spinner, zu früh aktivierte Aktionen und irreführendes aria-busy="false".

Mehrere setLoading(true)-Aufrufe helfen nicht: Ein Boolean speichert keine Multiplizität. Auch automatisches React-Batching ändert die Semantik nicht. Das Modell kann die Information „zwei Operationen laufen“ schlicht nicht ausdrücken.

So macht man es richtig mit Trade-offs

Der Tracker vergibt pro Aufruf eine Identität. Ein reiner Reducer hält eine neue Set-Instanz, damit React eine Zustandsänderung erkennen kann. Die Sequenznummer liegt im Ref, weil sie nicht selbst gerendert wird:

import { useReducer, useRef } from "react";

type PendingAction =
  | { type: "started"; id: number }
  | { type: "finished"; id: number };

function pendingReducer(
  state: ReadonlySet<number>,
  action: PendingAction
): ReadonlySet<number> {
  const next = new Set(state);
  if (action.type === "started") next.add(action.id);
  else next.delete(action.id);
  return next;
}

export function useRequestTracker() {
  const [pending, dispatch] = useReducer(
    pendingReducer,
    new Set<number>()
  );
  const nextId = useRef(0);

  async function run<T>(operation: () => Promise<T>): Promise<T> {
    const id = ++nextId.current;
    dispatch({ type: "started", id });
    try {
      return await operation();
    } finally {
      dispatch({ type: "finished", id });
    }
  }

  return {
    run,
    isLoading: pending.size > 0,
    pendingCount: pending.size
  };
}

Der Consumer ruft beispielsweise await run(loadOrders) und await run(exportOrders) auf. Endet A, entfernt der Reducer nur A. B bleibt in der Menge, also bleibt isLoading wahr. Ein doppeltes finished für dieselbe ID dekrementiert nicht versehentlich ein zweites Mal.

Der Trade-off ist zusätzlicher Zustand. Ein einfacher Zähler genügt, wenn jeder Start garantiert genau einen Abschluss besitzt; er ist kürzer, zeigt aber nicht, welche Operation hängt. Für unabhängig dargestellte Bereiche sind getrennte Tracker ehrlicher als ein globaler. Starten alle Operationen bewusst als ein Batch, kann auch Promise.allSettled dessen gemeinsame Lebenszeit modellieren. Eine Datenbibliothek ist sinnvoll, wenn Ladezustand, Cache, Retry und Deduplizierung bereits pro Query verwaltet werden sollen.

Wichtig: Der Tracker entscheidet nicht, welche Antwort Daten schreiben darf. Laden zwei Requests dieselbe Ressource, brauchst du zusätzlich eine fachliche Stale-Response-, Abbruch- oder Versionsstrategie.

Diagramm

Fallstricke am Rand

  • Starte Operationen nicht während des Renderns. Ref-IDs und Dispatch gehören in Event Handler, Effects oder andere kontrollierte Aufrufpfade.
  • Behandle Fehler im Consumer. Der Tracker reicht die ursprüngliche Erfüllung oder Ablehnung transparent weiter.
  • Beim Unmounten brauchst du je nach Operation weiterhin Cleanup oder AbortSignal; eine Pending-Menge ersetzt keine Ressourcenfreigabe.

Selbst ausprobieren

Nimm dir zehn Minuten und ersetze die API-Funktionen durch zwei steuerbare Promises. Starte A, dann B. Löse A zuerst auf und prüfe, dass pendingCount von zwei auf eins fällt und der Spinner sichtbar bleibt. Löse danach B auf; erst jetzt erwartest du null. Sende testweise ein zweites finished für A: Die Menge muss leer bleiben und darf keinen negativen Zustand erzeugen.

Verwandte Themen

AbortController beendet unnötige Arbeit, während der Tracker nur Sichtbarkeit modelliert. Stale-Response-Policies regeln konkurrierende Schreibrechte. Query-Key-Design definiert, welche Requests denselben Zustand teilen. Deterministische Promise-Tests erzwingen die kritische Abschlussreihenfolge.
