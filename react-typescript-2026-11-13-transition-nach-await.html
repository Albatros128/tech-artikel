Nach await braucht dein State-Update eine neue Transition-Grenze

Eine asynchrone Action bleibt pending, doch ihre Fortsetzung erbt nicht automatisch die Render-Priorität.

13.11.2026 · React-Concurrent-Rendering · React 19.3 + TypeScript 6.0 · Tief · ~8 min

Ein Profil-Editor speichert Daten über die API. Während des Requests zeigt der Button „Speichert …“. Nach der Antwort ersetzt die Komponente das Profil durch die Serverfassung. Das Ganze steht bereits in startTransition(async () => ...). Trotzdem behandelt React das abschließende setProfile als dringendes Update. Der Code sieht nach einer einzigen Transition aus, überschreitet aber eine unsichtbare JavaScript-Grenze: await.

TL;DR

React ruft eine Transition-Action sofort auf und markiert State-Updates, die während dieses synchronen Aufrufs geplant werden. Nach einem await läuft die Fortsetzung später weiter; React kann den Transition-Kontext derzeit nicht automatisch über diese Async-Grenze tragen. Umschließe State-Updates nach dem Warten deshalb mit einem weiteren startTransition. Das äußere useTransition liefert weiterhin den Pending-Zustand der Action. Diese Verschachtelung löst jedoch keine Race Conditions und ordnet parallele Requests nicht.

Prerequisites

Du kennst Hooks, Promise-Fortsetzungen und den Unterschied zwischen dringenden und nicht dringenden Updates. Die Beispiele beziehen sich auf die am 13.11.2026 aktuelle Dokumentation für React 19.3 und auf TypeScript 6.0.

Der Aha-Effekt

startTransition färbt nicht die gesamte lexikalische Funktion dauerhaft ein. Entscheidend ist der Zeitpunkt, an dem ein Setter aufgerufen wird. Vor dem ersten await geschieht das innerhalb des synchron ausgeführten Action-Aufrufs. Die Promise-Fortsetzung wird dagegen in einem späteren Job ausgeführt. Laut React-Dokumentation geht der Async-Kontext dabei derzeit verloren.

Darum können zwei Aussagen gleichzeitig stimmen: isPending beschreibt noch die laufende asynchrone Action, aber ein nachgelagertes setState besitzt ohne neue Markierung nicht die Transition-Priorität.

So macht man es falsch

Die realistische Fehlervariante wartet korrekt auf den Server und hält den Button pending. Sie verlässt sich aber darauf, dass die äußere Transition auch das Update nach der Antwort markiert:

// ProfileEditor.tsx – Fehlervariante
import { useState, useTransition } from "react";

type Profile = { id: string; displayName: string };

declare function saveProfile(profile: Profile): Promise<Profile>;

export function ProfileEditor({ initial }: { initial: Profile }) {
  const [profile, setProfile] = useState(initial);
  const [isPending, startTransition] = useTransition();

  function save(next: Profile) {
    startTransition(async () => {
      const saved = await saveProfile(next);
      setProfile(saved); // nicht als Transition markiert
    });
  }

  return (
    <button disabled={isPending} onClick={() => save(profile)}>
      {isPending ? "Speichert …" : "Speichern"}
    </button>
  );
}

Warum ist das falsch?

Transitions sind ein Scheduling-Signal für Rendering, kein allgemeiner Promise-Kontext. React kann ein nicht dringendes Rendering unterbrechen, wenn etwa eine Texteingabe verarbeitet werden muss. Das nach await ausgeführte Update erhält dieses Signal in der Fehlervariante nicht. Bei einem teuren Ergebnis-Teilbaum kann sich die Oberfläche deshalb anders verhalten als beabsichtigt.

Ein häufiger Reparaturversuch ist await startTransition(...). Das funktioniert nicht: Der eigenständige startTransition-Aufruf gibt nichts zurück. useTransition stellt den Pending-Zustand bereit; das Warten gehört innerhalb der Action.

So macht man es richtig mit Trade-offs

Markiere das Update dort, wo es tatsächlich geplant wird. Die äußere Action umfasst den Request und liefert isPending; die innere Transition klassifiziert die State-Änderung nach der Antwort:

// ProfileEditor.tsx – verbesserter Ausschnitt
import { useState, useTransition } from "react";

type Profile = { id: string; displayName: string };
type Props = {
  initial: Profile;
  saveProfile(profile: Profile): Promise<Profile>;
};

export function ProfileEditor({ initial, saveProfile }: Props) {
  const [profile, setProfile] = useState(initial);
  const [isPending, startTransition] = useTransition();

  function save(next: Profile) {
    startTransition(async () => {
      const saved = await saveProfile(next);

      startTransition(() => {
        setProfile(saved);
      });
    });
  }

  return (
    <button disabled={isPending} onClick={() => save(profile)}>
      {isPending ? "Speichert …" : "Speichern"}
    </button>
  );
}

Der Preis ist sichtbare Verschachtelung. Für einfache Navigationen ohne await reicht eine Transition. Für geordnete Mutationen sind useActionState oder Form-Actions oft die passendere Abstraktion. Sie modellieren Action-Zustand und Reihenfolge, können dadurch aber Operationen serialisieren. Direkte Transitions erlauben mehr Parallelität; dann musst du veraltete Antworten selbst verwerfen, Requests koordinieren oder eine fachliche Versionsregel verwenden.

Fallstricke am Rand

  • Transitions dürfen keine Texteingabe kontrollieren; deren State muss dringend bleiben.
  • Eine Transition bricht den Netzwerkrequest nicht ab und rollt Serveränderungen nicht zurück.
  • Mehrere asynchrone Actions können außer Reihenfolge fertig werden; die Verschachtelung behebt das nicht.

Selbst ausprobieren

Baue in 10 Minuten einen Editor mit einer künstlich verzögerten saveProfile-Funktion und einem Ergebnisbereich, der beim Rendern bewusst CPU-Arbeit simuliert. Vergleiche die Fehlervariante mit der inneren Transition und beobachte beide im React DevTools Profiler. Erwartung: isPending umfasst den Request in beiden Varianten; nur die zweite markiert das Update nach await als Transition. Verwandte Themen

useActionState verwaltet geordnete Actions. useOptimistic trennt sofortiges Feedback vom bestätigten Ergebnis. Request-Identität verhindert, dass ältere Antworten neueren State überschreiben. Suspense entscheidet, welche bereits sichtbaren Inhalte während einer Transition erhalten bleiben.
