Ein Generic braucht eine Inferenzquelle

Wenn nur der Aufrufer den Rückgabetyp kennt, prüft TypeScript keine Beziehung – es übernimmt eine Behauptung.

TypeScript-Typsystem · TypeScript 6.0 · Tief · ~8 min

Nach einem Release stürzt die Einstellungsseite nur bei einigen Bestandskunden ab. Im localStorage liegt noch {"theme":17}, der aktuelle Code erwartet jedoch theme: "light" | "dark". Der Aufruf load<UserSettings>("settings") kompiliert ohne Warnung. Das Generic sieht präzise aus, hat aber nichts geprüft.

TL;DR

Ein Typparameter ist besonders wertvoll, wenn er eine Beziehung zwischen Eingabe und Ausgabe transportiert. Taucht T nur im Rückgabewert auf, kann TypeScript ihn nicht aus einem Laufzeitwert ableiten. Bei load<T>(key) bestimmt der Aufrufer deshalb selbst, was zurückkommen soll. Besser ist load(key, decoder): Der Decoder akzeptiert unknown, validiert den Wert und liefert T. TypeScript inferiert T aus dieser überprüfbaren Eingabe.

Prerequisites

Du solltest Generics, Inferenz, unknown und JSON-Grenzen kennen. Das TypeScript-Handbuch zu Generics zeigt, wie Typinformationen aus Argumenten inferiert und zwischen Positionen weitergereicht werden. unknown verhindert Zugriffe vor einer Prüfung. MDN beschreibt, dass Web Storage ausschließlich Strings speichert. Der Versionsbezug ist TypeScript 6.0.

Der Aha-Effekt

Spitze Klammern sind kein Validierungsmechanismus. In einer guten generischen API fließt Typinformation aus einem Argument durch die Funktion zur Ausgabe. Fehlt diese Quelle, ist die explizite Angabe <UserSettings> keine Erkenntnis des Compilers, sondern eine Zusicherung des Callers. Sie ähnelt semantisch einem Cast, auch wenn die Syntax freundlicher wirkt.

Die zentrale Entscheidung: Lass den Rückgabetyp aus einem Wert inferieren, der die behauptete Struktur zur Laufzeit belegen kann.

So macht man es falsch

Die Funktion erlaubt für denselben Schlüssel beliebige, sogar widersprüchliche Typargumente. Der Cast hinter JSON.parse verbindet die Behauptung mit dem Rückgabewert, ohne die gespeicherten Daten anzusehen.

// storage.ts – vollständiges TypeScript-Modul ohne Abhängigkeiten
export function load<T>(key: string): T | null {
  const raw = localStorage.getItem(key);
  return raw === null ? null : (JSON.parse(raw) as T);
}

type UserSettings = {
  theme: "light" | "dark";
  compact: boolean;
};

const settings = load<UserSettings>("settings");
const count = load<number>("settings"); // ebenfalls erlaubt

settings?.theme.toUpperCase();
// Bei {"theme":17,"compact":true}: TypeError zur Laufzeit

Warum ist das falsch?

T kommt in keinem Parameter vor. Der Compiler besitzt daher keine Inferenzquelle, die UserSettings mit dem Schlüssel oder dem JSON-Text verknüpft. Nach dem Kompilieren ist T vollständig gelöscht; JSON.parse kann jede gültige JSON-Form erzeugen. Das beobachtbare Symptom erscheint erst beim ersten Zugriff, oft weit entfernt von der Speichergrenze.

Auch load<T extends object> löst das nicht. Die Constraint verbietet zwar number, beweist aber weder theme noch compact. Sie begrenzt Behauptungen, validiert jedoch keine Daten.

So macht man es richtig

Der Decoder ist ein Wert und damit eine echte Eingabe. Er übernimmt die Laufzeitprüfung; seine Rückgabe liefert TypeScript zugleich die Inferenzquelle für T. Ungültiges JSON und veraltete Strukturen scheitern direkt an der Grenze.

export type Decoder<T> = (value: unknown) => T;

export function load<T>(key: string, decode: Decoder<T>): T | null {
  const raw = localStorage.getItem(key);
  if (raw === null) return null;
  const parsed: unknown = JSON.parse(raw);
  return decode(parsed);
}

type UserSettings = {
  theme: "light" | "dark";
  compact: boolean;
};

function isRecord(value: unknown): value is Record<string, unknown> {
  return typeof value === "object" && value !== null;
}

const decodeSettings: Decoder<UserSettings> = (value) => {
  if (
    !isRecord(value) ||
    (value.theme !== "light" && value.theme !== "dark") ||
    typeof value.compact !== "boolean"
  ) {
    throw new Error("Ungültige UserSettings im Storage");
  }
  return { theme: value.theme, compact: value.compact };
};

const settings = load("settings", decodeSettings);
// Inferiert: UserSettings | null

Der Preis ist zusätzlicher Decoder-Code und eine definierte Fehlerstrategie. Für viele Modelle lohnt eine Schema-Bibliothek. Eine andere Alternative ist ein typisiertes Registry-Objekt, das Schlüssel fest mit Decodern koppelt; das verhindert zusätzlich, denselben Schlüssel verschieden zu interpretieren, erhöht aber die zentrale Konfiguration. Bewusst vertrauenswürdige, prozessinterne Daten dürfen einfacher bleiben – persistierte oder externe Daten nicht.

Textliche Erklärung: Beide Wege beginnen mit denselben untypisierten Daten. Nur das Decoder-Argument erzeugt eine überprüfbare Brücke vom Laufzeitwert zum inferierten Rückgabetyp.

Fallstricke am Rand

  • JSON.parse kann bereits bei syntaktisch ungültigem Text werfen. Entscheide, ob du Fehler weitergibst, in ein Result übersetzt oder den Eintrag entfernst.
  • Ein Type Predicate ist selbst eine Zusicherung. Teste Decoder mit fehlenden, falschen und zusätzlichen Feldern.
  • Ein Decoder ist zugleich ein Migrationspunkt: Alte Versionen können bewusst transformiert statt pauschal verworfen werden.

Selbst ausprobieren

Speichere in fünf bis zehn Minuten nacheinander gültige Einstellungen, {"theme":17,"compact":true} und syntaktisch ungültiges JSON. Die alte API liefert für die ersten beiden Fälle vermeintliche UserSettings; der Fehler entsteht erst bei der Nutzung. Die Decoder-Variante soll gültige Daten liefern und beide Fehlerformen unmittelbar beim Laden mit unterscheidbaren Meldungen stoppen.

Verwandte Themen

  • Schema-Inferenz: Bibliotheken können statischen Typ und Runtime-Schema aus einer Definition ableiten.
  • Key-Registry: Ein Mapping koppelt Storage-Schlüssel, Decoder und Rückgabetyp zentral.
  • Versionierte Persistenz: Decoder können alte Datenformen erkennen und migrieren.
  • Result-Typen: Erwartbare Validierungsfehler lassen sich explizit statt als Exception modellieren.
