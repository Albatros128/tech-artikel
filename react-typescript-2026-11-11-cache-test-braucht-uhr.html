Ein Cache-Test braucht eine Uhr, keine Wartezeit

TTL-Logik wird deterministisch, sobald verstrichene Zeit eine explizite Abhängigkeit ist.

11.11.2026 · Datenzugriff, Caching & Tests · TypeScript 6.0 + Performance API · Tief · ~8 min

Ein kleiner In-Memory-Cache hält Suchergebnisse 50 Millisekunden frisch. Der Test schreibt einen Eintrag, wartet 51 Millisekunden und erwartet danach einen Miss. Lokal ist alles grün. Im CI wird der Test unregelmäßig rot; gelegentlich dauert die Suite nur unnötig lange. Die Ursache liegt nicht zwingend im Cache. Der Test hat gleichzeitig TTL-Regel, Timer-Auflösung und Scheduler getestet.

TL;DR

Ein TTL-Cache beantwortet eine fachliche Frage: Liegt now vor expiresAt? Wenn der Cache die Uhr selbst über Date.now() oder performance.now() beschafft, muss der Test reale Zeit verstreichen lassen oder globale Timer manipulieren. Injiziere stattdessen eine minimale Clock. Produktion erhält eine monotone Uhr, der Test eine manuell fortschaltbare. So prüfst du die Ablaufgrenze ohne Schlafen und ohne globale Testumgebung.

Prerequisites

Du kennst Generics, Map und den Unterschied zwischen Unit- und Integrationstest. Die Beispiele verwenden TypeScript 6.0 und den eingebauten Node-Test-Runner. Für Browser-Caches ist die dokumentierte Semantik von performance.now() wichtig: Der Wert ist relativ zu timeOrigin und monoton, also nicht von nachträglichen Systemuhrkorrekturen betroffen.

Der Aha-Effekt

Zeit ist kein unsichtbarer Hintergrund, sondern Eingabe der Cache-Entscheidung. Ein Test, der wartet, kontrolliert diese Eingabe nur indirekt. Eine Clock macht sie so explizit wie den Schlüssel oder die TTL. Das erlaubt einen präzisen Test von 49 ms gegen 50 ms, ohne dass tatsächlich 50 Millisekunden vergehen.

Die Abstraktion muss nicht aus einem Framework stammen. Ein Objekt mit now(): number reicht. Entscheidend ist, dass Erzeugen und Prüfen eines Eintrags dieselbe Uhr verwenden. Dadurch bleibt die Einheit der Zeit innerhalb des Caches konsistent.

So macht man es falsch

Die Fehlervariante koppelt Produktionslogik und Test an die reale Wanduhr. Der Test enthält bewusst keine künstliche Übertreibung; genau solche kurzen Wartezeiten entstehen bei vermeintlich schnellen TTL-Tests:

// Ausschnitt: real-time-cache.test.ts
import assert from "node:assert/strict";
import test from "node:test";

const delay = (ms: number) =>
  new Promise<void>(resolve => setTimeout(resolve, ms));

test("expires after 50 ms", async () => {
  const cache = new RealTimeCache<string, string>(50);
  cache.set("profile", "Ada");

  await delay(51);

  assert.equal(cache.get("profile"), undefined);
});

Warum ist das falsch?

setTimeout(51) garantiert nicht, dass der Callback exakt nach 51 Millisekunden läuft; er wird erst ausführbar, wenn Timer und Event Loop ihn einplanen. Der Test wartet daher auf Infrastruktur, obwohl er nur eine Vergleichsregel prüfen will. Viele solcher Tests summieren reale Pausen. Knapp gewählte Grenzen können zudem durch Timerpräzision und Umgebung beeinflusst werden.

Date.now() ist epoch-basiert und kann laut MDN reduzierter Präzision unterliegen; außerdem kann die Systemuhr korrigiert werden. Für eine nur innerhalb derselben Seiten- oder Prozesslebenszeit gemessene TTL ist eine monotone Uhr das passendere Modell.

So macht man es richtig mit Trade-offs

Der Cache erhält seine Uhr im Konstruktor. Die Produktionsvoreinstellung nutzt performance.now(); der Test kontrolliert eine ManualClock:

// cache-clock.test.ts – lauffähiger Ausschnitt
import assert from "node:assert/strict";
import test from "node:test";

type Clock = { now(): number };

class ManualClock implements Clock {
  private time: number;
  constructor(time = 0) { this.time = time; }
  now() { return this.time; }
  advance(ms: number) { this.time += ms; }
}

class TtlCache<K, V> {
  private entries = new Map<K, { value: V; expiresAt: number }>();
  private readonly ttlMs: number;
  private readonly clock: Clock;

  constructor(ttlMs: number, clock: Clock = { now: () => performance.now() }) {
    this.ttlMs = ttlMs;
    this.clock = clock;
  }

  set(key: K, value: V) {
    this.entries.set(key, { value, expiresAt: this.clock.now() + this.ttlMs });
  }

  get(key: K): V | undefined {
    const entry = this.entries.get(key);
    if (!entry) return undefined;
    if (this.clock.now() >= entry.expiresAt) {
      this.entries.delete(key);
      return undefined;
    }
    return entry.value;
  }
}

test("expires exactly at the TTL boundary", () => {
  const clock = new ManualClock(1_000);
  const cache = new TtlCache<string, string>(50, clock);
  cache.set("profile", "Ada");

  clock.advance(49);
  assert.equal(cache.get("profile"), "Ada");
  clock.advance(1);
  assert.equal(cache.get("profile"), undefined);
});

Der Trade-off ist ein zusätzlicher Konstruktorparameter. Für eine kleine reine Funktion wäre isFresh(createdAt, ttl, now) noch einfacher. Globale Fake-Timer sind eine Alternative, wenn der Code mehrere echte Timer koordiniert; für eine einzelne Vergleichsregel vergrößern sie jedoch den Test-Scope.

Die monotone Standarduhr passt nur zu flüchtigen Einträgen innerhalb desselben Zeitursprungs. Persistierst du Ablaufzeitpunkte über Reloads, Tabs oder Prozesse hinweg, brauchst du epoch-basierte Zeit wie Date.now() – weiterhin injiziert, damit Tests sie kontrollieren können.

Diagramm

Fallstricke am Rand

  • Lege fest, ob exakt expiresAt bereits abgelaufen bedeutet; der Test dokumentiert hier >=.
  • Mische innerhalb eines Caches niemals Date.now()- und performance.now()-Werte.
  • Prüfe Räumung und Speichergrenzen separat; TTL allein verhindert keinen unbegrenzten Cache.

Selbst ausprobieren

Kopiere den lauffähigen Ausschnitt in cache-clock.test.ts und starte node --test cache-clock.test.ts mit einer aktuellen Node-Version, die Type Stripping unterstützt. Ändere anschließend >= zu >. Erwartung: Der Grenztest schlägt sofort fehl, ohne reale Wartezeit. Der hier gezeigte Test lief unter Node 24 erfolgreich; ein vollständiger tsc-Compile-Test war lokal nicht verfügbar.

Verwandte Themen

Cache Keys definieren Identität, während TTL Gültigkeit definiert. Stale-while-revalidate trennt Nutzbarkeit von Frische. Fake Timer sind sinnvoll für koordinierte Timer-APIs. Property-based Tests können viele Zeitpunkte rund um Ablaufgrenzen erzeugen.
