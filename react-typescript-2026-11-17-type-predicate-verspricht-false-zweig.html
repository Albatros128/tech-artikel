Ein Type Predicate verspricht auch den false-Zweig

Eine Geschäftsregel ist nicht automatisch ein Type Guard – selbst wenn jeder Treffer denselben Typ hat.

TypeScript-Typsystem · TypeScript 6.0, Predicate-Inferenz seit 5.5 · Tief · ~8 min

Eine Event-App trennt aktive Mitglieder von Gästen. Der positive Zweig funktioniert: Wer den Check besteht, ist sicher ein Mitglied. Wochen später verwendet ein Kollege denselben Check in einer partition-Funktion – und behandelt plötzlich inaktive Mitglieder als Gäste.

TL;DR

Die Signatur value is T ist eine bidirektionale Zusage: true bedeutet T, false bedeutet „nicht T“. Liefert eine Bedingung auch für manche Werte aus T den Wert false, ist sie kein gültiges Type Predicate. Nutze für solche Geschäftsregeln ein gewöhnliches boolean und trenne strukturelles Narrowing von fachlicher Selektion.

Prerequisites

Du solltest user-defined Type Guards, Unions und Generics kennen. Der Artikel bezieht sich auf TypeScript 6.0. Die automatische Inference einfacher Type Predicates kam mit TypeScript 5.5.

Der Aha-Effekt

TypeScript narrowt in beiden Kontrollflusszweigen. Die offizielle Dokumentation zeigt: Nach isFish(pet) ist der Wert im if-Zweig ein Fisch und im else-Zweig kein Fisch. Die 5.5 Release Notes formulieren das ausdrücklich als „if and only if“-Semantik und weisen darauf hin, dass explizite is-Annotationen vom Compiler nicht gegen ihre Implementierung geprüft werden.

Eigene Schlussfolgerung: Schreibe ein Type Predicate nur, wenn du sowohl den positiven als auch den negativen Satz in einem Code Review verteidigen kannst.

So macht man es falsch

Der folgende Guard vermischt die Typfrage „Mitglied oder Gast?“ mit der Geschäftsfrage „aktiver Tarif?“. Sein positiver Zweig ist korrekt, sein negativer Zweig nicht.

// Ausschnitt: realistische Fehlervariante
type Guest = { kind: "guest"; passId: string };
type Member = {
  kind: "member";
  accountId: string;
  plan: "active" | "paused";
};
type Attendee = Guest | Member;

function isActiveMember(value: Attendee): value is Member {
  return value.kind === "member" && value.plan === "active";
}

function partition<T, S extends T>(
  values: readonly T[],
  predicate: (value: T) => value is S
): [S[], Exclude<T, S>[]] {
  const yes: S[] = [];
  const no: Exclude<T, S>[] = [];
  for (const value of values) {
    if (predicate(value)) yes.push(value);
    else no.push(value as Exclude<T, S>);
  }
  return [yes, no];
}

const [activeMembers, guests] = partition(attendees, isActiveMember);
// TypeScript glaubt: guests ist Guest[]
guests.map(guest => guest.passId.toUpperCase());

Warum ist das falsch?

Ein pausiertes Mitglied liefert false, ist aber weiterhin ein Member. Zur Laufzeit landet es im zweiten Array; statisch ist dieses Array durch Exclude<Attendee, Member> als Guest[] typisiert. Der Zugriff auf passId ergibt dann undefined, der anschließende Methodenaufruf scheitert.

Das Problem sitzt nicht in der generischen Partition: Sie kann ihren Vertrag nur erfüllen, wenn das übergebene Predicate seinen eigenen Vertrag erfüllt. Eine explizite Predicate-Annotation wirkt hier wie eine Type Assertion an einer besonders wiederverwendbaren Stelle.

So macht man es richtig

Verwende für die vollständige Typgrenze einen echten Guard. Innerhalb der bereits verengten Menge bleibt die Tarifprüfung ein boolean. Eine zweite Partition darf deshalb keine Typen ausschließen.

// Vollständige, sichere Aufteilung
function isMember(value: Attendee): value is Member {
  return value.kind === "member";
}

function hasActivePlan(value: Member): boolean {
  return value.plan === "active";
}

function splitBy<T>(
  values: readonly T[],
  predicate: (value: T) => boolean
): [T[], T[]] {
  const yes: T[] = [];
  const no: T[] = [];
  for (const value of values) (predicate(value) ? yes : no).push(value);
  return [yes, no];
}

const [members, guests] = partition(attendees, isMember);
const [activeMembers, inactiveMembers] = splitBy(members, hasActivePlan);
// guests: Guest[]; beide Member-Gruppen: Member[]

Der Trade-off ist mehrstufiger Code, dafür bildet jede Stufe genau eine Aussage ab. Als Alternative kann eine Funktion eine discriminated union wie { status: "eligible"; member: Member } oder { status: "rejected"; reason: ... } zurückgeben. Das lohnt sich, wenn die Ablehnungsgründe fachlich relevant sind.

Fallstricke am Rand

  • Zusammengesetzte Bedingungen mit && sind verdächtig, wenn der zweite Teil nur eine Teilmenge des Zieltyps akzeptiert.
  • Array.filter nutzt nur Treffer; ein fehlerhafter false-Vertrag wird oft erst bei else, partition oder Wiederverwendung sichtbar.
  • Runtime-Validierung unbekannter Daten bleibt nötig; ein Predicate validiert nur so viel wie seine Implementierung tatsächlich prüft.

Selbst ausprobieren

Lege in zehn Minuten drei Werte an: einen Gast, ein aktives und ein pausiertes Mitglied. Führe die falsche Partition aus und protokolliere kind im angeblichen Gäste-Array. Erwartung: Dort erscheint auch member. Tausche anschließend den Guard gegen isMember und partitioniere die Mitglieder separat mit dem booleschen Tarifcheck. Nun entsprechen Laufzeitwerte und statische Gruppen einander.

Verwandte Themen

  • Assertion Functions: Sie versprechen ebenfalls mehr, als TypeScript aus der Implementierung beweist.
  • Runtime-Schemas: Sie bündeln Validierung und Typableitung an Datenaußengrenzen.
  • Discriminated Unions: Sie machen fachliche Ergebnisse und Ablehnungsgründe explizit.
  • Conditional Types: Exclude ist korrekt, kann aber einen falschen Predicate-Vertrag nicht reparieren.
