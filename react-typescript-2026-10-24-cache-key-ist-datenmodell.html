Ein Cache-Key ist Teil deines Datenmodells

Wer nur die Produkt-ID speichert, erklärt Sprache, Währung und Mandant versehentlich für bedeutungslos.

24.10.2026 · Datenzugriff & Caching · TypeScript 6.0 + Fetch API · Tief · ~8 min

Ein Nutzer öffnet Produkt 42 auf Deutsch und sieht 19,90 Euro. Kurz darauf öffnet ein anderer Mandant dasselbe Produkt auf Englisch und erwartet US-Dollar – bekommt aber exakt die erste Darstellung. Der Request im Network-Tab wäre korrekt gewesen. Er wurde nur nie ausgeführt, weil der Anwendungscache unter 42 bereits einen vermeintlichen Treffer gefunden hat.

TL;DR

Zwei Requests dürfen denselben Cache-Key teilen, wenn ihre Antworten für alle Consumer austauschbar sind. Nimm deshalb jedes Eingabefeld in die Identität auf, das die Repräsentation beeinflusst: Pfad, Query-Parameter, Mandanten- oder Berechtigungskontext und relevante Header. Baue den Key in genau einer typisierten Fabrik und teste gezielt, dass fachlich verschiedene Requests verschiedene Keys erhalten.

Prerequisites

Du kennst Map, fetch, Union Types und asynchrone Funktionen. Die Beispiele beziehen sich auf TypeScript 6.0 und die standardisierte Request-Schnittstelle. Vorausgesetzt sind DOM-Typen, ein Backend-Endpunkt für Produktdarstellungen und ein Runtime-Parser parseProduct, der unbekanntes JSON validiert.

Der Aha-Effekt

Ein Key ist keine technische Abkürzung, sondern eine Äquivalenzbehauptung: Gleicher Key bedeutet „dieselbe Antwort darf wiederverwendet werden“. Lässt die Key-Funktion locale weg, behauptet sie, deutsche und englische Darstellungen seien gleich. Lässt sie scopeId weg, behauptet sie dasselbe für zwei Sicherheitskontexte.

Damit wird die Key-Funktion zu einem kleinen, aber zentralen Datenmodell. TypeScript kann sicherstellen, dass nur ein definierter Key-Typ in den Cache gelangt. Es kann jedoch nicht selbst wissen, welche Eingaben die Serverantwort verändern. Diese fachliche Vollständigkeit musst du in der Fabrik ausdrücken und mit Gegenbeispielen prüfen.

So macht man es falsch

Die folgende Implementierung verwendet einen leicht verständlichen Key. Genau darin liegt der Fehler: productId identifiziert das Produkt, aber nicht seine konkrete Repräsentation.

import { parseProduct, type Product } from "./product-schema";

type ProductRequest = {
  scopeId: string;
  productId: string;
  locale: string;
  currency: "EUR" | "USD";
  accessToken: string;
};

const productCache = new Map<string, Product>();

export async function loadProduct(input: ProductRequest) {
  const cached = productCache.get(input.productId);
  if (cached) return cached;

  const url = new URL(`/api/products/${input.productId}`, location.origin);
  url.searchParams.set("locale", input.locale);
  url.searchParams.set("currency", input.currency);

  const response = await fetch(url, {
    headers: { Authorization: `Bearer ${input.accessToken}` }
  });
  if (!response.ok) throw new Error(`HTTP ${response.status}`);

  const product = parseProduct(await response.json());
  productCache.set(input.productId, product);
  return product;
}

Warum ist das falsch?

Der erste erfolgreiche Aufruf besetzt den Eintrag 42. Danach überspringt jeder Aufruf mit dieser Produkt-ID URL-Konstruktion, Authentifizierung und Serverlogik. Weder locale noch currency oder scopeId können den Treffer unterscheiden. Das Symptom ist deshalb nicht bloß „etwas zu alt“, sondern eine Antwortvariante, die nie für diesen Request bestimmt war.

Bei mandanten- oder berechtigungsspezifischen Antworten kann daraus eine Datenisolation-Schwäche entstehen. Das hängt davon ab, ob der zurückgegebene Inhalt tatsächlich vertrauliche Unterschiede enthält; der gezeigte Cache beseitigt jedenfalls die vorgesehene Trennung. Ein kürzeres Ablaufdatum reduziert nur das Zeitfenster. Es korrigiert nicht die falsche Identität.

So macht man es richtig mit Trade-offs

Definiere die Identität als explizites Tupel mit fester Reihenfolge. JSON.stringify vermeidet hier Trennzeichen-Kollisionen wie a:b gegen a und b:c. Der rohe Zugriffstoken gehört nicht in den Key: Er ist ein Secret und wechselt unabhängig von der fachlichen Identität. Verwende stattdessen einen stabilen, nicht geheimen Scope oder halte den gesamten Cache innerhalb einer Session.

import { parseProduct, type Product } from "./product-schema";

type Currency = "EUR" | "USD";
type ProductRequest = {
  scopeId: string;
  productId: string;
  locale: string;
  currency: Currency;
  accessToken: string;
};
type ProductKey = `product:${string}`;

const productCache = new Map<ProductKey, Product>();

export function productKey(input: ProductRequest): ProductKey {
  const identity = [
    input.scopeId,
    input.productId,
    input.locale.toLowerCase(),
    input.currency
  ] as const satisfies readonly [string, string, string, Currency];

  return `product:${JSON.stringify(identity)}`;
}

export async function loadProduct(input: ProductRequest): Promise<Product> {
  const key = productKey(input);
  const cached = productCache.get(key);
  if (cached) return cached;

  const url = new URL(`/api/products/${input.productId}`, location.origin);
  url.searchParams.set("locale", input.locale.toLowerCase());
  url.searchParams.set("currency", input.currency);

  const response = await fetch(url, {
    headers: { Authorization: `Bearer ${input.accessToken}` }
  });
  if (!response.ok) throw new Error(`HTTP ${response.status}`);

  const product = parseProduct(await response.json());
  productCache.set(key, product);
  return product;
}

Der Trade-off ist eine größere Zahl von Einträgen. Das ist kein Grund, Varianten zusammenzuwerfen: Begrenze Lebenszeit und Größe separat und definiere eine Invalidierungsstrategie. Identität beantwortet „welcher Eintrag?“, Eviction „wie lange bleibt er?“. Beides sind unterschiedliche Entscheidungen.

Als Alternative kannst du die normalisierte Request-URL plus relevante Request-Metadaten als Key verwenden oder das Caching dem HTTP-Layer überlassen. HTTP-Caches berücksichtigen URL und Methode; mit Vary kann der Server zusätzliche Header benennen, welche die Antwort beeinflussen. Ein selbst gebauter Map-Cache übernimmt diese Semantik nicht automatisch.

Fallstricke am Rand

  • Normalisiere äquivalente Eingaben an einer Stelle: etwa Sprachcodes, Default-Werte und die Reihenfolge frei kombinierbarer Filter.
  • Schreibe keine Access Tokens oder personenbezogenen Rohdaten in Keys. Keys landen häufig in Logs und Diagnosewerkzeugen.
  • Eine vollständige Identität ersetzt keine Invalidierung nach Mutationen. Sie verhindert nur falsche Treffer zwischen Varianten.
  • Für andere Methoden als GET gehören Methode und gegebenenfalls Body-Semantik in die Entscheidung; GET sollte keinen Request-Body tragen.

Selbst ausprobieren

Nimm dir zehn Minuten. Erzeuge vier Eingaben für dasselbe Produkt: zwei Sprachen, zwei Währungen und zwei Scopes. Prüfe zuerst, dass der alte Key viermal 42 ergibt. Prüfe danach paarweise, dass productKey bei jeder fachlichen Änderung verschieden ist, aber de-DE und DE-de nach deiner Normalisierungsregel denselben Key liefern. Entferne testweise scopeId aus dem Tupel: Mindestens ein Test muss rot werden.

Prüfstand: Die Key-Eigenschaften und die Trennzeichen-Kollision wurden mit einem ausführbaren Node-Modell geprüft. Der TSX-/TypeScript-Ausschnitt wurde in dieser Umgebung nicht kompiliert; ein bestandener Compile-Test wird nicht behauptet.

Verwandte Themen

HTTP-Vary überträgt dieselbe Identitätsfrage auf gemeinsam genutzte Caches. Cache-Invalidierung regelt, wann ein korrekt identifizierter Eintrag veraltet. Mandantenisolation verlangt, dass jeder gemeinsam genutzte Speicher den Sicherheitskontext respektiert. Property-basierte Tests können zufällige Eingabepaare auf unerwartete Key-Kollisionen prüfen.
