Ein erfolgreicher Request hat nicht immer einen Body

Modelliere JSON und „No Content“ als verschiedene Endpoint-Verträge, statt jede 2xx-Antwort blind zu parsen.

Datenzugriff & API-Modellierung · TypeScript 6.0 + Fetch API · Tief · ~8 min

Das Löschen eines Projekts funktioniert auf dem Server: Status 204 No Content, Datenbankzeile entfernt. Im Frontend erscheint trotzdem „Aktion fehlgeschlagen“. Der Stacktrace endet in response.json(), weil die zentrale Request-Funktion aus jedem erfolgreichen Status ein T machen will. Der Transport war erfolgreich; erst der Client hat eine nicht vorhandene Repräsentation verlangt.

TL;DR

Ein Status im 2xx-Bereich garantiert keinen JSON-Body. RFC 9110 schließt Content unter anderem bei 204, 304 und Antworten auf HEAD aus. Deshalb gehört die erwartete Body-Form in den Endpoint-Vertrag: Ein JSON-Endpunkt besitzt einen Decoder und liefert T; ein Empty-Endpunkt erwartet einen bodylosen Status und liefert void. So kann der Aufrufer keinen Wert verwenden, den HTTP niemals zugesagt hat.

Prerequisites

Du solltest fetch, Overloads, discriminated unions und unknown kennen. RFC 9110 beschreibt, wann Responses keinen Content enthalten. MDN dokumentiert 204 No Content sowie Response.json(), das den Body liest und als JSON parst. Der Versionsbezug ist TypeScript 6.0.

Der Aha-Effekt

Der Rückgabetyp einer HTTP-Abstraktion beschreibt nicht nur Nutzdaten, sondern ein Protokoll: Status, Content-Art und Decoder müssen zusammenpassen. Ein freies <T> lässt dagegen allein den Aufrufer bestimmen, was angeblich aus dem Netz kommt. Der Compiler bestätigt dann einen Wunsch, nicht den Endpoint.

Die zentrale Entscheidung: Nicht der erfolgreiche Status entscheidet, ob geparst wird, sondern der zuvor deklarierte Response-Vertrag.

So macht man es falsch

Die typische Hilfsfunktion prüft response.ok und parst danach ausnahmslos JSON. Der Cast betrifft nur TypeScript; er erzeugt weder einen Body noch validiert er dessen Form.

// Vollständiges TypeScript-Modul; keine Imports erforderlich.
async function request<T>(
  input: RequestInfo | URL,
  init?: RequestInit,
): Promise<T> {
  const response = await fetch(input, init);
  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`);
  }
  return response.json() as Promise<T>;
}

type Deleted = { deleted: true };

// Server antwortet korrekt mit 204 und leerem Body.
const result = await request<Deleted>("/api/projects/42", {
  method: "DELETE",
});

console.log(result.deleted); // wird nie erreicht

Warum ist das falsch?

response.ok bedeutet lediglich, dass der Status zwischen 200 und 299 liegt. Es sagt nichts über das Medienformat aus. Bei 204 darf die Response keinen Content enthalten; ein JSON-Parser kann aus leerer Eingabe keinen Wert konstruieren. Der Fehler tritt daher nach einem erfolgreichen DELETE auf und wird leicht fälschlich als Netzwerk- oder Serverfehler behandelt.

Auch T | undefined repariert das Design nicht: Dann muss jeder JSON-Aufrufer defensiv mit einem Zustand umgehen, der für seinen Endpoint vielleicht unmöglich ist. Die Body-Variante ist eine Eigenschaft des Endpoints und sollte dort diskriminiert werden.

So macht man es richtig

Die Endpoint-Beschreibung koppelt Methode, Pfad und Response-Form. JSON wird zunächst als unknown gelesen und von einem endpoint-spezifischen Decoder geprüft. Empty verlangt hier bewusst 204; andere APIs könnten zusätzlich 205 oder einen HEAD-Vertrag modellieren.

type Decoder<T> = (value: unknown) => T;

type JsonEndpoint<T> = Readonly<{
  path: string;
  method: "GET" | "POST" | "PUT";
  response: { kind: "json"; decode: Decoder<T> };
}>;

type EmptyEndpoint = Readonly<{
  path: string;
  method: "DELETE";
  response: { kind: "empty"; status: 204 };
}>;

async function call<T>(endpoint: JsonEndpoint<T>): Promise<T>;
async function call(endpoint: EmptyEndpoint): Promise<void>;
async function call<T>(
  endpoint: JsonEndpoint<T> | EmptyEndpoint,
): Promise<T | void> {
  const response = await fetch(endpoint.path, { method: endpoint.method });
  if (!response.ok) throw new Error(`HTTP ${response.status}`);

  if (endpoint.response.kind === "empty") {
    if (response.status !== endpoint.response.status) {
      throw new Error(`Erwartet 204, erhalten ${response.status}`);
    }
    return;
  }

  const contentType = response.headers.get("content-type") ?? "";
  if (!contentType.includes("application/json")) {
    throw new Error(`Erwartet JSON, erhalten ${contentType || "ohne Typ"}`);
  }
  const raw: unknown = await response.json();
  return endpoint.response.decode(raw);
}

const deleteProject = {
  path: "/api/projects/42",
  method: "DELETE",
  response: { kind: "empty", status: 204 },
} satisfies EmptyEndpoint;

await call(deleteProject); // Promise<void>

Der zusätzliche Vertrag erzeugt mehr Definitionen, dafür liegen Protokollwissen und Laufzeitprüfung an einer Stelle. Eine schlankere Alternative ist, rohe Response-Objekte zurückzugeben und jeden Aufrufer parsen zu lassen. Das ist flexibel, verteilt aber Status- und Content-Regeln über die Anwendung. Bei generierten OpenAPI-Clients sollte die Spezifikation diese Unterscheidung liefern; eine falsche Spezifikation bleibt dennoch ein Laufzeitproblem.

Diagramm

flowchart TD
    A[HTTP-Response ist erfolgreich] --> B{Endpoint-Vertrag}
    B -- JSON --> C[Content-Type prüfen und unknown decodieren]
    B -- Empty --> D[Erwarteten bodylosen Status prüfen]
    C --> E[Typisierter Wert oder klarer Vertragsfehler]

Textliche Erklärung: Der Status öffnet nur den Erfolgszweig. Erst der Endpoint-Vertrag bestimmt, ob ein Body dekodiert oder gerade seine Abwesenheit geprüft wird.

Fallstricke am Rand

  • 304 Not Modified gehört meist in eine Cache-Schicht und ist nicht durch response.ok abgedeckt.
  • HEAD liefert Repräsentations-Header ohne Message Body; modelliere die Methode ausdrücklich.
  • Ein JSON-Content-Type beweist noch keine Datenform. Der Decoder bleibt notwendig.

Selbst ausprobieren

Erzeuge in fünf Minuten new Response(null, { status: 204 }) und rufe darauf json() auf. Erwartung: Das Promise wird wegen leerer Eingabe abgelehnt. Prüfe anschließend denselben Response mit dem Empty-Zweig: Status 204 führt ohne Parsing zu undefined. Tausche den Status testweise gegen 200; der deklarierte Empty-Vertrag soll nun einen verständlichen Vertragsfehler liefern.

Verwandte Themen

  • Problem Details: Fehlerantworten benötigen einen eigenen Decoder statt einer angenommenen Erfolgsschematik.
  • Content Negotiation: Accept und Content-Type sind Teile desselben Medienvertrags.
  • OpenAPI: Response-Schemas sollten pro Statuscode statt nur pro Operation beschrieben werden.
  • ETag und 304: Bodylose Revalidierung verbindet HTTP-Semantik mit lokalem Cache-Zustand.
