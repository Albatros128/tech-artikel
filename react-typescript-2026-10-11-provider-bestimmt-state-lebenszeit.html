Der Provider bestimmt die Lebenszeit des Zustands

Context ist kein globaler Store. Wo du den Provider in den Baum setzt, entscheidet, welche Komponenten denselben Zustand teilen und wann dieser Zustand verworfen wird.

React-Context · React 19.3 + TypeScript · Tief · ~8 min

Eine Verwaltungsoberfläche öffnet zwei Kundeneditoren nebeneinander. Beide verwenden denselben useCustomerDraft-Hook. Beim Tippen in „Notiz“ ändert sich plötzlich auch der andere Editor. Der Reducer ist korrekt, die IDs sind unterschiedlich und React mischt keinen State. Beide Editoren lesen schlicht dieselbe Provider-Instanz, weil der Provider weit oben um die gesamte Anwendung liegt.

TL;DR

createContext erzeugt keinen Zustand. Der Zustand lebt in der Komponente, die ihn per Provider verteilt. Ein Provider oberhalb mehrerer Editoren bedeutet absichtlich eine gemeinsame Instanz; ein Provider pro Editor erzeugt isolierte Instanzen. Setze fachlichen Zustand deshalb an die kleinste Baumgrenze, die ihn wirklich teilen soll. Nutze einen stabilen key, wenn ein Wechsel der fachlichen Identität den State bewusst zurücksetzen muss.

Prerequisites

Du solltest createContext, useContext und die Regeln zur State-Identität im Komponentenbaum kennen. Seit React 19 kann das Context-Objekt selbst als Provider gerendert werden; die ältere <Context.Provider>-Schreibweise bleibt für ältere Versionen relevant.

Der Aha-Effekt

Die React-Dokumentation formuliert es ausdrücklich: Das Context-Objekt selbst hält keine Information. Es bezeichnet nur die Art von Information, die Provider anbieten und Konsumenten lesen. useContext sucht vom Konsumenten nach oben und nimmt den Wert des nächsten passenden Providers. Damit ist Provider-Platzierung keine Verkabelungsfrage, sondern eine Entscheidung über Ownership und Lebenszeit.

So macht man es falsch

Ein App-weiter Provider wirkt bequem, erweitert aber den Sharing-Bereich jedes Drafts auf die gesamte Anwendung:

// App.tsx – problematischer Ausschnitt
import { CustomerDraftProvider } from "./customer-draft";

export function App() {
  return (
    <CustomerDraftProvider initialCustomerId="none">
      <Router />
    </CustomerDraftProvider>
  );
}

// Zwei Editoren darunter lesen dieselbe Draft-Instanz.
export function Workspace({ ids }: { ids: string[] }) {
  return ids.map(id => <CustomerEditor key={id} customerId={id} />);
}

Warum ist das falsch?

Der Fehler liegt nicht in Context, sondern in der behaupteten Fachlichkeit: Der App-Provider sagt „alle Nachfahren teilen einen CustomerDraft“. customerId als Prop am Editor erzeugt keine neue Provider- oder State-Instanz. Auch ein Context-Wert mit mehreren Feldern löst das Ownership-Problem nicht automatisch; er macht nur den gemeinsam genutzten Zustand größer.

Der Default-Wert kann den Fehler zusätzlich verschleiern. Ein scheinbar gültiges leeres Draft-Objekt aus createContext lässt Komponenten außerhalb des Providers weiterlaufen. Für zwingende fachliche Provider ist null plus ein Hook, der ohne Provider wirft, meist die ehrlichere API.

So macht man es richtig mit Trade-offs

Der Provider besitzt Reducer und State. Der Workspace erzeugt pro fachlicher Editor-Instanz einen Provider. Der key verbindet Reacts Komponentenidentität mit der Kunden-ID:

// customer-draft.tsx – vollständiger relevanter Ausschnitt
import {
  createContext, useContext, useMemo, useReducer,
  type Dispatch, type ReactNode
} from "react";

type Draft = { customerId: string; note: string };
type Action = { type: "noteChanged"; note: string };

export function draftReducer(state: Draft, action: Action): Draft {
  switch (action.type) {
    case "noteChanged": return { ...state, note: action.note };
  }
}

type DraftContextValue = { draft: Draft; dispatch: Dispatch<Action> };
const DraftContext = createContext<DraftContextValue | null>(null);

export function CustomerDraftProvider(props: {
  customerId: string;
  children: ReactNode;
}) {
  const [draft, dispatch] = useReducer(draftReducer, {
    customerId: props.customerId,
    note: ""
  });
  const value = useMemo(() => ({ draft, dispatch }), [draft]);
  return <DraftContext value={value}>{props.children}</DraftContext>;
}

export function useCustomerDraft(): DraftContextValue {
  const value = useContext(DraftContext);
  if (value === null) throw new Error("CustomerDraftProvider fehlt");
  return value;
}

export function Workspace({ ids }: { ids: string[] }) {
  return ids.map(customerId => (
    <CustomerDraftProvider key={customerId} customerId={customerId}>
      <CustomerEditor />
    </CustomerDraftProvider>
  ));
}

Wird ein Editor entfernt, verschwindet seine Provider-Komponente und damit ihr Reducer-State. Eine neue ID erzeugt wegen des anderen key bewusst eine neue Instanz. Das ist dokumentiertes React-Verhalten zur State-Position im Baum, keine Eigenschaft von Context allein.

Der Trade-off: Tief platzierte Provider machen Abhängigkeiten weniger sichtbar und können Tests mehr Setup kosten. Bei wenigen Ebenen sind Props oft klarer. Soll der Draft Navigation, Remounts oder mehrere getrennte Baumzweige überleben, ist ein externer Store oder ein Router-/Server-Cache die passendere Ownership-Grenze.

Fallstricke am Rand

  • Ein neuer customerId-Propwert initialisiert useReducer nicht erneut; dafür braucht es einen bewussten Identitätswechsel per key oder eine Action.
  • Ein Provider im selben Komponenten-Return unterhalb eines useContext-Aufrufs beeinflusst diesen Aufruf nicht.
  • Neue Objektidentitäten im Context-Wert können Konsumenten aktualisieren; optimiere erst nach einer Messung.
  • Globale Provider sind für tatsächlich globale Werte wie Theme oder Session weiterhin sinnvoll.

Selbst ausprobieren

Rendere zwei Editoren zunächst unter einem gemeinsamen Provider und gib in beiden die aktuelle customerId und Notiz aus. Ändere eine Notiz. Verschiebe danach den Provider in die map-Schleife und wiederhole den Versuch. Erwartung: Zuerst teilen beide Editoren einen Draft; danach ändern sie sich unabhängig. Tausche zusätzlich eine ID aus und beobachte den Reset durch den neuen key. Dauer: etwa zehn Minuten.

Verwandte Themen

Reducer modellieren erlaubte Draft-Übergänge. State Colocation setzt dieselbe Ownership-Idee ohne Context um. Split Contexts für State und Dispatch können Abhängigkeiten präziser machen, sollten aber anhand realer Renderprofile bewertet werden. Externe Stores lösen Sharing außerhalb eines einzelnen React-Teilbaums. Router-Keys und Komponenten-Keys steuern bewusst, wann React Zustand erhält oder verwirft.
