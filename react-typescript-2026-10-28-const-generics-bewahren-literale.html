Literalgenauigkeit gehört an die Generic-API-Grenze

as const an jedem Aufruf ist oft kein Datenproblem, sondern ein Hinweis auf eine zu breit inferierende Bibliotheks-API.

28.10.2026 · TypeScript-Generics · TypeScript 6.0, const-Typparameter seit 5.0 · Tief · ~8 min

Du baust einen typisierten Router. Aus seiner Konfiguration soll automatisch die Union "dashboard" | "profile" entstehen. Trotzdem akzeptiert navigate("dashbaord") den Tippfehler. Die Route steht als Literal im Quelltext, doch am Ende bleibt nur string. Der übliche Patch lautet as const – und wandert bald in jeden Aufruf deiner API.

TL;DR

Wenn eine Generic-API inline geschriebene Konfiguration als präzise Datenbeschreibung behandeln soll, setze den const-Modifikator am Typparameter und verwende readonly-kompatible Constraints. Damit wird const-ähnliche Inferenz zum Standard der API. Das friert keine Werte zur Laufzeit ein, verengt keine bereits verbreiterte Variable und ist ungeeignet, wenn Aufrufer die Daten bewusst verändern sollen.

Prerequisites

Du kennst Generics, Constraints, typeof und Indexed Access Types. Die Beispiele beziehen sich auf TypeScript 6.0. const-Typparameter kamen mit TypeScript 5.0. Für die Laufzeitgrenze ist außerdem das Verhalten von Object.freeze relevant.

Der Aha-Effekt

Die Frage ist nicht nur, welcher Typ einen Parameter begrenzt, sondern auch, wie genau TypeScript den Typ am Aufruf inferieren soll. Gewöhnliche Inferenz wählt bei veränderbaren Objekt- und Array-Ausdrücken oft allgemeinere Typen. Das ist sinnvoll, wenn der Wert später mutiert wird. Für deklarative Konfiguration vernichtet es jedoch genau die Information, aus der deine API sichere Schlüssel oder Kommandos ableiten soll.

Ein const-Typparameter verschiebt diese Entscheidung zum API-Autor. Inline-Literale werden standardmäßig so präzise inferiert, als hätte der Aufrufer const-ähnliche Typen angefordert. Der Modifikator ist damit eine Inferenzrichtlinie – keine Validierung und kein Mechanismus für Laufzeit-Unveränderlichkeit.

So macht man es falsch

Diese selbständige TypeScript-Moduldatei braucht keine Imports. Der Constraint prüft zwar die Form jeder Route, die gewöhnliche Inferenz verbreitert aber die Namen:

export type RouteSpec = {
  name: string;
  path: `/${string}`;
  roles: readonly string[];
};

export function defineRoutes<T extends readonly RouteSpec[]>(
  routes: T
): T {
  return routes;
}

export const routes = defineRoutes([
  { name: "dashboard", path: "/dashboard", roles: ["admin"] },
  { name: "profile", path: "/profile", roles: ["user", "admin"] }
]);

export type RouteName = (typeof routes)[number]["name"];
// RouteName ist string – der Tippfehler bleibt typgültig.
export const navigate = (name: RouteName) => name;
navigate("dashbaord");

Warum ist das falsch?

Die API verspricht eine Beziehung zwischen Eingabe und Rückgabetyp, verliert aber beim Inferieren die Literale, auf denen diese Beziehung beruht. Das beobachtbare Symptom ist eine nutzlose string-Union: Autocomplete kann keine endliche Menge anbieten und ungültige Namen erreichen nachgelagerten Code.

as const am Aufruf repariert das Beispiel, verteilt die Verantwortung aber an jeden Consumer. Noch wichtiger: Eine vorher deklarierte Variable ist bereits verbreitert. Laut TypeScript-Dokumentation wirkt der Modifikator nur auf Objekt-, Array- und primitive Ausdrücke, die direkt im Aufruf stehen. Er kann verlorene Information nicht rückwirkend rekonstruieren.

So macht man es richtig mit Trade-offs

Die korrigierte API ändert genau ein Wort. Ihr Constraint bleibt readonly-kompatibel, damit die präzise readonly-Kandidatin nicht an einem mutablen Constraint scheitert:

export type RouteSpec = {
  name: string;
  path: `/${string}`;
  roles: readonly string[];
};

export function defineRoutes<
  const T extends readonly RouteSpec[]
>(routes: T): T {
  return routes;
}

export const routes = defineRoutes([
  { name: "dashboard", path: "/dashboard", roles: ["admin"] },
  { name: "profile", path: "/profile", roles: ["user", "admin"] }
]);

export type RouteName = (typeof routes)[number]["name"];
// "dashboard" | "profile"
export const navigate = (name: RouteName) => name;

navigate("dashboard");
// navigate("dashbaord"); // Compilerfehler

Das Muster passt zu Routern, Event-Katalogen, Query Keys und Schema-Buildern: Der konkrete Literalwert ist Teil des Vertrags. Der Preis sind tiefere readonly- und Literaltypen, die bei absichtlicher Mutation stören können. Für veränderbare Arbeitsdaten ist ein normaler Generic oft ehrlicher. Eine Alternative bleibt as const am einzelnen Literal; sie ist sinnvoll, wenn nur ein Aufruf Präzision braucht oder du die Bibliotheks-API nicht kontrollierst. Explizite Generic-Argumente funktionieren ebenfalls, sind aber ausführlich und können vom Laufzeitwert wegdriften.

Wichtig: Die Funktion gibt zur Laufzeit dieselbe Referenz zurück. Wer echte Unveränderlichkeit braucht, muss sie separat implementieren, etwa mit defensiven Kopien oder Object.freeze; letzteres ist laut MDN zudem nur flach.

Fallstricke am Rand

  • Ein Constraint wie const T extends string[] kann auf string[] zurückfallen, weil die readonly-Tupel-Kandidatin nicht zu einem mutablen Array passt.
  • Eine Variable wie const config = [...] ist ohne as const nicht automatisch ein Literal-Tupel. const verhindert nur die Neuzuweisung der Variablen.
  • Daten aus JSON bleiben Laufzeitdaten. Präzise Generics ersetzen dort weder Parsing noch Validierung.

Selbst ausprobieren

Nimm dir zehn Minuten und kopiere beide Varianten in den TypeScript Playground mit Version 6.0. Fahre über RouteName: Oben erwartest du string, unten die Union aus zwei Namen. Entferne danach readonly aus dem Array-Constraint und beobachte den Rückfall. Speichere die Routen zuletzt erst in einer normalen Variablen und übergib diese; auch der const-Generic kann die bereits verlorenen Literale nicht wiederherstellen.

Prüfstand: Dokumentstruktur, Diagrammanzahl und das Laufzeitverhalten „gleiche Referenz, nicht eingefroren“ wurden lokal geprüft. Ein TypeScript-Compile-Test war in dieser Umgebung nicht verfügbar und wird nicht behauptet.

Verwandte Themen

satisfies prüft eine Konfiguration, ohne ihren Ausdruck auf den Zieltyp zu annotieren. NoInfer steuert, welches Argument einen Generic mitbestimmen darf. Template Literal Types leiten aus erhaltenen Literalen neue Namensräume ab. Runtime-Validierung übernimmt dort, wo Werte nicht aus vertrauenswürdigem TypeScript-Quelltext stammen.
