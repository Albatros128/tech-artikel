Fehlen ist nicht dasselbe wie undefined

Exakte optionale Properties machen aus einer stillen JavaScript-Eigenheit eine überprüfbare API-Entscheidung.

12.11.2026 · TypeScript-Typsystem · TypeScript 6.0 · Tief · ~8 min

Ein Profilformular sendet nur geänderte Felder. Der Nutzer ändert den Anzeigenamen, lässt die Biografie unberührt und klickt auf Speichern. Trotzdem ist bio nach einem lokalen Objekt-Merge plötzlich undefined. Der Patch enthielt den Schlüssel, obwohl er fachlich „keine Änderung“ bedeuten sollte. TypeScript hatte das Objekt akzeptiert – weil optionale Properties standardmäßig zwei verschiedene Laufzeitzustände zusammenfallen lassen.

TL;DR

Bei einem Patch bedeutet ein fehlender Schlüssel meist „beibehalten“. Ein vorhandener Schlüssel bedeutet „ändern“ – selbst wenn sein Wert undefined ist. Aktiviere strictNullChecks und exactOptionalPropertyTypes, damit bio?: string | null nur Abwesenheit, Text oder bewusstes Leeren durch null erlaubt. Wenn undefined tatsächlich ein gültiger Wert sein soll, schreibe ihn explizit in den Typ. Die Compileroption ersetzt keine Runtime-Validierung externer JSON-Daten.

Prerequisites

Du kennst Partial, Objekt-Spread und strictNullChecks. Die Beispiele beziehen sich auf TypeScript 6.0. exactOptionalPropertyTypes existiert seit TypeScript 4.4, gehört nicht automatisch zur strict-Familie und verlangt strictNullChecks.

// tsconfig.json – relevanter Ausschnitt
{
  "compilerOptions": {
    "strict": true,
    "exactOptionalPropertyTypes": true,
    "noEmit": true,
    "target": "ES2022"
  }
}

Der Aha-Effekt

Beim Lesen liefern patch.bio und ein fehlendes bio beide undefined. Das macht sie aber nicht identisch. Object.hasOwn(patch, "bio") erkennt einen vorhandenen Schlüssel auch dann, wenn dessen Wert undefined ist. Objekt-Spread kopiert vorhandene aufzählbare Properties. Damit kann { ...profile, ...patch } einen gültigen Wert überschreiben.

Das Fragezeichen sollte deshalb nicht als Kurzform für | undefined gelesen werden. Es beschreibt zunächst die Anwesenheit des Schlüssels. Die Compileroption sorgt dafür, dass der Werttyp exakt das bleibt, was rechts vom Doppelpunkt steht.

So macht man es falsch

Diese Variante wirkt plausibel: Das Formular normalisiert ein leeres Eingabefeld mit || undefined und baut daraus einen Patch. Ohne exakte optionale Properties akzeptiert der Compiler das Objekt.

// profile-patch.ts – Fehlervariante
type Profile = {
  displayName: string;
  bio: string | null;
};

type ProfilePatch = Partial<Profile>;

function applyPatch(current: Profile, patch: ProfilePatch): Profile {
  return { ...current, ...patch };
}

const patch: ProfilePatch = {
  displayName: "Ada L.",
  bio: undefined, // ohne Flag erlaubt
};

applyPatch({ displayName: "Ada", bio: "Compilerbau" }, patch);
// Laufzeit: { displayName: "Ada L.", bio: undefined }

Warum ist das falsch?

Die Typaussage bio: string | null verspricht, dass ein fertiges Profil nie undefined enthält. Der Merge verletzt diese Invariante, weil die schwächere Patch-Typisierung einen dritten Wert hereingelassen hat. Symptome tauchen später auf: Rendering-Code behandelt null, erhält aber undefined; ein lokaler Merge unterscheidet sich vom Server; oder Object.keys meldet ein Feld, das fachlich gar nicht geändert wurde.

Über HTTP wird es noch tückischer: JSON.stringify lässt object properties mit undefined aus. Derselbe Patch überschreibt lokal die Biografie, überträgt den Schlüssel aber nicht zum Server. Das ist keine TypeScript-Eigenheit, sondern JavaScript- und JSON-Verhalten.

So macht man es richtig mit Trade-offs

Definiere zuerst das Protokoll: Abwesenheit heißt „unverändert“, null heißt „löschen“, ein String heißt „setzen“. Dann kann Partial<Profile> mit exakten optionalen Properties dieses Protokoll ausdrücken. Erzeuge fehlende Felder wirklich durch Weglassen:

// profile-patch.test.ts – lauffähiger Ausschnitt
import assert from "node:assert/strict";
import test from "node:test";

type Profile = { displayName: string; bio: string | null };
type ProfilePatch = Partial<Profile>;

function buildPatch(name: string, bioChanged: boolean, bio: string): ProfilePatch {
  return {
    displayName: name.trim(),
    ...(bioChanged ? { bio: bio.trim() || null } : {}),
  };
}

function applyPatch(current: Profile, patch: ProfilePatch): Profile {
  return { ...current, ...patch };
}

test("an untouched bio is absent and survives the merge", () => {
  const current: Profile = { displayName: "Ada", bio: "Compilerbau" };
  const patch = buildPatch("Ada L.", false, "");
  const next = applyPatch(current, patch);

  assert.equal(Object.hasOwn(patch, "bio"), false);
  assert.deepEqual(next, { displayName: "Ada L.", bio: "Compilerbau" });
});

Der Trade-off ist Migrationsarbeit: Bibliothekstypen oder bisherige Zuweisungen können Fehler melden. Aktiviere das Flag bewusst und repariere Stellen fachlich, statt überall | undefined anzuhängen. Eine Alternative ist eine discriminated union wie { kind: "keep" } | { kind: "set"; value: string } | { kind: "clear" }. Sie ist ausführlicher, aber bei komplexen Befehlen noch eindeutiger als Anwesenheitssemantik.

Fallstricke am Rand

  • exactOptionalPropertyTypes prüft nur Compile-Time-Zuweisungen; API-Antworten beginnen weiterhin als unknown.
  • in berücksichtigt auch geerbte Properties; für reine Nutzdaten ist Object.hasOwn präziser.
  • Ein undefined in Arrays wird bei JSON-Serialisierung zu null, nicht ausgelassen.

Selbst ausprobieren

Speichere den lauffähigen Ausschnitt als profile-patch.test.ts und starte node --test profile-patch.test.ts mit einer aktuellen Node-Version, die Type Stripping unterstützt. Ergänze danach const invalid: ProfilePatch = { bio: undefined }; und prüfe das Projekt mit tsc: Mit dem Flag soll die Zuweisung fehlschlagen. Der Laufzeittest wurde hier unter Node 24 ausgeführt; ein lokaler TypeScript-Compiler war nicht verfügbar.

Verwandte Themen

Runtime-Validierung schützt dieselbe Grenze gegen fremde Daten. Discriminated Unions machen komplexere Patch-Befehle explizit. Form-State-Modellierung trennt „berührt“ von „leer“. JSON Merge Patch definiert eine standardisierte, aber eigene null-Semantik.
