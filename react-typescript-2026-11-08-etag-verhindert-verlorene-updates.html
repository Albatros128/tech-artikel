Ein Save-Request braucht die gelesene Version

ETag und If-Match machen aus stillem Überschreiben einen behandelbaren Konflikt.

08.11.2026 · Datenzugriff & Race Conditions · TypeScript 6.0 + Fetch/HTTP · Tief · ~8 min

Zwei Support-Mitarbeiter öffnen denselben Kunden. Lea ändert die Rechnungsadresse und speichert. Karim hat noch die alte Ansicht offen, korrigiert später nur die Telefonnummer und sendet trotzdem das komplette Formular. Sein Request ist technisch erfolgreich – und setzt Leas Adresse unbemerkt auf den alten Stand zurück. Die UI hatte kein Timing-Problem. Ihr fehlte ein Vertrag darüber, auf welcher Version die Änderung basiert.

TL;DR

Sende bei einer Mutation nicht nur neue Werte, sondern auch die Version, die beim Lesen galt. HTTP bietet dafür starke ETag-Validatoren und den Request-Header If-Match. Hat sich die Ressource inzwischen geändert, lehnt der Server die Mutation mit 412 Precondition Failed ab. Erst dann entscheidet die Oberfläche bewusst zwischen Neuladen, Vergleichen und Zusammenführen. Automatisches Wiederholen ohne Vorbedingung würde den Schutz wieder abschalten.

Prerequisites

Du kennst fetch, async/await und discriminated unions. Die Beispiele beziehen sich auf TypeScript 6.0. Für das Protokoll sind RFC 9110: If-Match, die MDN-Seiten zu ETag und 412 relevant.

Der Aha-Effekt

Ein Formularentwurf besteht logisch aus zwei Dingen: den bearbeiteten Daten und dem Wissensstand, gegen den sie entstanden sind. Nur die Daten zu typisieren reicht nicht. Die Version ist Teil des Mutation-Commands.

Der ETag bleibt dabei ein undurchsichtiges Token. Der Client muss weder Hash noch Revisionsnummer verstehen; er bewahrt den Headerwert exakt auf und sendet ihn als If-Match zurück. RFC 9110 verlangt für diesen Vergleich eine starke Validierung. Damit kann der Server die Vorbedingung zusammen mit dem Schreiben atomar prüfen.

So macht man es falsch

Der naive Client liest ein DTO, verliert aber die Version und überschreibt später blind die Ressource:

type Customer = {
  id: string;
  phone: string;
  billingAddress: string;
};

export async function saveCustomer(customer: Customer): Promise<Customer> {
  const response = await fetch(`/api/customers/${customer.id}`, {
    method: "PUT",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(customer),
  });

  if (!response.ok) throw new Error(`Speichern fehlgeschlagen: ${response.status}`);
  return response.json() as Promise<Customer>;
}

Auch ein „vor dem Speichern noch einmal GET“ behebt das Rennen nicht. Zwischen diesem GET und dem PUT kann erneut jemand schreiben. Die Prüfung gehört auf den Server in dieselbe atomare Operation wie das Update.

Warum ist das falsch?

Der Server sieht nur einen gültigen neuen Zustand. Ihm fehlt die Information, dass der Client von einer älteren Repräsentation ausgegangen ist. Last-write-wins ist dann keine neutrale technische Vorgabe, sondern eine fachliche Konfliktstrategie – meist eine unbeabsichtigte.

Das Symptom bleibt lange unsichtbar: Beide Requests liefern Erfolg, jeder Client zeigt zunächst plausible Daten, und erst später fällt der verlorene Wert auf. Frontend-Tests mit einem einzigen Editor entdecken das nicht. Der Fehler entsteht durch zwei gültige Schreibvorgänge auf derselben Ressource.

So macht man es richtig mit Trade-offs

Modelliere gelesene Daten und Version gemeinsam. Die Ergebnis-Union zwingt Aufrufer, den Konflikt als eigenen Zustand zu behandeln:

type Customer = {
  id: string;
  phone: string;
  billingAddress: string;
};

type Versioned<T> = { value: T; etag: string };
type SaveResult =
  | { kind: "saved"; customer: Versioned<Customer> }
  | { kind: "conflict" };

export async function loadCustomer(id: string): Promise<Versioned<Customer>> {
  const response = await fetch(`/api/customers/${id}`);
  if (!response.ok) throw new Error(`Laden fehlgeschlagen: ${response.status}`);

  const etag = response.headers.get("ETag");
  if (!etag) throw new Error("API liefert keinen ETag");
  return { value: await response.json() as Customer, etag };
}

export async function saveCustomer(
  current: Versioned<Customer>,
): Promise<SaveResult> {
  const response = await fetch(`/api/customers/${current.value.id}`, {
    method: "PUT",
    headers: {
      "Content-Type": "application/json",
      "If-Match": current.etag,
    },
    body: JSON.stringify(current.value),
  });

  if (response.status === 412) return { kind: "conflict" };
  if (!response.ok) throw new Error(`Speichern fehlgeschlagen: ${response.status}`);

  const etag = response.headers.get("ETag");
  if (!etag) throw new Error("Update liefert keinen neuen ETag");
  return { kind: "saved", customer: { value: await response.json() as Customer, etag } };
}

Der Preis ist echte Konflikt-UX. Nach 412 kannst du den aktuellen Serverstand laden, Unterschiede zeigen und den Nutzer entscheiden lassen. Ein automatischer Feld-Merge ist nur sicher, wenn deine Domänenregeln ihn erlauben.

Eine numerische version im JSON-Command ist eine gute Alternative, wenn du Protokoll und Backend vollständig kontrollierst oder nicht nur HTTP-Clients hast. Pessimistisches Sperren verhindert paralleles Bearbeiten früher, benötigt aber Lock-Lebenszyklen, Timeouts und eine verständliche Blockierungs-UX.

Fallstricke am Rand

  • Schwache ETags mit W/ erfüllen den starken If-Match-Vergleich nicht.
  • Bei Cross-Origin-Requests muss die API ETag über Access-Control-Expose-Headers sichtbar machen.
  • Nach einem Konflikt blind ohne If-Match zu wiederholen erzeugt wieder Last-write-wins.

Selbst ausprobieren

Simuliere in zehn Minuten einen In-Memory-Server mit Wert und Versionszähler. Lass zwei Clients Version 1 lesen. Client A speichert mit Version 1 und erzeugt Version 2. Client B sendet danach ebenfalls Version 1. Erwartung: Der Server lehnt B ab und der Wert von A bleibt erhalten. Lade für B Version 2 neu und wiederhole bewusst mit einer zusammengeführten Änderung.

Prüfstand: Dieser Ablauf wurde unter Node mit zwei konkurrierenden Bearbeitern ausgeführt; HTML-Struktur, Überschriftenfolge, Diagrammanzahl und Wortumfang wurden automatisiert geprüft. Ein TypeScript-Compile- und Browser-Integrationstest war lokal nicht verfügbar und wird nicht behauptet.

Verwandte Themen

Optimistic UI braucht eine Rückrollstrategie für 412. JSON Patch kann die Konfliktfläche verkleinern, ersetzt aber keine Versionsprüfung. Idempotency Keys verhindern doppelte Ausführung, nicht verlorene Updates. Merge-Strategien gehören in die Domäne, sobald Felder nicht unabhängig sind.
