Cache den laufenden Request, nicht erst sein Ergebnis

Wer den Cache erst nach await füllt, lässt parallele Aufrufer durch dieselbe Lücke fallen.

Datenzugriff & Caching · TypeScript 7.0.2 + Fetch API · Tief · ~8 min

Profilkopf, Berechtigungsleiste und Aktivitätsfeed brauchen denselben Benutzer. Alle drei mounten nahezu gleichzeitig. Obwohl ein Map-Cache existiert, zählt die Telemetrie drei Aufrufe des Loaders. Der Cache ist nicht defekt – er wird nur im falschen Moment befüllt.

TL;DR

Speichere bei einem Cache-Miss sofort das laufende Promise unter dem vollständigen Request-Key. Weitere Aufrufer erhalten dasselbe Promise. Ersetze den Eintrag nach Erfolg durch Wert plus Ablaufzeit und entferne ihn nach einem Fehler. So deduplizierst du konkurrierende Aufrufe auf Anwendungsebene. Das ergänzt HTTP-Caching, ersetzt aber weder dessen Validatoren noch eine durchdachte Invalidierungsstrategie.

Prerequisites

Du solltest Promises, Map, discriminated unions und Fetch kennen. Der Code verwendet TypeScript 7.0.2. Für die zweite Cache-Schicht sind der MDN-Leitfaden zu HTTP-Caching und RFC 9111 relevant.

Der Aha-Effekt

Ein Cache-Eintrag muss nicht erst fertige Daten repräsentieren. „Diese Arbeit läuft bereits“ ist ebenfalls ein wertvoller Zustand. Ein Promise ist dafür die natürliche gemeinsame Referenz: Beliebig viele Consumer können dasselbe Ergebnis beobachten, ohne den Loader erneut zu starten.

Request-Deduplizierung beginnt vor dem ersten await. Danach ist das Zeitfenster für parallele Misses bereits offen.

So macht man es falsch

Der klassische Value-Cache schützt nur spätere Aufrufe. Treffen zwei Aufrufer ein, bevor der erste Loader abgeschlossen ist, sehen beide eine leere Map.

// userRepository.ts – problematische Variante
type User = { id: string; displayName: string };

const values = new Map<string, User>();

export async function getUser(id: string): Promise<User> {
  const cached = values.get(id);
  if (cached) return cached;

  const response = await fetch(`/api/users/${encodeURIComponent(id)}`);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);

  const user = (await response.json()) as User;
  values.set(id, user); // zu spät für parallele Aufrufer
  return user;
}

await Promise.all([getUser("42"), getUser("42")]);
// Zwei Loader-Aufrufe sind möglich.

Warum ist das falsch?

JavaScript führt beide Funktionsaufrufe bis zum ersten await aus. Beide prüfen die Map, beide finden keinen Eintrag und beide starten fetch. Erst nach den Responses wird gespeichert. Der Browser-HTTP-Cache kann je nach Headern und Request-Eigenschaften helfen; die Anwendung hat aber keine eigene Deduplizierung garantiert.

Zudem erfüllt fetch() sein Promise auch bei HTTP-Statuscodes wie 404. Deshalb muss der Loader response.ok prüfen. Andernfalls kann ein Fehlerbody als scheinbar gültiger Wert im Cache landen.

So macht man es richtig – mit Trade-offs

Modelliere Pending und Ready explizit. Der Eintrag wird synchron gesetzt, bevor get zurückkehrt. Die Identitätsprüfung im Fehlerpfad verhindert, dass ein alter, später fehlschlagender Request versehentlich einen neueren Eintrag löscht.

// requestCache.ts
type Entry<T> =
  | { status: "pending"; promise: Promise<T> }
  | { status: "ready"; value: T; expiresAt: number };

export class RequestCache<K, T> {
  private readonly entries = new Map<K, Entry<T>>();

  constructor(
    private readonly load: (key: K) => Promise<T>,
    private readonly ttlMs = 30_000,
  ) {}

  get(key: K): Promise<T> {
    const entry = this.entries.get(key);

    if (entry?.status === "pending") return entry.promise;
    if (entry?.status === "ready" && entry.expiresAt > Date.now()) {
      return Promise.resolve(entry.value);
    }

    const promise = this.load(key)
      .then((value) => {
        this.entries.set(key, {
          status: "ready",
          value,
          expiresAt: Date.now() + this.ttlMs,
        });
        return value;
      })
      .catch((error: unknown) => {
        const current = this.entries.get(key);
        if (current?.status === "pending" && current.promise === promise) {
          this.entries.delete(key);
        }
        throw error;
      });

    this.entries.set(key, { status: "pending", promise });
    return promise;
  }

  invalidate(key: K): void {
    this.entries.delete(key);
  }
}
// userRepository.ts – Ausschnitt
type User = { id: string; displayName: string };

const users = new RequestCache<string, User>(async (id) => {
  const response = await fetch(`/api/users/${encodeURIComponent(id)}`);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return (await response.json()) as User;
});

const [headerUser, feedUser] = await Promise.all([
  users.get("42"),
  users.get("42"),
]); // ein Loader-Aufruf, dasselbe Ergebnis

Der Trade-off ist zusätzlicher Lebenszyklus: TTL, manuelle Invalidierung und Fehlerpolitik werden Teil deiner Architektur. Für Server-State mit Mutationen, Refetch-Regeln und Persistenz ist eine etablierte Datenbibliothek meist sinnvoller. Der kleine Cache passt zu begrenzten Read-through-Fällen, deren Schlüssel und Gültigkeit klar sind.

Fallstricke am Rand

  • Der Key muss URL, Query, relevante Header, Mandant und Berechtigungskontext abbilden. Sonst teilst du falsche Daten.
  • Cache abgelehnte Promises nicht dauerhaft; ein temporärer Fehler würde sonst „kleben“.
  • Ein einzelnes AbortSignal gehört nicht einem Consumer, wenn mehrere denselben Request teilen. Nutze Cache-eigene Abbruchlogik oder Referenzzählung.
  • Eine TTL ist keine fachliche Invalidierung. Nach Mutationen solltest du betroffene Keys gezielt löschen oder aktualisieren.

Selbst ausprobieren

Plane zehn Minuten ein. Ersetze den Loader durch eine Funktion, die einen Zähler erhöht, 50 Millisekunden wartet und den Key zurückgibt. Starte zehn parallele get("42")-Aufrufe und prüfe: Zähler gleich eins, alle Ergebnisse gleich. Lass den ersten Lauf einmal ablehnen und rufe danach erneut auf. Erwartung: Nach dem Fehler ist der Eintrag entfernt und der Loader startet wieder. Teste zuletzt zwei verschiedene Keys; jetzt muss der Zähler zwei ergeben.

Verwandte Themen

  • HTTP-Validatoren: ETag und If-None-Match vermeiden unnötige Payloads über Prozessgrenzen hinweg.
  • Stale-while-revalidate: trennt sofortige Anzeige von Hintergrund-Aktualisierung.
  • Abort und Subscriber-Lebenszeit: gemeinsames Laden braucht eine andere Ownership als komponentenlokale Requests.
  • Runtime-Validierung: ein gecachter Wert sollte erst nach erfolgreicher Boundary-Prüfung als Domänendaten gelten.
