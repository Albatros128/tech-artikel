Ein Callback ist als Property strenger als als Methode

Eine kleine Syntaxentscheidung bestimmt, ob strictFunctionTypes zu enge Event-Handler abweist.

09.11.2026 · TypeScript-Typsystem · TypeScript 6.0 · Tief · ~8 min

Eine Editor-Komponente meldet Texteingaben und Tastenkürzel über denselben Event-Kanal. Ein bestehender Handler kennt nur Texteingaben und greift sofort auf event.value zu. Beim Refactoring wird er als allgemeiner Handler registriert; TypeScript akzeptiert die Zuweisung. Erst beim ersten Tastenkürzel scheitert der Code zur Laufzeit. Das Überraschende: strict: true war aktiv.

TL;DR

Unter strictFunctionTypes werden Parameter normaler Funktionstypen kontravariant geprüft: Ein Consumer darf nicht weniger Eingaben verstehen als sein Aufrufer liefern kann. TypeScript nimmt Methoden aus dieser strengeren Prüfung aus und behandelt ihre Parameter bivariant. Definiere öffentliche Callback- und Handler-APIs deshalb als Funktions-Properties – handle: (event: T) => void – wenn die sichere Richtung der Zuweisung wichtig ist.

Prerequisites

Du kennst strukturelle Typisierung, Generics und discriminated unions. Die Beispiele nutzen TypeScript 6.0 mit strict: true. Die relevante Ausnahme ist in der TSConfig-Referenz zu strictFunctionTypes und den TypeScript-2.6-Release-Notes dokumentiert.

// tsconfig.json
{
  "compilerOptions": {
    "strict": true,
    "noEmit": true,
    "target": "ES2022"
  },
  "files": ["handlers.ts"]
}

Der Aha-Effekt

Ein Handler ist ein Consumer. Wenn die Komponente jedes EditorEvent senden darf, muss der Handler ebenfalls jedes EditorEvent akzeptieren. Ein Handler, der nur TextChanged versteht, ist dafür zu speziell. Die sichere Zuweisungsrichtung läuft bei Eingabeparametern entgegen der Vererbungsrichtung – das ist Kontravarianz.

Methodensyntax sieht fast gleich aus, hat aber andere Zuweisungsregeln. TypeScript lässt Methoden aus Kompatibilitätsgründen bivariant; unter anderem bleiben dadurch generische Klassen und DOM-Hierarchien praktikabel. Diese Ausnahme ist dokumentiert, aber in einer Callback-API leicht zu übersehen.

So macht man es falsch

Die Methodensyntax lockert die Prüfung. Der folgende spezialisierte Handler kann als allgemeiner Handler durchrutschen:

type TextChanged = { kind: "text"; value: string };
type Shortcut = { kind: "shortcut"; command: "save" | "undo" };
type EditorEvent = TextChanged | Shortcut;

interface MethodHandler<T> {
  handle(event: T): void;
}

const textOnly: MethodHandler<TextChanged> = {
  handle(event) {
    console.log(event.value.toLowerCase());
  },
};

const unsafe: MethodHandler<EditorEvent> = textOnly; // erlaubt
unsafe.handle({ kind: "shortcut", command: "save" }); // Laufzeitfehler

Das Beispiel ist kein künstlicher Cast. Die problematische Information geht bei einer regulären Zuweisung zwischen zwei Instanzen desselben generischen Interfaces verloren.

Warum ist das falsch?

Der Aufrufer hält einen MethodHandler<EditorEvent> und darf daher beide Union-Mitglieder übergeben. Das konkrete Objekt kann aber nur eines davon verarbeiten. Bivarianz akzeptiert sowohl die sichere als auch die unsichere Richtung, obwohl die Implementierung beim Shortcut kein value erhält.

Das Symptom erscheint typischerweise nach einer API-Erweiterung: Ein Event-Union bekommt ein neues Mitglied, alte spezialisierte Handler bleiben zuweisbar und brechen erst auf dem neuen Pfad. Eine exhaustive Verzweigung kann gar nicht helfen, weil der Handler-Typ das zusätzliche Mitglied bereits ausgeblendet hat.

So macht man es richtig mit Trade-offs

Schreibe den Callback als Property mit einem Funktionstyp. Unter strictFunctionTypes wird die unsichere Zuweisung dann abgewiesen:

type Handler<T> = {
  handle: (event: T) => void;
};

const textOnly: Handler<TextChanged> = {
  handle: event => console.log(event.value.toLowerCase()),
};

// Fehler: Handler<TextChanged> ist nicht Handler<EditorEvent>
// const unsafe: Handler<EditorEvent> = textOnly;

const complete: Handler<EditorEvent> = {
  handle: event => {
    if (event.kind === "text") {
      console.log(event.value.toLowerCase());
      return;
    }
    console.log(`Command: ${event.command}`);
  },
};

Der Trade-off ist strengere Komposition: Einen spezialisierten Handler kannst du nicht mehr bequem in einen breiteren Kanal stecken. Wenn eine Komponente tatsächlich nur TextChanged emittiert, sollte ihr eigener Generic-Parameter das ausdrücken. Wenn mehrere Event-Arten getrennte Lebenszyklen haben, sind separate Callbacks wie onTextChange und onShortcut oft klarer.

Explizite Varianzannotationen wie in T sind hier keine Reparatur. Das Handbook warnt davor, sie zur Änderung strukturellen Verhaltens zu verwenden; TypeScript leitet die korrekte Varianz der Funktions-Property bereits ab.

Fallstricke am Rand

  • strictFunctionTypes ist Teil von strict, kann aber separat deaktiviert werden.
  • Die Ausnahme betrifft Methodendeklarationen, nicht jede Funktion, die als Objektwert geschrieben wird.
  • Ein Cast kann die Prüfung weiterhin umgehen und verschiebt das Risiko zurück zur Laufzeit.

Selbst ausprobieren

Kopiere beide Varianten in handlers.ts und aktiviere die gezeigte Konfiguration. Erwartung: Die Zuweisung mit MethodHandler bleibt erlaubt, dieselbe Zuweisung mit Handler erzeugt einen Typfehler. Führe anschließend die Methodenversion als JavaScript aus; beim shortcut-Event scheitert der Zugriff auf toLowerCase. Die Übung dauert etwa zehn Minuten.

Verwandte Themen

Discriminated Unions machen vollständige Eventbehandlung sichtbar. Event Maps koppeln Eventnamen an Payloads. Generic Component APIs können den tatsächlich emittierten Subtyp tragen. Variance Annotations helfen selten bei Diagnose und Performance, nicht als Ersatz für eine passende Struktur.
