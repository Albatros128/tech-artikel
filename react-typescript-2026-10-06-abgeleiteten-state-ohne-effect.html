Abgeleitete Werte gehören in den Renderpfad

Ein Effect, der gefilterte Daten in State kopiert, erzeugt eine zweite Wahrheit. Direkte Ableitung hält Eingaben und Ausgabe im selben Render konsistent.

06.10.2026 · React-Render-Verhalten · React 19.3 · Tief · ~8 min

Die Suche zeigt schon den neuen Text, die Ergebnisliste aber noch die Treffer der vorherigen Eingabe. Einen Moment später springt sie um. Bei schnellem Tippen wirkt die Oberfläche, als würde sie hinterherlaufen.

Oft steckt kein langsamer Filter dahinter. Die Komponente speichert lediglich etwas, das sie bereits aus users, query und direction berechnen könnte. Ein Effect aktualisiert diese Kopie erst nach dem Commit.

TL;DR

Wenn ein Wert vollständig aus aktuellen Props und aktuellem State entsteht, berechne ihn während des Renderns. Speichere nur die minimalen unabhängigen Eingaben. Nutze useMemo erst als gemessene Optimierung – nicht, um die Korrektheit der Ableitung herzustellen.

Prerequisites

Du solltest den React-Ablauf aus Render und Commit, den Zweck von useEffect und die Semantik von useMemo kennen. Die Beispiele orientieren sich an der aktuellen React-19.3-Dokumentation.

Der Aha-Effekt

State ist nicht einfach ein bequemer Ablageort. Er ist eine eigenständige Information, die sich über Zeit verändern kann. Speichert eine Komponente zusätzlich eine berechenbare Kopie, muss sie fortan zwei Wahrheiten synchron halten.

Der Renderpfad besitzt bereits den aktuellen Snapshot aller Props und State-Werte. Eine reine Funktion kann daraus unmittelbar die sichtbare Liste erzeugen. React empfiehlt ausdrücklich, Transformationen für die Darstellung auf Komponentenebene zu berechnen; ein Effect mit anschließendem State-Update startet den Ablauf erneut. [1]

So macht man es falsch

Diese Variante ist in echten Such- und Tabellenkomponenten verlockend: Der Effect „reagiert“ auf jede relevante Eingabe und schreibt das Ergebnis in einen separaten State.

Selbst mit vollständiger Dependency-Liste bleibt das Grundproblem bestehen. Fehlt später eine Dependency, wird daraus zusätzlich ein Stale-Data-Bug. Ist users bei jedem Parent-Render eine neue Array-Referenz, läuft der Effect auch bei inhaltlich unveränderten Daten erneut.

Warum ist das falsch?

Nach einer Eingabe rendert React zunächst mit dem neuen query, aber dem bisherigen visibleUsers. Erst nach dem Commit läuft der Effect. Dessen setVisibleUsers fordert einen zweiten Render an. React dokumentiert genau diesen kaskadierenden Ablauf für unnötige Effects. [1]

Das ist mehr als ein Performance-Thema: Innerhalb des ersten Render-Snapshots widersprechen sich Suchfeld und Liste. Tests müssen Zwischenzustände berücksichtigen, und Server Rendering kann den Effect überhaupt nicht ausführen. Effects sind für die Synchronisierung mit externen Systemen gedacht, etwa Browser-APIs, Netzwerkverbindungen oder fremde Widgets. [2]

So macht man es richtig

Extrahiere zuerst eine reine Ableitungsfunktion. filter erzeugt ein neues Array; sort mutiert nur dieses neue Array, nicht die Prop-Eingabe.

Die Komponente speichert nur Suchtext und Sortierrichtung. Die sichtbare Liste entsteht im selben Render:

Diese Version berechnet bei jedem Render neu. Das ist zunächst die richtige Semantik. Rendering soll eine reine Berechnung sein: gleiche Eingaben, gleiche Ausgabe, ohne fremde Objekte zu verändern. [3]

Ist die Ableitung nach Messung relevant teuer und ändern sich ihre Eingaben selten, kannst du genau die Zeile mit useMemo(() => deriveVisibleUsers(...), [users, query, direction]) umschließen. Der Trade-off sind Dependency-Pflege und zusätzlicher Code. React beschreibt useMemo ausschließlich als Performanceoptimierung; die Komponente muss auch ohne Cache korrekt funktionieren. [4]

Diagramm

flowchart TD
  A[Props oder State ändern] --> B[Render mit alter Ableitung]
  B --> C[Commit]
  C --> D[Effect berechnet]
  D --> E[setState]
  E --> F[Zweiter Render]
  A -. direkt ableiten .-> G[Render mit aktuellem Wert]
  G --> H[Commit]

Oben: Effect-basierte Synchronisierung committed zunächst eine veraltete Ableitung und fordert danach einen zweiten Render an. Unten: direkte Ableitung erzeugt den aktuellen Wert im ersten Render.

Fallstricke am Rand

  • Mutation: Sortiere keine Prop-Arrays direkt. Kopiere sie oder sortiere ein bereits neu erzeugtes Array.
  • Referenzidentität: Eine bei jedem Render neue Ergebnisliste kann memoized Child-Komponenten neu rendern lassen. Das ist ein möglicher Grund für gemessenes useMemo, nicht für abgeleiteten State.
  • Echte Synchronisierung: Muss das Ergebnis in URL, Local Storage oder ein fremdes Widget geschrieben werden, existiert ein externes System; dafür kann ein Effect sinnvoll sein.
  • Serverdaten: Lokales Filtern ist keine Alternative zu serverseitiger Pagination oder Suche, wenn der Client gar nicht den vollständigen Datensatz besitzt.

Selbst ausprobieren

Baue beide Varianten in einer kleinen React-Komponente nach und setze je einen console.count in den Komponentenrumpf und in den Effect. Tippe drei Zeichen in das Suchfeld. Beobachte in der Effect-Variante zusätzliche Renderdurchläufe und kurzfristig unterschiedliche Snapshots.

Teste danach deriveVisibleUsers separat: aktive Benutzer filtern, auf- und absteigend sortieren und prüfen, dass das Eingabearray unverändert bleibt. Für den Artikel liefen vier solche Prüfungen unter Node.js 24 erfolgreich. Ein TypeScript-Compiler und React-Runtime-Test standen nicht zur Verfügung; ein bestandener TSX-Typecheck wird daher nicht behauptet.

Verwandte Themen

State-Minimierung reduziert widersprüchliche Wahrheiten. Referenzstabilität erklärt, wann Memoization über Komponentengrenzen wirkt. React Profiler liefert Messdaten vor einer Optimierung. Server State trennt entfernte Daten von lokalem UI-State. Keys setzen State gezielt zurück, wenn sich die Identität einer Ansicht ändert.
