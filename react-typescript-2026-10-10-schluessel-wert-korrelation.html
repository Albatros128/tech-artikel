Ein Schlüssel und sein Wert müssen im Typ zusammenbleiben

Zwei korrekt aussehende Unions ergeben noch keinen korrekten Änderungsvertrag. Erst eine Union aus vollständigen Paaren erhält die Beziehung zwischen Feld und Wert.

TypeScript-Typsystem · TypeScript 6.0 · Tief · ~8 min

Ein Profil-Editor soll Änderungen als kleine Objekte an einen Reducer schicken. field darf nur bekannte Felder enthalten, value nur bekannte Werttypen. Der Code sieht streng typisiert aus. Trotzdem akzeptiert TypeScript plötzlich { field: "loginCount", value: "oft" }. Beide Einzelwerte gehören jeweils zu irgendeinem Feld – nur nicht zueinander.

TL;DR

Modelliere abhängige Angaben nicht als unabhängige Unions. Erzeuge mit einem Mapped Type für jeden Schlüssel eine vollständige Variante und lies diese Zwischenstruktur anschließend mit [keyof T] als Union aus. So bleibt field: "loginCount" mit value: number gekoppelt. Das Muster eignet sich für Reducer-Actions, Event-Queues, Formularänderungen und Command-APIs – aber nicht als Runtime-Validierung externer Daten.

Prerequisites

Du solltest keyof, Indexed Access Types und Mapped Types kennen. Die verwendeten Sprachmittel sind in TypeScript 6.0 unverändert verfügbar; der Artikel setzt strict und strictNullChecks voraus.

Der Aha-Effekt

keyof T liefert eine Union der Schlüssel. T[keyof T] liefert getrennt davon eine Union aller Werte. In einem Objekt mit beiden Typen entsteht ihr kartesisches Produkt: Jeder Schlüssel darf mit jedem Werttyp kombiniert werden. Die Korrelation existiert nicht mehr. Eine discriminated Union dreht die Modellierung um: Nicht „Schlüsselunion plus Wertunion“, sondern „Union aller gültigen Schlüssel-Wert-Paare“.

So macht man es falsch

Die folgende API beschränkt beide Properties und bleibt dennoch zu weit:

// profile-change.ts – typisiert, aber unkorreliert
type EditableProfile = {
  displayName: string;
  loginCount: number;
  newsletter: boolean;
};

type LooseChange<T extends object> = {
  field: keyof T;
  value: T[keyof T];
};

const acceptedByMistake: LooseChange<EditableProfile> = {
  field: "loginCount",
  value: "oft" // string gehört zu displayName – wird trotzdem akzeptiert
};

Warum ist das falsch?

Für EditableProfile wird field zu "displayName" | "loginCount" | "newsletter". Der Wert wird unabhängig zu string | number | boolean. Nirgends steht noch, dass "newsletter" genau boolean verlangt. Ein generischer Funktionsaufruf mit getrennten Parametern kann die Beziehung kurzfristig erhalten, aber beim Speichern in Arrays, beim Dispatchen oder Serialisieren brauchst du ein einzelnes Objekt, das diese Beziehung selbst trägt.

Beobachtbar wird der Fehler erst später: Ein Reducer schreibt einen String in ein Zahlenfeld, eine Validierungsfunktion wählt anhand von field die falsche Annahme oder ein Backend lehnt den Command ab. Der Typ hat Wertebereiche geprüft, aber nicht den Vertrag.

So macht man es richtig mit Trade-offs

Der Mapped Type erzeugt zunächst eine Property pro Feld. Jede Property enthält eine vollständige Variante. Der abschließende Indexed Access extrahiert die Property-Werte als Union:

// profile-change.ts – vollständiges TypeScript-Modul
export type ChangeOf<T extends object> = {
  [K in keyof T]-?: { field: K; value: T[K] }
}[keyof T];

export type EditableProfile = {
  displayName: string;
  loginCount: number;
  newsletter: boolean;
};

export type ProfileChange = ChangeOf<EditableProfile>;

export function describeChange(change: ProfileChange): string {
  switch (change.field) {
    case "displayName":
      return `Name: ${change.value.toUpperCase()}`; // value ist string
    case "loginCount":
      return `Logins: ${change.value.toFixed(0)}`;  // value ist number
    case "newsletter":
      return change.value ? "Newsletter an" : "Newsletter aus";
  }
}

export function applyChange(
  profile: EditableProfile,
  change: ProfileChange
): EditableProfile {
  return { ...profile, [change.field]: change.value };
}

Das -? entfernt Optionalität von der gemappten Zwischenstruktur. Ohne diesen Modifier könnte ein optionales Quellfeld beim abschließenden Indexzugriff zusätzlich undefined als ganze Union-Variante einführen. T[K] darf für ein optionales Feld weiterhin selbst undefined enthalten – das ist eine separate fachliche Entscheidung.

Der Trade-off liegt in der Typkomplexität. Bei zwei stabilen Feldern sind explizite Varianten oft lesbarer. Bei vielen Feldern oder häufigen Änderungen verhindert die Ableitung dagegen Drift. Wenn unterschiedliche Felder zusätzliche Metadaten oder Berechtigungen brauchen, ist ein bewusst formulierter Command-Typ besser als noch mehr Typ-Metaprogrammierung.

Textuelle Erklärung: Aus jedem Profilfeld entsteht zunächst eine eigene Variante. Der Indexzugriff vereinigt diese Varianten, ohne die Beziehung zwischen jeweiligem Schlüssel und Wert zu verlieren.

Fallstricke am Rand

  • Symbole und numerische Schlüssel landen ebenfalls in keyof T; begrenze bei JSON-Commands gegebenenfalls auf Extract<keyof T, string>.
  • Readonly-Felder sollten vor der Ableitung mit Pick oder einem expliziten editierbaren Modell ausgeschlossen werden.
  • Ein Type Assertion wie as ProfileChange kann den Schutz wieder umgehen.
  • Nach JSON.parse brauchst du weiterhin Runtime-Validierung.

Selbst ausprobieren

Kopiere beide Typen in den TypeScript Playground. Lege je eine Änderung für displayName, loginCount und newsletter an. Vertausche danach zwei Werte. Erwartung: LooseChange akzeptiert die falschen Paare; ChangeOf meldet sie. Ergänze anschließend ein Feld locale: "de" | "en". Die neue gültige Variante soll automatisch entstehen. Dauer: etwa zehn Minuten.

Verwandte Themen

Discriminated Unions ermöglichen das Narrowing im switch. Key Remapping kann technische Felder bei der Ableitung herausfiltern. Conditional Types helfen, nur Felder bestimmter Wertklassen auszuwählen. NoInfer ist nützlich, wenn eine generische Funktion ihren Modelltyp nicht zusätzlich aus dem Change-Argument ableiten soll. Schema-Validierung überführt dieselbe Korrelation an Runtime-Grenzen.
